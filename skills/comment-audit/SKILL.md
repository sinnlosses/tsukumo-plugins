# コメント監査

コメントを1ブロックずつ、決まった順番の問いに通して「消す／縮める／正典へ移す／残す」に分ける。
**直すのはコメントだけで、コードには触らない。** コメントが要るのはコードが分かりにくいからだ、と
いう箇所は、リファクタの候補として報告するだけにする。

最適化するのは**読み手が1ブロックを読んで得るもの**で、消した行数ではない。本物の警告を消す損は、
出来の悪いコメントを1つ残す損より大きい。**迷ったら残す。**

## 判定の1問

すべての判定はこの1問に落ちる: **このコメントを消したとき、コードだけを見て直した人が壊す・
誤って使う場面を、具体的に1つ挙げられるか。** 挙げられなければ消す。挙げられた場面が、
リポジトリ全体の規約や設計判断を読めば防げるもの（正典に従っているだけのもの）なら、それも消す。
下の「判定の順番」の表は、この1問に当てはめやすい種類ごとの当たりを先に並べたもので、
表のどれにも当たらなければこの1問へ戻って考える。

## 始める前に

1. **プロジェクトの規約を読む。** `CLAUDE.md` と、そこから引かれているコーディング規約のコメントの
   節を探す。規約がこのスキルの判定と食い違ったら**規約のほうに従う**（たとえば「正典の節への参照を
   残す」「行数の目安を置かない」）。正典（設計判断・経緯・用語を置く `docs/` のファイル）がどこかも
   ここで押さえる
2. **範囲を決める。** ファイル・ディレクトリ・差分（`git diff <起点>`）のどれか。リポジトリ全体と
   言われたら、先に量を測って順番を決める:

   ```bash
   python3 ${CLAUDE_SKILL_DIR}/scripts/comment_density.py src --exclude .test. --top 20
   ```

   出るのはコメント行の割合・ブロックの長さ別の内訳・割合の高いファイルの表。**コメント行の多くが
   長いブロック（5行以上）にあるなら、効くのは「縮める」の段**で、1行の言い直しを消しても量は
   ほとんど減らない。この内訳を利用者に見せてから始める
3. **1回に回すのは1〜数ファイル。** 広い範囲は、ディレクトリや機能ごとのまとまりに分けて続ける
   （1回の差分を人が読める大きさに保つ）

## 判定の順番

ブロックごとに、上から順に問う。**最初に当たったところで決まる。** どれにも当たらなければ残す。

| # | 問い | 当たったら |
| --- | --- | --- |
| 1 | 型名・関数名・引数名・次の1行を言い直しているだけか | 消す |
| 2 | 昔の実装・過去の設計・「以前は〜だった」「〜をやめた」の話か | 正典へ移して消す |
| 3 | いつ決まったか・誰が言ったか（日付・「〜の指摘」「ユーザーの決定」）か | その部分を消す。理由は残す |
| 4 | 採らなかった案の比較（どの案をなぜ捨てたか）か | 正典へ移して消す。**素直に書き直すと壊れることを防ぐ一言だけは残す** |
| 5 | ほかの箇所との照らし合わせ（「〜と同じ割り切り」「〜と同じ考え方」）か | 消す。揃えておく義務があるときだけ `{@link}` か1行の参照にする |
| 6 | 正典に書いてあることの要約か | 消す。参照も置かない |
| 7 | 規約・方針・設計判断に従っているだけ（「〜の規約どおり」とその正典への参照）か | 消す |
| 8 | 用語の出典（用語集などの語を指すだけ）か | 消す |
| 9 | 同じ制約を、呼び出しの経路上の別の関数でも書いているか | それを決めている関数の1か所に寄せ、ほかは参照にする |
| 10 | このコードを呼ぶ側・使う側を並べているか（「〜が呼ぶ」「〜が使う」） | 消す。呼ぶ側に求める条件だけを「何が満たされているか」で残す。今の使い手はエディタの参照検索が出す |
| 11 | 今のコードと食い違っている（古くなった）か | 消す。挙動のほうが正しいか怪しければ、消さずに報告する |
| 12 | ファイル・モジュールの責務／外から使うものの契約／規約の例外／今の挙動の制約・前提・外部との対応関係／見落としやすい罠のどれかか | 残す |

**長いブロックは、段落ごとにこの順番を当てる。** 1つのブロックに「残す制約」と「照らし合わせ」
「経緯」が混ざっているのが、長いコメントのいちばん多い形。残す段落だけにすれば、制約はそのまま
で短くなる。残した段落の言い回しは削るが、**言っていることの数は減らさない**。

### 残すときの指し方

残すブロックが別の場所をファイルのパス・節の番号で指していたら、移設・改名で古くならないものに
替える。コードはシンボルの名前（JSDoc の中なら `{@link}`）、ドキュメントは節の見出しの句で指す。
パスは、実在しなくなっても何も落ちないまま残りやすい。プロジェクトの規約が指し方を決めていれば、
規約のほうに従う。

節への参照を添えるのは、残すと決めた制約の理由が長くて正典にあり、それを読まないと直してよいかを
決められないときだけ。コメントは制約そのものを自分の言葉で書き、参照は理由の置き場としてだけ
添える。参照だけで制約を言っていない（規約・方針への参照、用語の出典）コメントは上の判定表で
すでに消す対象なので、ここでは残さない。

### 正典へ移すとき

先に正典の該当箇所を見る。**既に書いてあれば消すだけ、無ければ正典に書いてから消す。**
コードに残すのは、必要なら節への1行の参照だけ。プロジェクトに正典の置き場が無いなら、
移さずに「移す候補」として報告に挙げる（置き場を勝手に作らない）。

### 触らないもの

- ライセンスの表記・生成物の印（`// @generated` など）・lint や型検査への指示
  （`eslint-disable`・`@ts-expect-error` の理由の行など）
- 公開 API のドキュメントコメントのうち、利用者向けの契約（引数の単位・投げる例外・スレッド安全性）
- 文字列リテラルの中身（プロンプトや説明文）。コメントに見えても、コードの一部

## 直したあと

1. プロジェクトの検証コマンドを通す（コメントしか触っていなくても、整形・lint・コメントを読む
   テストがある）
2. 報告する:
   - 判定ごとのブロック数と、減ったコメント行の数
   - 正典へ移したもの（移した先の節）
   - **コメントで補っている分かりにくいコード**（リファクタの候補）と、
     **挙動のほうが怪しい古いコメント**。どちらも直さずに挙げる
   - 迷って残したもの（多ければ、判定を利用者と擦り合わせる材料になる）

## 書く前に効かせる

掃除だけでは、次に書くコメントでまた溜まる。監査で同じ種類が繰り返し当たったら、その種類を
プロジェクトのコメントの規約（判定の表）に足すよう提案する。**提案に留め、規約は利用者の承認を
得てから直す。**
