会話の明示の指示と、引数 `<パス>` のファイルと、エージェントのドラフト（`tw status` の着手可否が `DRAFT` の課題）をタスクにする。ルールは `task-model` スキルの
`WORKFLOW.md`（以下「正典」）。`tw` は
`task-model` のタスク運用のコマンド（`tw-reference.md`「`tw` コマンドの参照」）。

**登録までで止め、実行はしない**（実行は `/next-task`）。分解は方針決めを含むので、**委譲せず
ユーザーがいるセッションで行い**、`/loop` や `/next-task` からは呼ばない。

## このプロジェクトの設定（`tw config`）

!`tw config 2>&1 || true`

タスクは Beads に置かれている（正典「Beads とトラッカー」）。トラッカーが `github` なら、タスクID は
`tw new` が返す Issue 番号の `GH-<n>` で、`T-xxx` をそう読み替える。`--deps` にもその形で渡す。
`## 完了条件` に書く**検証コマンド**は `verify` の行の値。`なし` なら完了条件は検証可能な言葉だけで書く。
`MISSING` の行などで設定が読めないときは `task-model` スキルの `preflight.md` に従う。

## 手順

0. **依存を確かめる**: `task-model` スキルの `preflight.md` に従う。

1. **読む**: `tw status` で既存の一覧を見る（本文は読まない。重なりそうな1件があるときだけ
   `tw show T-xxx` で読む）。終了コード6（`MISSING`）なら
   タスク運用を始めてよいかユーザーに確かめてから `/setup-tasks`、1・3 は理由を報告して終了する。

   会話・引数・`tw status` の `DRAFT` の行と `triage` 行を見て、扱うものを決める（判定は保守的に。迷ったら拾わない）:

   | 入口 | 扱い |
   | --- | --- |
   | 引数 `<パス>` のファイル（`/plan-tasks <パス>`） | そのファイルを全体読んで手順2へ。そのファイルは消さず書き換えない |
   | `tw status` の着手可否が `DRAFT` の行（ドラフトの課題） | `tw show <ID>` で読んでユーザーに見せる。**承認を得たものだけ**手順2へ進め、手順4のとおり `## 完了条件`・`## やること` を書き起こして手順5の「ドラフトを進める」で `todo`（判断待ちなら `hold`）にする。却下されたものは手順5の「ドラフトを却下する」で閉じる。答えが無いものは触らない |
   | 会話の明示の指示（「これタスクにして」「それでいいよ」） | そのまま手順2へ |
   | `tw status` の `triage` 行（トラッカーから取り込んだ振り分け前の課題） | `tw show <ID>` で読み、`## 完了条件`・`## やること`・`difficulty`・`loopable` を書き起こしてユーザーに見せ、承認を得たものだけ `tw adopt` する（手順5） |
   | どれも無い | 未対応の指示は無いと報告して終了する |

2. **確かめる**: 各項目について**いまの `main` のコードとドキュメントを読んで裏を取る**。すでに
   満たされている・事実と違うと分かったものはタスクにせず、根拠を添えて報告する（勝手に消さない）。
   待ち時間・実行時間を縮めることが目的の項目（「〜を速くする」「時間を半分にする」の類い）は、
   読むだけで済ませず**実際に走らせて段ごとの内訳**（何に何秒・何分掛かったか、どう測ったか）を測る。
   走らせて測る前に `tw metrics --stages --days 28` を打ち、記録から遅い段を引く。項目が `/next-task` の
   サイクルの段のことなら、その行を前提にして `### 実測の内訳` に写す（測り方は `tw metrics --stages` の
   記録。`tw-reference.md` の `metrics` の行）。記録が無い・項目がサイクルの外の処理なら、これまでどおり走らせて測る。
   測った結果が項目の前提（どこが遅いか）と違ったら、前提と完了条件の数値を実測に合わせて書き直してから
   手順3へ進み、書き直したことを報告の「人に知らせること」に出す。
   項目の本文が前提にする既存の振る舞い（「既存」「いまは〜」「GH-nnn が入れた」）も実物で確かめ、
   食い違いは登録の前に直す（決まりは `WORKFLOW.md` の「タスクの本文」の「段の中身の書き方」）。

3. **分解する**: 1項目＝1タスクとは限らない。方針決めが要るものは前段のタスクに切り出して
   `dependencies` で後ろに置く。**前段が設計を書くタスクなら、後段の `## 目的・背景` には設計の結論を
   先取りして書かず、前段の `## 完了条件` に「後段（対象のタスクIDの範囲）の本文を設計の結論に
   合わせて直す」を足す。揃えるときは実装の広がり（消す口・プロトコルの変更・触る機能の数）を見て
   後段の `difficulty` も見直す、も同じ完了条件に入れる。** 1タスクは1コミットで説明が付く大きさに。既存タスクと重なるなら
   新しく作らず、その本文の `## 目的・背景` か `## 注意` に足す（`tw show` の本文に足して
   `tw edit T-xxx --change-frame --body-file -`）。
   既存のタスクどうしで後段を前段に待たせたいときは、本文の `## 注意` に書くだけにせず
   `tw edit T-後段 --add-deps T-前段` で Beads に入れる（`tw status` の BLOCKED に出て、別のセッションの
   `/next-task` が依存を無視して着手しなくなる。外すのは `--remove-deps`）。

4. **書く**: `summary` は1行（収まらなければ大きすぎるので手順3へ戻る。正典「summary」）。
   `loopable` を決める前に、正典「loopable」の「止まる要因」の表を本文に当てて、実行中に利用者の手が要って
   止まる要因を洗い出す。解ける要因はその場でユーザーに聞き、結果を `## 決まっていること（蒸し返さない）` に
   焼いて `Y`、解けない要因が残れば `N`（`Y` のまま実行中に質問が要ると、hook の `tw ask-guard` が拒んで `N` に直させる）。判断を待つ事柄そのものが残るなら
   `--hold` にする。本文は**正典「タスクの本文」の枠（7つの見出しをこの順に全部）**で書き、
   書くことの無い欄は見出しだけ置いて空か「なし」にする:

   - `## 目的・背景`（何のためか、コードのどこがどうなっているかをファイル名・関数名つきで）と
     `## 完了条件`（検証可能な言葉。検証コマンドを通すことを毎回書き、その値は書き写さない（引数を足した形を含む）。全段が要る作業は設定の `verify_before_ship` に任せる）は空にできない
   - `## 解くべき論点` は `opus` なら必ず書く
   - 待ち時間・実行時間を縮めるタスクは、`## 目的・背景` の中に小見出し `### 実測の内訳` を置き、手順2の
     内訳（段・秒数や分数・測り方）を書く。内訳が無いまま登録せず手順2へ戻る（測れないなら、測ることを
     前段のタスクにして `dependencies` で後ろに置く）
   - **`## やること` は必ず書く**（空だと `tw new` が拒む。正典「タスクの本文」）。手順2で読んだ
     いまの主ブランチをもとに、`### 1. …` の形で実行の順に番号を振った段で書き、`## 完了条件` の各行を
     どの段のどのファイルのどこをどう直して満たすかまで書く。並べて走らせてよい段は段の欄を書く（正典
     「タスクの本文」の「段の形」）。段の中身は正典「タスクの本文」の「段の中身の書き方」に従って書く。
     小見出し `### 名指すファイル`・`### 作業先` は正典「タスクの本文」の「登録時に書く `## やること`」に従って置く。空にできるのは `--hold` で登録するものだけ（todo に戻したあと、
     着手のときに書く）。あわせて `## 完了条件` か `## 注意` に「調べて成り立たなければ `dropped` で
     閉じてよい」逃げ道を書く
   - 文書の写しを畳むタスクの対応づけの段は、正典「段の中身の書き方」に従って置く。一覧は
     `python3 ${CLAUDE_SKILL_DIR}/scripts/removed_lines.py` が、ファイルごとに「消した行 | 残る先」の
     表の下書き（動かしただけの行と空行は出ない。記号だけの行は動かしても出る）で出す。作業ツリーに残すなら
     範囲を付けずに作業ツリーで打ち（git add 済みと未追跡のファイルも見る）、コミットを積む別の作業ツリーなら
     `main..<枝>` を付ける。本文にはその両方の打ち方を、委譲先が別のリポジトリから打てるよう
     `${CLAUDE_SKILL_DIR}` を実際の絶対パス（リンクで入れていれば
     `~/.claude/skills/plan-tasks/scripts/removed_lines.py`）に置き換えて書く
   - 会話で画（SVG・画像・HTML のラフ）を見せて合意した項目は、その画を作業先のリポジトリの
     見本の置き場にファイルで保存し、`## 決まっていること（蒸し返さない）` か `## 参考情報` から
     パスで名指す。言葉の説明は残し、食い違ったら見本が勝つと書く。置き場は作業先の CLAUDE.md や
     docs が決めていればそこ、無ければ会話で決める。決まらなければ保存せず、見本が無いことを本文に書く
   - 委譲しない近道の印（`tw new --direct`）は、正典「difficulty とモデルの切り替え」の「委譲しない近道」の
     基準の表に当たるときに付ける。表の値（`difficulty`・段の数・名指すファイルの数・作業先）は `tw` が検査するので
     値を覚えて書かず表を読む。人が見るのは、振る舞いの契約（公開の出力・引数・終了コード・正典の規則）を
     変えないことだけで、変えるかもしれないなら付けない
   - グローバルへのリンク（例: パッケージマネージャのグローバルリンク）・brew・シェルの設定ファイル・mise の
     グローバル設定・ホームのディレクトリの削除のような、ホームや共有の環境を変える手順は、
     `## 注意` の中に `### 人がやること` の小見出しで分けて書き、委譲先には渡さない。この小見出しが
     残るタスクは、正典「loopable」の「止まる要因」の表で見る（検証より前に要る手順があれば `N`、
     `ship` のあとでよいものだけなら `Y`）

5. **登録する**: 依存の先にあるものから1件ずつ `tw new`（`CREATED` の ID を後ろの `--deps` に使う）。
   `--summary` は単一引用符で囲む（`` ` `` を含むことが多い）:

   ```bash
   tw new --summary '`readTaskSummaries` をタスクの置き場から読む' --difficulty sonnet --loopable Y \
     --deps T-521 --body-file - <<'EOF'
   ## 目的・背景
   …
   ## 決まっていること（蒸し返さない）
   なし
   ## 解くべき論点
   なし
   ## やること
   ### 1. 要約をタスクの置き場から読む
   `src/task-summary.ts` の `readTaskSummaries` を …（完了条件の1行目）
   ### 2. テストを足す
   …（完了条件の2行目）
   ### 名指すファイル
   - `src/task-summary.ts`
   - `test/`（テストを置く）
   ## 完了条件
   …
   ## 注意
   なし
   ## 参考情報
   なし
   EOF
   ```

   近道の印を付けるタスク（手順4）は `--direct` を足す（例 `tw new --summary '…' --difficulty haiku --loopable Y --direct --body-file - <<'EOF'`）。
   `tw adopt` も同じく `--direct` を足す。

   | 出力 | すること |
   | --- | --- |
   | `CREATED` | 次の1件へ |
   | 終了コード2で「近道は…」 | 近道の印（`--direct`）が基準を外れた。`--direct` を外して打ち直す（基準に合わせて計画を縮めない） |
   | `LOCKED` | 採番の錠が取れない。行に `rmdir` が添えてあれば古い錠なので、その旨を報告して止まる（壊さない） |
   | 終了コード2 | 本文が枠と違う（見出しの欠け・順・枠の外の見出し）・空にできない欄が空・`## やること` が空（`--hold` を除く）・`### 名指すファイル` が無い・形が違う・パスが主ブランチ（`### 作業先` があればそのリポジトリの主ブランチ）の木に無い・`### 作業先` が絶対パス1行でない・git のリポジトリの根でない・Beads に無い `--deps`（解決済みなら外す）。直して打ち直す |
   | 続く行の `TRACKER\tFAILED` | 登録は済んでいる。報告に添え、最後に `tw sync` を1回打ち直す |

   振り分け前の課題は `tw new` ではなく
   `tw adopt <ID> --difficulty … --loopable … --body-file -`（`ADOPTED` の3列目が振られた ID）。
   本文は `tw new` と同じく手順4のとおり書く（`## やること` も要る。終了コード2の理由も同じ）。

   **ドラフトを進める**（承認を得たドラフトの課題）: `tw new` は打たず、同じ課題を書き足す。`## 目的・背景` は
   ドラフトの書いたまま残し（変えるなら `--change-frame`）、`## 完了条件`・`## やること` などを
   `tw edit <ID> --section '<節名>' --body-file -` で1節ずつ書く（ドラフトの空の節を初めて書く編集は `FRAME_CHANGED` にならない）。
   見立ての `difficulty`・`loopable` は `tw edit <ID> --difficulty … --loopable …` で直す。書けたら
   `tw edit <ID> --status todo`（判断待ちが残るなら `hold`）。出力が `NOT_READY\t<ID>\tDRAFT\t<理由>` なら、
   本文が `tw new` の検査を通っていない（状態は変わっていない）ので、理由のとおり直して打ち直す。

   **ドラフトを却下する**: 却下の理由を `## 結果` にして `tw done <ID> --dropped --result-file -`。
   `claim` もコミットも `tw ship` も要らず、`DONE\t<ID>\tbeads:<id>\tドラフトを閉じた` でその場で閉じる。

6. **送る**: タスクは Beads に入っていて、引数のファイルは消さず書き換えないので、コミットするものは普通は無い。
   その場合はコミットも `tw ship` も打たない。作業ツリーに自分の変更が出ていたときだけ、整形コマンド
   （`tw config` の `format` の行があれば）を打ってから 1 コミット（件名にタスクIDを付けない）→ `tw ship`。
   `SHIPPED` 以外なら、task-model の `tw-reference.md` の終了コード表のとおり止まって預ける。push はしない。

## 完了報告のフォーマット

報告は人が読むためのもの。

1. **結論を1文目に置く**: 「N件を T-xxx〜T-yyy として登録し、main へ送りました。」。
   `SHIPPED` 以外で止まったときは、止まったことと先頭語を結論にする
2. **対応表**（全項目。**取りこぼしの検知点はここだけなので必ず出す**）: 列は
   項目・発言 | タスクID | `summary` | `difficulty` | `loopable` | 依存 | `hold`。
   ドラフト由来は承認の発言を表の見出しの1行に添える（ドラフトの課題はその ID のまま）。タスクにしなかった項目と、残した
   未承認のドラフト・却下して閉じたドラフトも行に入れ、タスクIDの列に理由を書く
3. **人に知らせること**があるときだけ: 裏取りで項目の中身と違うと分かったこと、その場で
   決めてもらったこと、`loopable: N` と `hold` の理由（`/loop` では進まないため）

書かないもの: `SHIPPED` の範囲・コミットのハッシュ、`tw status` の件数、
どの項目をどの入口から拾ったか（決まった手順のとおりで、見たければ `tw status` で見られる）。
