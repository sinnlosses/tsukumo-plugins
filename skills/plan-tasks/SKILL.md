`develop/direction.md` と `develop/draft/` に溜まった指示をタスクにする。ルールは `task-workflow` スキルの
`WORKFLOW.md`（以下「正典」）。`tw` は
`task-workflow` のタスク運用のコマンド（正典「`tw` コマンドの参照」）。

**登録までで止め、実行はしない**（実行は `/next-task`）。分解は方針決めを含むので、**委譲せず
ユーザーがいるセッションで行い**、`/loop` から直接は呼ばない。例外は `/next-task` が `READY` 0件の
ときに無人でこの手順を読む場合で、そのとき扱ってよいのは `## ユーザーから`（ファイル入口）
だけ（以下「無人のとき」）。

## このプロジェクトの設定（設定ファイル AGENTS.md → CLAUDE.md の「## タスク運用」節）

!`r=$(git rev-parse --show-toplevel 2>/dev/null); n=; for f in AGENTS.md CLAUDE.md; do [ -n "$r" ] && [ -f "$r/$f" ] && s=$(sed -n '/^## タスク運用/,/^## /p' "$r/$f" | grep .) && [ -n "$s" ] && { n=$f; break; }; done; if [ -n "$n" ]; then echo "（$n から読んだ）"; echo "$s"; else echo '（「## タスク運用」節が無い。AGENTS.md・CLAUDE.md の他の節に書かれた検証コマンドを探す。無ければ /setup-tasks で節を用意する）'; fi`

節に `- タスクの置き場: beads` があれば **Beads 方式**（正典「Beads 方式」）で、下の「Beads 方式では」の
注記に読み替える（トラッカーが `github` なら、タスクID は `tw new` が返す Issue 番号の `GH-<n>` で、
`T-xxx` をそう読み替える。`--deps` にもその形で渡す）。`## 完了条件` に書く**検証コマンド**はこの節の値。`なし` なら完了条件は検証可能な言葉だけで書く。

## 手順

0. **依存を確かめる**: `command -v tw` が何も返さなければ、`tw` が PATH に張られていないとして
   `MISSING` を報告して終了する（plugin で入れるなら `/plugin install tsukumo-workflow@tsukumo-plugins`、
   リンクで入れるなら `task-workflow` を含めて `./install.sh` を打ち直すよう案内する）。

1. **読む**: `tw status` で既存の一覧を見る（本文は読まない。重なりそうな1件があるときだけ
   `develop/task/T-xxx.md` を開く。Beads 方式では `tw show T-xxx`）。終了コード5（`LEGACY`）なら「旧形式。正典「旧形式からの移行」の
   手順で `tw migrate --dry-run` から移す（スキルは移さない）」と案内して終了、6（`MISSING`）なら
   タスク運用を始めてよいかユーザーに確かめてから `/setup-tasks`、1・3 は理由を報告して終了する。

   `develop/direction.md` と `develop/draft/` を見て、扱うものを決める（判定は保守的に。迷ったら拾わない）:

   | 置き場・入口 | 扱い |
   | --- | --- |
   | `develop/direction.md` の `## ユーザーから`（節見出しの無い古いファイルは全体） | そのまま手順2へ |
   | `develop/draft/` のファイル（1件1ファイル） | 項目をユーザーに見せ、**承認を得たものだけ**手順2へ。無人のときは見ない |
   | `develop/direction.md` に残った旧い `## エージェントのドラフト` の節 | 1件ずつ正典「指示メモ」の形で `develop/draft/` のファイルへ移して節を消し、上の行と同じに扱う。無人のときは触らない |
   | 会話の明示の指示（「これタスクにして」「それでいいよ」） | `develop/direction.md` を経由せず手順2へ。無人のときは使わない |
   | Beads 方式の `triage` 行（トラッカーから取り込んだ振り分け前の課題） | `tw show <ID>` で読み、`## 完了条件`・`## やること`・`difficulty`・`loopable` を書き起こしてユーザーに見せ、承認を得たものだけ `tw adopt` する（手順5）。無人のときは見ない |
   | どれも無い | 未対応の指示は無いと報告して終了する |

2. **確かめる**: 各項目について**いまの `main` のコードとドキュメントを読んで裏を取る**。すでに
   満たされている・事実と違うと分かったものはタスクにせず、根拠を添えて報告する（勝手に消さない）。
   待ち時間・実行時間を縮めることが目的の項目（「〜を速くする」「時間を半分にする」の類い）は、
   読むだけで済ませず**実際に走らせて段ごとの内訳**（何に何秒・何分掛かったか、どう測ったか）を測る。
   走らせて測る前に `tw metrics --stages --days 28` を打ち、記録から遅い段を引く。項目が `/next-task` の
   サイクルの段のことなら、その行を前提にして `### 実測の内訳` に写す（測り方は `tw metrics --stages` の
   記録。`WORKFLOW.md` の `metrics` の行）。記録が無い・項目がサイクルの外の処理なら、これまでどおり走らせて測る。
   測った結果が項目の前提（どこが遅いか）と違ったら、前提と完了条件の数値を実測に合わせて書き直してから
   手順3へ進み、書き直したことを報告の「人に知らせること」に出す。

3. **分解する**: 1項目＝1タスクとは限らない。方針決めが要るものは前段のタスクに切り出して
   `dependencies` で後ろに置く。**前段が設計を書くタスクなら、後段の `## 目的・背景` には設計の結論を
   先取りして書かず、前段の `## 完了条件` に「後段（対象のタスクIDの範囲）の本文を設計の結論に
   合わせて直す」を足す。揃えるときは実装の広がり（消す口・プロトコルの変更・触る機能の数）を見て
   後段の `difficulty` も見直す、も同じ完了条件に入れる。** 1タスクは1コミットで説明が付く大きさに。既存タスクと重なるなら
   新しく作らず、その本文の `## 目的・背景` か `## 注意` に足す（`develop/task/T-xxx.md` を直して手順7で
   一緒にコミットする。Beads 方式では `tw show` の本文に足して `tw edit T-xxx --change-frame --body-file -`）。
   既存のタスクどうしで後段を前段に待たせたいときは、本文の `## 注意` に書くだけにせず
   `tw edit T-後段 --add-deps T-前段` で台帳に入れる（`tw status` の BLOCKED に出て、別のセッションの
   `/next-task` が依存を無視して着手しなくなる。外すのは `--remove-deps`）。

4. **書く**: `summary` は1行（収まらなければ大きすぎるので手順3へ戻る。正典「summary」）。
   `loopable` を `N` にしたくなったら、その場でユーザーに聞く（正典「loopable」の表。聞いて解けたら
   結果を `## 決まっていること（蒸し返さない）` に焼いて `Y`）。判断を待つ事柄そのものが残るなら
   `--hold` にする。本文は**正典「タスクファイル」の枠（7つの見出しをこの順に全部）**で書き、
   書くことの無い欄は見出しだけ置いて空か「なし」にする:

   - `## 目的・背景`（何のためか、コードのどこがどうなっているかをファイル名・関数名つきで）と
     `## 完了条件`（検証可能な言葉。検証コマンドを通すことを毎回書く）は空にできない
   - `## 解くべき論点` は `opus` なら必ず書く
   - 待ち時間・実行時間を縮めるタスクは、`## 目的・背景` の中に小見出し `### 実測の内訳` を置き、手順2の
     内訳（段・秒数や分数・測り方）を書く。内訳が無いまま登録せず手順2へ戻る（測れないなら、測ることを
     前段のタスクにして `dependencies` で後ろに置く）
   - **`## やること` は必ず書く**（空だと `tw new` が拒む。正典「タスクファイル」）。手順2で読んだ
     いまの主ブランチをもとに、`### 1. …` の形で実行の順に番号を振った段で書き、`## 完了条件` の各行を
     どの段のどのファイルのどこをどう直して満たすかまで書く。並べて走らせてよい段は段の欄を書く（正典
     「タスクファイル」の「段の形」）。段の中身は正典「タスクファイル」の「段の中身の書き方」に従って書く。
     小見出し `### 名指すファイル` に、計画が
     前提にするファイル（新しく作るファイルは置くディレクトリ）をリポジトリの根からの相対パスで並べる。
     作業先が別のリポジトリなら、小見出し `### 作業先` にそのリポジトリの根の絶対パスを1行置き、
     名指すファイルはその根からの相対にする。空にできるのは `--hold` で登録するものだけ（todo に戻したあと、
     着手のときに書く）。あわせて `## 完了条件` か `## 注意` に「調べて成り立たなければ `dropped` で
     閉じてよい」逃げ道を書く
   - 文書の写しを畳む（重複した記述を消して正典へ寄せる）タスクは、`## やること` の最後の実装の段のあとに、
     消した行の一覧を出して1行ずつ残る先（正典の表の行・残した文）を対応づける段を置く。一覧は
     `python3 ${CLAUDE_SKILL_DIR}/scripts/removed_lines.py` が、ファイルごとに「消した行 | 残る先」の
     表の下書き（動かしただけの行と空行は出ない。記号だけの行は動かしても出る）で出す。委譲先が作業を
     コミットせずに作業ツリーに残すなら範囲を付けずに作業ツリーで打ち（git add 済みと未追跡のファイルも
     見る）、コミットを積む別の作業ツリーなら `main..<枝>` を付ける。本文にはその両方の打ち方を書く。
     委譲先が手で数えない。本文には委譲先が別の
     リポジトリから打てるよう、`${CLAUDE_SKILL_DIR}` を実際の絶対パス（リンクで入れていれば
     `~/.claude/skills/plan-tasks/scripts/removed_lines.py`）に置き換えて書く。`## 完了条件` には
     「消した行の全部に残る先を対応づけた表が報告にある（残る先の無い行は、消してよい理由を添える）」を入れる
   - 会話で画（SVG・画像・HTML のラフ）を見せて合意した項目は、その画を作業先のリポジトリの
     見本の置き場にファイルで保存し、`## 決まっていること（蒸し返さない）` か `## 参考情報` から
     パスで名指す。言葉の説明は残し、食い違ったら見本が勝つと書く。置き場は作業先の CLAUDE.md や
     docs が決めていればそこ、無ければ会話で決める。決まらなければ保存せず、見本が無いことを本文に書く
   - 委譲しない近道の印（`tw new --direct`）は、正典「difficulty とモデルの切り替え」の「委譲しない近道」の
     基準の表に当たるときに付ける。表の値（`difficulty`・段の数・名指すファイルの数・作業先）は `tw` が検査するので
     値を覚えて書かず表を読む。人が見るのは、振る舞いの契約（公開の出力・引数・終了コード・正典の規則）を
     変えないことだけで、変えるかもしれないなら付けない
   - グローバルへのリンク（例: パッケージマネージャのグローバルリンク）・brew・シェルの設定ファイル・mise の
     グローバル設定・ホームのディレクトリの削除のような、ホームや共有の環境を変える手順は、
     `## 注意` の中に `### 人がやること` の小見出しで分けて書き、委譲先には渡さない。この小見出しが
     残るタスクは、`loopable` を決めるときの判断材料に入れる

5. **登録する**: 依存の先にあるものから1件ずつ `tw new`（`CREATED` の ID を後ろの `--deps` に使う）。
   `--summary` は単一引用符で囲む（`` ` `` を含むことが多い）:

   ```bash
   tw new --summary '`readTaskSummaries` を develop/task/ から読む' --difficulty sonnet --loopable Y \
     --deps T-521 --body-file - <<'EOF'
   ## 目的・背景
   …
   ## 決まっていること（蒸し返さない）
   なし
   ## 解くべき論点
   なし
   ## やること
   ### 1. 要約を develop/task/ から読む
   `src/task-summary.ts` の `readTaskSummaries` を …（完了条件の1行目）
   ### 2. テストを足す
   …（完了条件の2行目）
   ### 名指すファイル
   - `src/task-summary.ts`
   - `test/`（テストを置く）
   ## 完了条件
   …
   ## 注意
   なし
   ## 参考情報
   なし
   EOF
   ```

   近道の印を付けるタスク（手順4）は `--direct` を足す（例 `tw new --summary '…' --difficulty haiku --loopable Y --direct --body-file - <<'EOF'`）。
   Beads 方式の `tw adopt` も同じく `--direct` を足す。

   | 出力 | すること |
   | --- | --- |
   | `CREATED` | 次の1件へ |
   | 終了コード2で「近道は…」 | 近道の印（`--direct`）が基準を外れた。`--direct` を外して打ち直す（基準に合わせて計画を縮めない） |
   | `LOCKED` | 採番の錠が取れない。行に `rmdir` が添えてあれば古い錠なので、その旨を報告して止まる（壊さない） |
   | 終了コード2 | 本文が枠と違う（見出しの欠け・順・枠の外の見出し）・空にできない欄が空・`## やること` が空（`--hold` を除く）・`### 名指すファイル` が無い・形が違う・パスが主ブランチ（`### 作業先` があればそのリポジトリの主ブランチ）の木に無い・`### 作業先` が絶対パス1行でない・git のリポジトリの根でない。Beads 方式では Beads に無い `--deps` も（解決済みなら外す）。直して打ち直す |
   | 続く行の `TRACKER\tFAILED` | 登録は済んでいる。報告に添え、最後に `tw sync` を1回打ち直す |

   Beads 方式の振り分け前の課題は `tw new` ではなく
   `tw adopt <ID> --difficulty … --loopable … --body-file -`（`ADOPTED` の3列目が振られた ID）。
   本文は `tw new` と同じく手順4のとおり書く（`## やること` も要る。終了コード2の理由も同じ）。

6. **置き場から取り除く**: `## ユーザーから` はタスクにした行を消して節を見出しだけに戻し、
   承認を得たドラフトはそのファイルを `git rm` する（未承認のファイルは残す）。

7. **コミットして送る**: `git add` する前に整形コマンドを打つ（`タスク運用`節が `なし` なら不要。
   手順6で書き換えた `develop/direction.md` はそのままだと整形コマンドの検査に引っかかりうる）。
   打ったら、登録したタスクファイル・`develop/direction.md`（と直した既存タスク）を**個別に** `git add`
   し、手順6の `git rm` と合わせて1コミット（Beads 方式ではタスクファイルが無いので、それ以外だけ）（件名に
   タスクIDを付けない。例「指示をタスクにする（T-531〜T-533）」）→ `tw ship`。`SHIPPED` 以外の
   扱いは `next-task` スキルの `ship-stopped.md` の表と同じ（止まって預ける）。push はしない。

## 完了報告のフォーマット

報告は人が読むためのもの。

1. **結論を1文目に置く**: 「N件を T-xxx〜T-yyy として登録し、main へ送りました。」。
   `SHIPPED` 以外で止まったときは、止まったことと先頭語を結論にする
2. **対応表**（全項目。**取りこぼしの検知点はここだけなので必ず出す**）: 列は
   項目・発言 | タスクID | `summary` | `difficulty` | `loopable` | 依存 | `hold`。
   ドラフト由来は承認の発言を表の見出しの1行に添える。タスクにしなかった項目と、残した
   未承認のドラフトも行に入れ、タスクIDの列に理由を書く
3. **人に知らせること**があるときだけ: 裏取りで項目の中身と違うと分かったこと、その場で
   決めてもらったこと、`loopable: N` と `hold` の理由（`/loop` では進まないため）

書かないもの: `SHIPPED` の範囲・コミットのハッシュ、`tw status` の件数、
`develop/direction.md` のどの節を空にしたか・どのドラフトを消したか（どれも決まった手順の
とおりで、見たければ `git log` と `tw status` で見られる）。
