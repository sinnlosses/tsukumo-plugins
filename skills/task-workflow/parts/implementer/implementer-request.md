# 実装の依頼文の型

`tw brief implementer` が読み、場合に当たる節を選んで `{{名前}}` の値を埋め、委譲先へ渡す依頼文として出す型。
節の名前と、どの場合にどの節を選ぶか・値の中身は `tw brief --help` が持つ。最初の `## ` より前の行は出さない。

## 常に

タスク {{task_id}} を進める。まず `tw show {{task_id}}` で読み、次に {{here}}/implementer-brief.md を読んで従う。
`tw verify`・`tw pause` は引数なしで打つのが基本。ID を付けるなら着手中の {{task_id}} だけ（違う ID は `NOT_OWNER` で拒まれる）。

## 計画どおり

`## やること` は書いてある。`tw show {{task_id}}` で読み、段{{step}}（`### {{step}}.`）だけをそのとおり実装して返す。
次の段はメインが `SendMessage` で渡す。判断が想定より要ると分かったら押し切らず、そこで止めて報告する。
`## 目的・背景`・`## 完了条件` は変えない（変えると `FRAME_CHANGED` で拒まれる。`--change-frame` は付けず、変えたい理由を報告する）。

## 書き直し

**先に `tw edit {{task_id}} --section 'やること' --body-file -` で `## やること` を書き、作業せずに返す**
（節の中身だけを渡し、`## やること` の見出しの行は付けない。`### 1. …` の形で `### 1.` から穴なく
実行の順に番号を振った段で書き（形が違えば `tw edit` が終了コード2で拒む）、完了条件の各行を
どの段のどのファイルのどこをどう直して満たすかまで書き、各段に `- 満たす完了条件: <行番号>` の欄を置く。
段は1回の返却で済ませる大きさにする。
並べて走らせてよい段は段の欄も書く（正典「タスクの本文」の「段の形」）。
段の中身は、{{task_model}}/WORKFLOW.md の「タスクの本文」の「段の中身の書き方」に従って書く（語を消す・描画を変える・文書の写しを畳むタスクの段もそこにある。
本文が前提にする既存の振る舞いの裏取りと、食い違ったときに止めて報告することもそこにある）。
出力・文言・定数を変える作業なら、段を書く前に、変える文字列をリポジトリ全体で grep し、その文字列を写した検査・文書を
`### 名指すファイル` に足してから書く（名指しの外の写しは、検証が落ちてから見つかる）。
`## 解くべき論点` に論点があれば、答えは `## やること` の最初の段 `### 1.` より前に
`**論点への答え**: …` の太字の行で書く（`### 論点への答え` の小見出しは `tw edit` が拒む）。
作業ツリーが変わったあとの初回の記入は `WORK_BEFORE_PLAN` で拒まれるので、読むだけの調べを
先に済ませてから書く）。返却の先頭は計画の要点を1文で、2行目に、計画を書いたあとで打った `tw plan-phases <ID> --through 計画` の出力の
`PHASES\t…` の行を1字も変えずに貼る（tsukumo で動いているとき、メインはこの行を写して `work_plan` を呼ぶ。返却のあとはゲートが Bash を拒み、メインは `tw` を打てない）。この回は `phase_result` を呼ばない。そのあとはメインが
`SendMessage` で渡す段を1つずつ、`## やること` のとおり実装する。判断が想定より要ると
分かったら押し切らず、そこで止めて報告する。`## 目的・背景`・`## 完了条件` は変えない
（変えると `FRAME_CHANGED` で拒まれる。`--change-frame` は付けず、変えたい理由を報告する）。

## 古い計画

登録時の `## やること` は古い（変わったファイル: {{stale_files}}）。いまの主ブランチで調べ直して丸ごと書き直す。

## 別のリポジトリ

- 作業先のリポジトリ {{work_repo}} では、別の作業ツリー（`git -C {{work_repo}} worktree add -b {{branch}} {{worktree}} {{base}}`。
  すでにあればそのまま使う）で直してコミットし、**コミットのあと**にその作業ツリーを cwd にして `tw verify` を打つ（控えは cwd の作業ツリーごとで、鍵に `HEAD` の
  SHA を含むので、コミットの前に打つと受け入れで `NOT_VERIFIED head` になる）。`tw step`・`tw pause` は
  着手した側（Beads のある作業ツリー {{claimed}}）を cwd にして打ち、作業先の作業ツリーでは
  打たない（`NOT_OWNER` か `MISSING …/.beads` で拒まれる）。作業先の作業ツリーで打つ `tw` は
  `tw verify` だけ。最後の段の返却は、
  作業先の作業ツリーの `tw verify-check` が `VERIFIED_SAME` でなければ hook に拒まれる。**`{{base}}` へ入れず、
  作業ツリーと枝を消さずに残して**、作業ツリーのパスと `tw verify` の判定行（`VERIFIED`・
  `VERIFY_NOT_PASSED` など）を報告に書く。作業先に `.tw/config.toml` があれば台帳（`.beads`）が無くても
  `tw verify` は打てる。設定が無く `tw verify` が `MISSING` を返すときは、検証コマンドを自分で打って通し、打ったコマンドと終了コードを報告に書く。作業先が tsukumo-plugins で `skills/task-model/scripts/` を直すタスク（tw 自身を直すタスク）のときは、`tw` を打たず（グローバルの `tw` は本体の旧い版を指すため）、作業ツリーの `skills/task-model/scripts/tw/task.py <サブコマンド>` を直に実行して確かめる。
- 作業先の本体の作業ツリー（`git worktree list` の先頭。全プロジェクトが参照する実体のことがある）のファイルは読むだけで、書き換えない。そこを cwd に
  して編集しない。枝も切り替えない。編集は必ず自分の作業ツリー {{worktree}} の下のパスに対して行う。
- 作業先の作業ツリーのパスのファイルは、本体のパスで読んだだけでは Edit が拒まれる（別のパスなので）。Edit の前に、作業ツリーのパスでその回に Read する。

## 並列の段

同じ作業ツリーでほかの段の担当が同時に動いている。書き換えるのは段{{step}}の `- 触るファイル:` の欄のファイル（{{touched}}）だけにする。
最後の段でなければ `tw verify` も検証コマンドの全段も打たない（対象を絞った単体テストは打ってよい）。
止めて返すときは、基本の引数なしの `tw pause` の代わりに `tw pause {{task_id}} {{step}}`（ID と段の番号の2つ）を打つ。

## 目視

- 本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開き、作った画面と見比べる。
  食い違ったら見本に合わせ、見比べた結果を報告に1行書く。
- 画面・見た目を確かめる完了条件があるタスクでは、撮った画像のパス（幅ごとに1行。いちばん狭い
  幅がどれかも書く）を報告に書く。画像は作業ツリーの外の、受け入れまで消えない場所に置く。
- 描画を変えるタスクでは、段1の前に、変える場面を変更前の状態で撮り、そのパスを最初の返却に書く。後で撮る変更後の画は、同じ場面・同じ幅で撮る。画像は作業ツリーの外の、受け入れまで消えない場所に置く。
- 描画を変えるタスクでは、部品を差し替えて組み立てた直後に画を撮り、E2E の期待値の撮り直しと
  `tw verify` の前に、`tw pause` を打ってから画像のパスを書いた『目視待ち』の報告を返して止まる。メインが `SendMessage` で
  承認を返してから、期待値の撮り直しと `tw verify` に進む。差し戻されたら直して撮り直し、もう一度
  『目視待ち』で返す。
- 目視待ちで返す段が最後の段でないなら、`tw pause` は引数なしでなく 段の番号つき（`tw pause <ID> <段の番号>`）で打つ。
  引数なしの `tw pause` は段の控えにならず、承認後の最後の段のあとに `tw accept` が `NOT_LAST_STEP` で止まる。
  最後の段が目視待ちなら、引数なしでよい。
