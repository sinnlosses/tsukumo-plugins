# 実装の依頼の決まり

`task-workflow`（タスクを段に分けて進めるオーケストレーター）から委譲された実装担当が、最初に読んで従う決まり。タスクごとに変わること（タスクID・渡された段・別のリポジトリ・並列の段・描画）は依頼文が足す。

## タスクの読み書き

- まず `tw show <ID>` で読む。書き足すときは節の中身だけを `tw edit <ID> --section '<節名>' --body-file -` に渡す。
- 前提が崩れていて作業が要らないと分かったら、作業せずに止まって、`dropped` にすべき理由を報告する（`## やること` は書かなくてよい）。
- `## 目的・背景` がファイルの存在・パス・行番号を主張していたら、作業の前に実物で確かめる（別のリポジトリのファイルなら、そのリポジトリの実物を見る）。違っていたら直さず「前提が誤り」と報告する。
- 本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開いて読み、`## やること` と作るものを見本と食い違わないようにする。
- 本文に `## 結果` の節を書かない（`tw done` が書く）。
- 完了条件が後段のタスクの本文を直す・分けるよう求めていても、後段には手を付けず申し送りだけ書く（本文の編集と `tw new` での分割はメインが受け入れで行う）。

## コミットと `tw` コマンド

- ドラフト（課題）は `tw new --draft` で積むが、委譲先は `tw new` を打てないので、ドラフトにしたい改善は報告に `- ドラフト: <何を変えるか（1行）>`（子項目に `根拠`・`出し先`）で書き、メインが積む。
- コミットしない（`git add -A` もしない）。ただし、作業先が別のリポジトリのときは依頼文で指示した別の作業ツリーでコミットしてから `tw verify` を打つ（`skills/task-workflow/other-repo.md` の実装役の手順に従う）。
- 打ってよい `tw` は `tw show`・`tw edit`・`tw verify`・`tw step`・`tw pause` だけ。どの作業ツリーで打つかは依頼文に従う（作業先が別のリポジトリなら、`tw verify` は作業先の作業ツリー、`tw step`・`tw pause` は着手した側）。
- 検証コマンドは `tw verify` で打って通す。打つ前に主ブランチを取り込み、取り込んだら先頭に `FOLDED` が出る。通ると作業ツリーの中身の鍵が控えられ、受け入れで中身が同じなら検証を省ける。落ちたら `VERIFY_NOT_PASSED` と、落ちた回を残した時刻つきのログのパスが出る。
- 検証コマンド（check の全段）は `tw verify` 以外で打たない（対象を絞った単体テスト・E2E のファイル単位の実行は打ってよい）。
- `CONFLICT` が出たら解かずに、衝突したファイルを添えて報告して止まる。
- `tw verify` を通したあとにファイルを変えたら打ち直す。

## 段の進め方と返却

- `## やること` の段（`### <n>.`）を1つずつ、渡された段だけ進めて返す。次の段は同じ会話に `SendMessage` で届く。
- 最後でない段は返す直前に `tw step <ID> <段の番号>` を打つ。最後の段は `tw verify` を通してから返す。
- 作業があるなら、返す前に `## やること` を `tw edit` で書き、`tw verify` を通す。作業が無い返却（前提が誤り・dropped・計画だけ）は拒まれない。
- 判断が要って止めて返すとき・`CONFLICT` で止まるとき・計画を作業の後に書いたとき・目視待ちで返すとき・受け入れの差し戻しの直しを、依頼で `tw verify` を打たないよう言われて返すときは、返す直前に `tw pause` を打つ（`tw verify` を打たないと hook の返却ゲート `NOT_VERIFIED content` に拒まれるため）。`tw step`・`tw pause` は、打ったあとに中身を変えたら打ち直す。
- 返却の本文の先頭に、した結果を1文で書く（計画だけの回なら計画の要点、段を済ませたらその要約）。止めたとき・「前提が誤り」・`dropped` にすべきときは、先頭を `止めた:`・`前提が誤り:`・`dropped にすべき:` で始めて理由を続ける。進み具合の帯を進める口は返却の書式ではなく、次の `phase_result`。
- 段を済ませたら（止めたときも）、`SubagentHandback` の直前に MCP ツール `phase_result` を1回呼ぶ。`phase`＝渡された段の番号、`count`＝`## やること` の段の数、
  `outcome`＝`finished`（止めたら `stopped` と1〜2文の `reason`、要らない段と分かったら `skipped`）。計画だけの回は呼ばない。
  結果の正典は tsukumo の契約 `docs/architecture/workflow-contract.md`「スキルの契約」
  （https://github.com/sinnlosses/tsukumo/blob/main/docs/architecture/workflow-contract.md）。
  `phase_result` が一覧に無い環境では呼ばない（メインは本文の先頭で止めたかを読む）。
- 最後の段（`tw verify` を打つ段。並列の段では最後の段の担当だけ）の返却の本文には `## 構造の変更` の節を書く。中身は tsukumo の `graph` の記法で、1行1辺、行頭 `+ ` / `- ` / `~ ` で足した・消した・変えた（例: `+ A -> B: 語`）。構造が変わらないときは `なし: <理由>` の1行を書く。節が無い・空・各行がこの形でない（`なし: <理由>` は他の行と混ぜない）と `tw handback-guard` が拒む。
- 段の区切り（`tw step` を打つ前後）と、`unresponsive.md` 項3の無音の閾値を超えうる長いコマンドの前に、メインへ `SendMessage({to:"main"})` で `状況 | 何をした・何が分かった` の1行を送る（段の番号は入れない）。長いコマンドの実行中は受け取れず、メインから尋ねても返らないので、前に送っておく。`SendMessage` が使えない環境では送らなくてよい。
- 最後の段（`tw verify` を打つ段）の担当だけ、`tw verify` の前に、このファイルの2つ上のディレクトリ（`task-workflow` の置き場）の `scripts/self_review.py` を打つ（引数なし。並列の段で最後でない段の担当は打たない）。台本は作業ツリーの差分を読むので、コミットする前（差分があるうち）に打つ。コミットしてから `tw verify` を打つ作業先（別のリポジトリ）では、台本 → 直す → コミット → `tw verify` の順にする。出た `SELF` の行ごとに、行のコマンドを打って問いに答え、当たったものを直してから `tw verify` を打つ。`SKIPPED` の行はその性質を判定できなかったという知らせなので、報告にそのまま書く。
- 台本の答えは報告に、`SELF` の行ごとに `自己点検: <性質>: 当たり、<直したこと>` か `自己点検: <性質>: 外れ` の1行で書く。`NOTHING` だけなら、次の項の観点の点検の答えを書く。
- 台本の `SELF` の行に答えて直したあとも、最後の段の担当は、`tw verify` の前（コミットする作業先ではコミットの前）に作業ツリーの差分（`git diff HEAD` と、`git ls-files --others --exclude-standard` の未追跡のファイル）を読み、`task-workflow` の置き場の `review-criteria.md` の4種類で点検して、当たるものを直す。順は台本の行 → 4種類の観点（並列の段で最後でない段の担当は行わない）。答えは台本の答えと同じ書式で `自己点検: 観点: 当たり、<直したこと>` か `自己点検: 観点: 外れ` と書く。台本が `NOTHING` でも観点の点検は行い、`自己点検: なし` は台本が `NOTHING` で観点も外れのときだけ書く。
- 報告では `## 完了条件` の各行について、満たしたか・何で確かめたかを1行ずつ書く。見た目や設定を変えたら、実際に効いたことを実物で確かめる。
- 報告には、読んだ規約の節を `- 規約: <読んだ節の名前をカンマ区切り>` の1行で書く（読まなかったら `- 規約: なし`。節の中身は書かない）。friction log の近くに置く。

## friction log

気になった点は、終わってから思い出す自由記述ではなく、作業中に気づいた時点で `retrospect` スキル（Skill ツールで名前を指して呼ぶ）の副ファイル `detail.md` の節「色と1行の書式」の1行（`- <色>: <何が起きたか>（<根拠の場所>）`）で書き留め、報告に載せる。検証コマンドやテストが1回落ちて、打ち直したら通ったときも書く。何も起きなければ「friction log: なし」と書く。

## 作業の作法

- `git stash` を使わない（stash の山は作業ツリーの間で共有され、別のセッションの退避を取り違える）。変更の前後を見比べるなら一時コミットか `git show HEAD:<path>` で見る。
- 変更前後の比較用の控えなど作業ツリーに置かない一時ファイルは、作業ツリーの外の絶対パス（`/tmp/<名前>/…`）へ Write ツールで書く。Bash のリダイレクトの書き先を `$変数` で決める形や、`node -e`・Python のコードで書く形は、hook が作業ツリーへの書き込みとみなして止めるので使わない。
- ファイルを Edit する前に、その回で一度 Read する（Read せずに Edit すると失敗して打ち直しになる）。`SendMessage` で再開した回も、前の回で読んだファイルでも最初の Edit の前に改めて Read する。
- `sed -i`・`perl -i`・リダイレクト・`tee` などシェルでのファイルの書き換えは、hook が作業ツリーへの書き込みとみなして拒む。同じコマンド列に含めた `git mv` なども走らないので、一括の書き換えも `Edit` で書く（拒む判定の中身は `tw` の `tw-reference.md`「hook の関門」節）。Edit で一括に直したあとは、`git diff --stat` で `## やること` の触るファイルの外が変わっていないかを見る。報告に書く変更の出どころは差分で確かめる。
- グローバルへのリンク（例: パッケージマネージャのグローバルリンク）・ホームのファイル・グローバル設定を触らない。必要なら報告に書く。
- 外部に捨てる資源（リポジトリ・Project など）を作る前に、`gh auth status` のスコープで消せることを確かめる。消せなければ作らずに、人にスコープの追加を頼む。
- `/` やホーム全体を `find` で探さない（置き場の見当が付く所だけ探す。ルートから探すと上限で背景に回り、報告のあとも走り続ける）。
- 待つコマンドには必ず上限を付ける（回数か、スクリプトの中の待ちの timeout か、シェルを呼ぶツールの timeout 引数。`timeout` コマンドは環境に無いことがある）。背景のコマンドの完了を待ったまま手番を終えない。撮影などが終わらなければ止めて、そのことを報告に書く。
- 作業先が tsukumo-plugins で task-model を直すときは、段の途中の確かめを名前を渡したテストだけを単体で流す。入口は関数名の先頭で決まる（`selftest_t_*` なら `python3 skills/task-model/scripts/tests/selftest_task.py`、`selftest_b_*` なら `python3 skills/task-model/scripts/tests/selftest_beads.py`）。名前を渡さない全件は9分前後かかることがあるので、全件は最後の `tw verify` でだけ流す（検証コマンドを `tw verify` 以外で打たない、という上の線の中で打つ）。
- 背景で起こしたコマンド（テスト・サーバ・watch）は、報告の前に止める（残ると同じ作業ツリーで受け入れの検証コマンドが返らなくなる）。
- 新しく書くコメントは、プロジェクトの規約（CLAUDE.md など）があればそれに従い、呼ぶ側・前例のファイル名・正典の要約と参照を並べない。前例のファイルのコメントの量を手本にしない。「〜のは、…ため」のような方針・理由の説明も足さない。
- コメントを足す前に、次を自分で当てる。(a) そのコメントを消すと壊れる場面を言えるか（言えなければ足さない）。(b) コードの言い直し・規約をなぞる一文・経緯・採らなかった案との比較・ほかの箇所との照らし合わせではないか（当たれば足さない）。(c) 1行を決まった幅で割らず、意味の切れ目で行を改めているか。規則の中身は写さず、プロジェクトの規約ファイル（例: `.claude/rules/comments.md`。あれば）を指す。
- 文書・コメント・説明文に、全体についての事実（「既定は〜」「〜のときだけ」「〜の件は全部〜」）を書くときは、当てはまる箇所を grep や表の走査で全件数えてから書く。報告に数えた手と件数を1行書く。
- 関数を別ファイルへ移す・形を変える作業では、呼ぶたびに評価される引数（期限・時刻・カウンタ・乱数など）を、呼び出し側で1回にまとめて渡す形に変えていないかを、`git show main:<ファイル>` の元の呼び出しと突き合わせる。
- 掛かり方・条件を変えた作業では、消した語で grep するだけでなく、書き換えた主張を別の言い方で書いた箇所（「掛からない」「だけ」など）も grep で洗い、残った文を直すか報告に書く。
- 書き始める前に、プロジェクトの規約のファイル（CLAUDE.md から引かれるコーディング規約など）の索引で、これから触る層・種類（型・テスト・UI・コメントなど）の節を特定して読む。受け入れ役は同じ規約で差分を点検するので、読まずに書くと差し戻しになる。読んだ節は返却に `- 規約: <節の名前>`（読まなかったら `なし`）の1行で書く。
- 自分に `Agent` ツールがあるときだけ: サブエージェントの中では別のエージェント（fork を含む）を立てず、レーンを順に自分で読む。
