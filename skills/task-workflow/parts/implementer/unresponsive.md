# 委譲先の無応答に対応する

並列の段の担当を起こしたときは、担当それぞれに独立して当てはめる。ほかの担当が返していても、
残りの担当の無応答は別に扱う。
   1. **完了の通知が「背景の作業を待っている」で届いたら、待たずにその場で作業ツリーと成果物を見る**。
   2. **完了の通知だけが届いて返却（済んだ段か止めた理由を書いた報告）が無ければ、
      段の進み具合を見て、同じ委譲先へ催促する**。着手した作業ツリーの段 n の控え
      （名前と置き場は `skills/task-model/tw-reference.md` の `step` の行）の有無と、
      作業ツリー（作業先が別のリポジトリなら作業先の作業ツリー）の `git status` で見分ける:
      - 控えも差分も無ければ、段は未着手。
      - 差分だけがあれば、段は途中。
      - 控えがあれば、段は済んでいて返却だけが欠けている（最後の段は控えを打たないので、
        `tw verify-check` が `VERIFIED_SAME` かで見る）。

      催促は新しい委譲先を立てず、同じ委譲先へ `SendMessage` で「どこまで進んだか確かめて
      段 n を済ませて返す」と送る。催促しても返らないときは、次項以降の止め方・引き継ぎへ進む。
   3. **委譲先の合図も作業ツリーの動きも5分無ければ（無音）、同じ委譲先へ `SendMessage` で状況を1行で
      尋ね、尋ねてから5分、返事も作業ツリーの動きも無ければ、作業ツリーに手を出さずに `TaskStop` で止める**
      （5分はどちらも暫定の値で、この項だけに書く。手順5(f)の見張りに渡す `T` は最初の5分の `300` 秒）。尋ねる段は必須で、返事は無くても動きがあれば待つ。
      長いコマンドの実行中は委譲先がメッセージを受け取れず返らないので、止める判断は動きの有無に寄せる。
   4. 止めたら最後の状態と `git diff` を読み、**完了条件を満たしていれば手順6で受け入れる**。
   5. 途中なら、済んだことと残りを明示して**別のサブエージェントに引き継ぐ**。`tw release` で
      捨てるのは差分が使えないときだけ。
   6. **見張りに `ESCALATE_SUGGEST\tT-xxx\t<引き金>\t<詳細>\t<次のモデル>` が出たら、止めずに、上のモデルへ引き上げるか待つかを決める**。
      引き金は `edit-churn`（同じファイルを5回書き換えた）・`verify-failed-streak`（`verify` が2回続けて落ちた）・
      `slow-delegation`（経過が同じ difficulty の委譲の中央値の3倍を超えた。基準は `tw metrics --stages` と同じ直近28日の元から毎回引く）。
      引き上げるなら、委譲先が段を返した切れ目で `delegate.md` の (c) の手（`TaskStop`、次のモデルで起こし直し、済んだ段の次から
      `tw brief implementer T-xxx --step <n>`）を使う。次のモデルが `-` のときや、段がほぼ終わっているときは待つ。
      提案は強制ではなく、出ても委譲先は止まらない。同じ引き金は同じ委譲で1回しか出ない。
