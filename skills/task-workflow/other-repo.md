# 作業先が別のリポジトリのとき

タスクが直す対象が自分の作業ツリーの外のリポジトリのときの、実装の依頼文の項目（手順5c）と、受け入れ（手順6）のうち別のリポジトリに特有のこと。

## 実装の依頼文の項目（手順5c）

   作業先が別のリポジトリ（`## やること` の `### 作業先`）のタスクでは、`tw brief implementer` が
   `${CLAUDE_SKILL_DIR}/parts/implementer/implementer-request.md` の `別のリポジトリ` の節を依頼文に足す。中身は、作業先の別の作業ツリーで直してコミットしてから
   その作業ツリーで `tw verify` を打つこと、`tw step`・`tw pause` は着手した側で打つこと、作業先の本体を書き換えないこと、
   作業ツリーのパスでその回に Read してから Edit すること。枝（タスクIDの小文字。`T-012` なら `t-012`）・作業ツリーの道・
   作業先の主ブランチは tw が埋めるので、メインは書かない（道の決め方は `tw brief --help`）。枝の名前が違うと関門が作業先を
   見ない（正典の `tw-reference.md`「hook の関門」節）。関門が作業先の検証を求めずに通したとき（同じ節）は、受け入れで検証コマンドを打つ。

## 受け入れ（手順6）

   `tw accept T-xxx` は単一のリポジトリのときと同じく着手した作業ツリーで打つ。`tw` が `### 作業先` から作業先の作業ツリー
   （枝はタスクIDの小文字）を引き、レビューの判定（主ブランチから枝までの範囲つき）・木の控え・`tw verify-check` をその作業ツリーで打ち、
   `accept`・`review`（1回目）の lap も書く。整形は打たない（`FORMATTED` の行は出ない）。出力は `parts/acceptor/accept.md` の表のとおりに読み、
   受け入れ役の依頼文の作業ツリー・差分のコマンドは `tw brief acceptor` が埋める。ここに残すのは別のリポジトリに特有の行だけ。

   **作業先の本体の汚れ**: `tw claim` が着手の時点の本体の汚れを控え、`tw accept` が（`--after-review` でも）本体の汚れを1ファイル1行で出す。

   | 行 | すること |
   | --- | --- |
   | `MAIN_DIRTY_FROM_DELEGATE\t<パス>`（終了コード4。控えに無く、中身が委譲先の枝の同じパスの blob と同じ） | 委譲先が本体に書き残したもの。報告と食い違うものとして `${CLAUDE_SKILL_DIR}/parts/implementer/return-abnormal.md` の表に従い、委譲先へ `SendMessage` で伝えて差し戻す。`git restore` はこの行のファイルだけに打つ |
   | `MAIN_DIRTY_UNKNOWN\t<パス>`（終了コード4。控えに無く、blob が枝と違う・枝に無い・消えたファイル） | 委譲先か別の作業か分からない。消さずに、ファイルと `git diff` の要点を添えて人に預けて終了する |
   | `MAIN_DIRTY_BEFORE\t<パス>`（止まらない。着手の前から在る） | 別の作業。消さない。本体が汚れているあいだは下の `tw land` が `NOT_LANDED` で止まるので、汚れが消えるのを待つか、人に預けて終了する |

   控えの無い着手（控えを取らない旧い `tw` で着手した）では `MAIN_DIRTY_BEFORE` を判定せず、前からの汚れも `MAIN_DIRTY_UNKNOWN` になる。
   作業先の作業ツリーが無ければ `MISSING\t作業先 <本体> の作業ツリー（枝 <枝>）`（終了コード6）なので、委譲先の報告のパスを確かめて人に預ける。

   **検証**: `NOT_VERIFIED` なら作業先の作業ツリーで `tw verify` を打ち直してから `tw accept T-xxx --after-review` を打ち直す。
   受け入れで直すならその作業ツリーで直してコミットしてから打つ。作業先に設定が無い（`tw verify-check` の行が `NOTHING`）と控えが無いので、
   委譲先の報告を信用せず検証コマンドを打つ（`tw land` はタスク運用を始めていない作業先でも打てる）。

   **合流**: 検証が済んだら、着手した作業ツリーで `tw lap T-xxx land start` を打ち、作業先の作業ツリーで
   `cd <パス> && tw land <枝>` を打ち、出力を読んだ直後に着手した作業ツリーで `tw lap T-xxx land end` を打つ（`tw land` は台帳が別なので lap を書かない）。
   `tw land` は作業先の本体で `<枝>` を ff-only で主ブランチへ合流し、入ったことを確かめてから作業ツリーと枝を消す。
   `git merge`・`git worktree remove`・`git branch -d` を素で打たない。

   | `tw land` の先頭語 | すること |
   | --- | --- |
   | `LANDED` に続けて `REMOVED`・`DELETED` | 次へ |
   | `NOT_LANDED`（何も変えていない） | 理由が「ff-only で合流できない」なら、作業先の主ブランチが先へ進んでいる。その作業ツリーで主ブランチを取り込んで `tw verify` を打ち直してから、もう一度打つ。ほかの理由は行を添えて人に預けて終了する |
   | `NOT_REMOVED`（合流は済んでいる） | 残った作業ツリーか枝を報告に書いて次へ進む（消すのは人に預ける） |
   | `GIT_READ_ONLY` | `task-model` の tw-reference.md の終了コード表のとおり |

   **許可規則**: auto mode の分類器は、作業先の本体の主ブランチへ合流するコマンドを [Modify Shared Resources]
   として拒むことがある。`tw land` も許可規則が無ければ拒まれうるので、利用者が `settings.json` の
   `permissions.allow` に `Bash(tw land:*)` を置く。エージェントは置かない。拒まれたら回り道をせず、
   作業ツリーのパスと枝を添えて人に預けて終了する。
