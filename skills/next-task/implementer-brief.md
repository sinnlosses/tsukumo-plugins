# 実装の依頼の決まり

`/next-task` から委譲された実装担当が、最初に読んで従う決まり。タスクごとに変わること（タスクID・渡された段・別のリポジトリ・並列の段・描画）は依頼文が足す。

## タスクの読み書き

- まず `tw show <ID>` で読む。書き足すときは節の中身だけを `tw edit <ID> --section '<節名>' --body-file -` に渡す。
- 前提が崩れていて作業が要らないと分かったら、作業せずに止まって、`dropped` にすべき理由を報告する（`## やること` は書かなくてよい）。
- `## 目的・背景` がファイルの存在・パス・行番号を主張していたら、作業の前に実物で確かめる（別のリポジトリのファイルなら、そのリポジトリの実物を見る）。違っていたら直さず「前提が誤り」と報告する。
- 本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開いて読み、`## やること` と作るものを見本と食い違わないようにする。
- 本文に `## 結果` の節を書かない（`tw done` が書く）。
- 完了条件が後段のタスクの本文を直す・分けるよう求めていても、後段には手を付けず申し送りだけ書く（本文の編集と `tw new` での分割はメインが受け入れで行う）。

## コミットと `tw` コマンド

- `direction`・`draft` の行の置き場（例 `.tw/`）を触らない。ただし `draft` の行のディレクトリ（例 `.tw/draft/`）にドラフトを積むときは、ドラフトの形（太字の見出し1行・`根拠`・`出し先` の子項目）で書く。
- コミットしない（`git add -A` もしない）。
- 打ってよい `tw` は `tw show`・`tw edit`・`tw verify`・`tw step`・`tw pause` だけ。
- 検証コマンドは `tw verify` で打って通す。打つ前に主ブランチを取り込み、取り込んだら先頭に `FOLDED` が出る。通ると作業ツリーの中身の鍵が控えられ、受け入れで中身が同じなら検証を省ける。落ちたら `VERIFY_NOT_PASSED` と、落ちた回を残した時刻つきのログのパスが出る。
- 検証コマンド（check の全段）は `tw verify` 以外で打たない（対象を絞った単体テスト・E2E のファイル単位の実行は打ってよい）。
- `CONFLICT` が出たら解かずに、衝突したファイルを添えて報告して止まる。
- `tw verify` を通したあとにファイルを変えたら打ち直す。

## 段の進め方と返却

- `## やること` の段（`### <n>.`）を1つずつ、渡された段だけ進めて返す。次の段は同じ会話に `SendMessage` で届く。
- 最後でない段は返す直前に `tw step <ID> <段の番号>` を打つ。最後の段は `tw verify` を通してから返す。
- 作業があるなら、返す前に `## やること` を `tw edit` で書き、`tw verify` を通す。作業が無い返却（前提が誤り・dropped・計画だけ）は拒まれない。
- 判断が要って止めて返すとき・`CONFLICT` で止まるとき・計画を作業の後に書いたとき・目視待ちで返すときは、返す直前に `tw pause` を打つ。`tw step`・`tw pause` は、打ったあとに中身を変えたら打ち直す。
- 返却の1行目の頭の語は、計画だけの回が `計画 0/<段の数>`、段を済ませたら `段 <n>/<段の数>`、止めたら `止めた <n>/<段の数>`（`n` はいま渡されている段）で、あとに ` | <要約か理由>` を続ける。2行目からは報告の本文。
  tsukumo で動かすと、この1行目が進み具合の帯を進める。書式の正典は tsukumo の契約 `docs/architecture/workflow-contract.md`「委譲の返却」
  （https://github.com/sinnlosses/tsukumo/blob/main/docs/architecture/workflow-contract.md）で、読めなければ上の頭の語で返せばよい。
  契約が足す点: 差し戻しを受けてやり直した段は同じ `段 <n>/<段の数>` をもう一度返す。並列の段も段の番号だけで表し、どの委譲先が返したかは書かない。
- 報告では `## 完了条件` の各行について、満たしたか・何で確かめたかを1行ずつ書く。見た目や設定を変えたら、実際に効いたことを実物で確かめる。

## friction log

気になった点は、終わってから思い出す自由記述ではなく、作業中に気づいた時点で `../retrospect/SKILL.md` の節「色と1行の書式」の1行（`- <色>: <何が起きたか>（<根拠の場所>）`）で書き留め、報告に載せる。検証コマンドやテストが1回落ちて、打ち直したら通ったときも書く。何も起きなければ「friction log: なし」と書く。

## 作業の作法

- `git stash` を使わない（stash の山は作業ツリーの間で共有され、別のセッションの退避を取り違える）。変更の前後を見比べるなら一時コミットか `git show HEAD:<path>` で見る。
- `sed -i` などで複数のファイルを一括で書き換えたら、`git diff --stat` で `## やること` の触るファイルの外が変わっていないかを見る。報告に書く変更の出どころは差分で確かめる。
- グローバルへのリンク（例: パッケージマネージャのグローバルリンク）・ホームのファイル・グローバル設定を触らない。必要なら報告に書く。
- 外部に捨てる資源（リポジトリ・Project など）を作る前に、`gh auth status` のスコープで消せることを確かめる。消せなければ作らずに、人にスコープの追加を頼む。
- `/` やホーム全体を `find` で探さない（置き場の見当が付く所だけ探す。ルートから探すと上限で背景に回り、報告のあとも走り続ける）。
- 待つコマンドには必ず上限を付ける（回数か、スクリプトの中の待ちの timeout か、シェルを呼ぶツールの timeout 引数。`timeout` コマンドは環境に無いことがある）。背景のコマンドの完了を待ったまま手番を終えない。撮影などが終わらなければ止めて、そのことを報告に書く。
- 作業先が tsukumo-plugins で task-workflow を直すときは、段の途中の確かめを `python3 skills/task-workflow/scripts/selftest_task.py <テストの関数名> …` で名前を渡したテストだけを単体で流す。名前を渡さない全件は9分前後かかることがあるので、全件は最後の `tw verify` でだけ流す（検証コマンドを `tw verify` 以外で打たない、という上の線の中で打つ）。
- 背景で起こしたコマンド（テスト・サーバ・watch）は、報告の前に止める（残ると同じ作業ツリーで受け入れの検証コマンドが返らなくなる）。
- 新しく書くコメントは、プロジェクトの規約（CLAUDE.md など）があればそれに従い、呼ぶ側・前例のファイル名・正典の要約と参照を並べない。前例のファイルのコメントの量を手本にしない。「〜のは、…ため」のような方針・理由の説明も足さない。
- 自分に `Agent` ツールがあるときだけ: サブエージェントの中では別のエージェント（fork を含む）を立てず、レーンを順に自分で読む。
