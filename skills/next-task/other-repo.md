# 作業先が別のリポジトリのとき

タスクが直す対象が自分の作業ツリーの外のリポジトリのときの、実装の依頼文の項目（手順5c）と受け入れ（手順6）。

## 実装の依頼文に足す項目（手順5c）

   - 作業先が別のリポジトリのときだけ渡す（下の手順6の「作業先が別のリポジトリのとき」）: 「作業先の
     リポジトリでは、別の作業ツリー（`git -C <作業先> worktree add -b <枝> <パス> main`。`<枝>` はタスクIDを
     小文字にしたもの。`T-012` なら `t-012`）で直してコミットし、**コミットの
     あと**にその作業ツリーを cwd にして `tw verify` を打つ（控えは cwd の作業ツリーごとで、鍵に `HEAD` の
     SHA を含むので、コミットの前に打つと受け入れで `NOT_VERIFIED head` になる）。`tw step`・`tw pause` は
     着手した作業ツリーを cwd にして打つ（印は作業先の作業ツリーにも置かれる）。最後の段の返却は、
     作業先の作業ツリーの `tw verify-check` が `VERIFIED_SAME` でなければ hook に拒まれる。**`main` へ入れず、
     作業ツリーと枝を消さずに残して**、作業ツリーのパスと `tw verify` の判定行（`VERIFIED`・
     `VERIFY_NOT_PASSED` など）を報告に書く。作業先に `.tw/config.toml` があれば台帳（`.beads`）が無くても
     `tw verify` は打てる。設定が無く `tw verify` が `MISSING` を返すときは、検証コマンドを自分で打って通し、打ったコマンドと終了コードを報告に書く」。
     `<枝>` と `<パス>` は依頼文に書いて渡す。`tw handback-guard` は `### 作業先` のリポジトリの作業ツリーのうち
     この名前の枝のものを見るので、別の名前で作ると関門が作業先を見ない。作業先で `tw verify` が `MISSING`
     （`INVALID` も同じ）を返すとき、または作業先の設定ファイルに検証コマンドの行が無いときは、関門は
     その作業ツリーの検証を求めずに通す（控えで確かめられないので、受け入れで検証コマンドを打つ）。
     別のリポジトリの作業ツリーには着手の控えが無いので、そこでのコミットは hook に拒まれない
   - 同じく作業先が別のリポジトリのときだけ渡す: 「作業先の本体の作業ツリー（`git worktree list` の
     先頭。全プロジェクトが参照する実体のことがある）のファイルは読むだけで、書き換えない。そこを cwd に
     して編集しない。枝も切り替えない。編集は必ず自分の作業ツリーの下のパスに対して行う」

## 委譲の前に本体の汚れを控える（手順4aのあと）

   作業先が別のリポジトリのとき、最初の委譲の前に `git -C <作業先の本体> status --short` を打ち、出力を
   一言メモしておく（空なら「空」）。本体には、委譲先ではなく別のセッションが未コミットの変更を置いている
   ことがある。受け入れで見つけた汚れが委譲の前から在ったものかを、この控えで区別する。

## 受け入れ（手順6）

   **最初に本体の汚れを見る**（`git diff` や `tw verify-check` より前）: `git -C <作業先の本体> status --short`
   を打ち、委譲の前の控えと比べる。

   | 見たもの | すること |
   | --- | --- |
   | 空、または控えと同じ | 次へ |
   | 控えに無いファイルがあり、中身（`git hash-object <ファイル>`）が委譲先の枝の同じパス（`git rev-parse <枝>:<パス>`）の blob と同じ | 委譲先が本体に書き残したもの。報告と食い違うものとして `${CLAUDE_SKILL_DIR}/return-abnormal.md` の表に従い、委譲先へ `SendMessage` で伝えて差し戻す。`git restore` は blob が同じと確かめたファイルだけに打つ |
   | 控えに無いファイルがあり、blob が枝と違う・枝に無いファイル | 委譲先か別の作業か分からない。消さずに、ファイルと `git diff` の要点を添えて人に預けて終了する |
   | 控えにあったファイル（委譲の前から在る） | 別の作業。消さない。本体が汚れているあいだは下の `tw land` が `NOT_LANDED` で止まるので、汚れが消えるのを待つか、人に預けて終了する |

   **作業先が別のリポジトリのとき**（タスクが直す対象が自分の作業ツリーの外のリポジトリ）: 控えは
   cwd の作業ツリーごとに別なので、`git diff` と `tw verify-check` は、委譲先が残した作業先の作業ツリー
   （報告のパス。枝はタスクIDを小文字にした `<枝>`）で `cd <パス> && tw verify-check` と打つ（自分の作業ツリーで打つと `NOT_VERIFIED none`
   になるだけ）。レビューの判定も同じ作業ツリーで、主ブランチから委譲先の枝までの範囲を渡して打ち
   （`python3 ${CLAUDE_SKILL_DIR}/scripts/review_needed.py --difficulty <difficulty> main..<枝>`）、
   レビュアーに渡す差分のコマンドも `git diff main...<枝>` に、コメント行を拾うコマンドの範囲も
   `main..<枝>` にする。表は同じに読む。`VERIFIED_SAME` なら、検証コマンドを打たずに同じ作業ツリーで
   `cd <パス> && tw land <枝>` を打つ。`tw land` は作業先の本体で `<枝>` を ff-only で主ブランチへ合流し、
   入ったことを確かめてから作業ツリーと枝を消す。`git merge`・`git worktree remove`・`git branch -d` を
   素で打たない。
   `NOT_VERIFIED` ならその作業ツリーで `tw verify` を打ち直してから同じ段取りへ進む。受け入れで直すなら
   その作業ツリーで直してコミットしてから打つ。設定が無く `tw` が `MISSING` を返す作業先では控えが無いので、
   委譲先の報告を信用せず検証コマンドを打つ（`tw land` はタスク運用を始めていない作業先でも打てる）。

   | `tw land` の先頭語 | すること |
   | --- | --- |
   | `LANDED` に続けて `REMOVED`・`DELETED` | 次へ |
   | `NOT_LANDED`（何も変えていない） | 理由が「ff-only で合流できない」なら、作業先の主ブランチが先へ進んでいる。その作業ツリーで主ブランチを取り込んで `tw verify` を打ち直してから、もう一度打つ。ほかの理由は行を添えて人に預けて終了する |
   | `NOT_REMOVED`（合流は済んでいる） | 残った作業ツリーか枝を報告に書いて次へ進む（消すのは人に預ける） |
   | `GIT_READ_ONLY` | `task-workflow` の WORKFLOW.md の終了コード表のとおり |

   **許可規則**: auto mode の分類器は、作業先の本体の主ブランチへ合流するコマンドを [Modify Shared Resources]
   として拒むことがある。`tw land` も許可規則が無ければ拒まれうるので、利用者が `settings.json` の
   `permissions.allow` に `Bash(tw land:*)` を置く。エージェントは置かない。拒まれたら回り道をせず、
   作業ツリーのパスと枝を添えて人に預けて終了する。
