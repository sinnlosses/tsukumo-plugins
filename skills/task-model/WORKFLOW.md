# タスク運用（Beads ＋ `tw` コマンド）の正典

タスクの本文・着手の印・採番・履歴は Beads（`bd`）に置き、`tw` が Beads とトラッカーと git をつなぐ
（末尾の「Beads とトラッカー」）。エージェントのドラフトも Beads の課題（`draft`）に置く。

タスク運用のスキル（下の用語の入口・流れ・並びのスキル）が従うルール。このファイルとこのスキルの副ファイルは、
個々のスキルの名前を書かず、役の名で書く。
**手順は `tw` コマンドが持ち、自己テスト（`scripts/tests/selftest_task.py`）で守る。** スキルの本文は
「どのサブコマンドをいつ打つか」と「人が判断する点」だけで、プロジェクト側で手順を上書きする
仕組みは無い。

**用語**（役の名。どのスキルが担うかは、それぞれのスキルの説明が言う）:

- **入口**: タスクを1件選んで着手の印を立て、流れを呼ぶ手順。`/loop` から回すのもこれ
- **登録の入口**: 指示・ドラフトの課題をタスクに分解して `tw new`・`tw edit` で登録する手順
- **一覧の入口**: タスクの一覧と状態を読むだけの手順
- **用意の入口**: プロジェクトに `.tw/config.toml` と `.beads` を用意する手順
- **流れ（flow）**: 着手の印の立ったタスクを段に並べて進める順。既定は委譲→受け入れ→振り返り→送り出しで、
  変種（委譲しない近道・メインで行う・`hold` を決める）もある。設定の並びを順に呼ぶものを**オーケストレーター**と呼ぶ
- **並びのスキル**: 流れの1段を担う差し替えの単位。設定の `steps` に全名で並べ、オーケストレーターが順に呼ぶ。
  既定の並びは**実装**・**受け入れ**・**振り返り**・**送り出し**の4つ

## ファイル配置と設定ファイル

設定は `.tw/config.toml`、作業ツリーごとの控えは `.tw/local/` に置く。
| 場所 | 役割 |
| --- | --- |
| 本体の根の `.beads/` | タスクの本文・着手の印・採番・履歴（Beads。下の「Beads とトラッカー」）。`bd init --stealth` が `.git/info/exclude` で外すのでコミットしない。全作業ツリーで1つ |
| `.tw/config.toml` | 設定（下）。コミットする |
| `.tw/.gitignore` | 中身 `local/`。`.tw/local/` だけを git の外に置く。`init.py` が書き（無いときと、旧い形のとき）、`tw` は書かない。コミットする |
| `docs/history/retrospect.md` | 横断の振り返りの記録（1回ごとに先頭へ `## YYYY-MM-DD（開始日〜終了日）` の見出しを足す。書くのは週ごとの振り返り）。`tw status` が見出しの日付から `retrospect_due` を決める |
| 台帳 `$(git rev-parse --path-format=absolute --git-common-dir)/task-workflow/`（環境変数 `TW_STATE_DIR` があれば `$TW_STATE_DIR/<本体の作業ツリーの名前>-<共有の git dir の realpath の sha1 の先頭12桁>/`） | 着手から送り出しまでの出来事（`flow/<YYYY-MM>.jsonl`。1行1出来事。`tw metrics` が読む。会話・コマンド・パスは入れない。消えない）。コミットしない。全作業ツリーで1つ。`TW_STATE_DIR` を付けると、そのあとの記録はその下に書き、共有の git dir の台帳は読まない（写さない）。書けなければ標準エラーに1行出すだけで、元のサブコマンドの出力と終了コードは変わらない |
| 作業ツリーの根の `.tw/local/task-open-claims/T-xxx` | `claim` から `done`・`release`・`ship` までの控え（中身は空）。`tw commit-guard`・`tw handback-guard`・`tw ask-guard`・`tw ref-guard` が読む。コミットしない。作業ツリーごと |
| 共有の git dir の `hooks/reference-transaction`（`git rev-parse --git-path hooks` の下。`core.hooksPath` があれば置かない） | `tw ref-guard` を呼ぶ薄い殻（2行目が印 `# tw ref-guard`）。`claim` が置き、`done`・`ship` では消さない。控えの無い作業ツリーでは何もしない。印の無い利用者の hook があれば置かない。消してよい（次の `claim` が置き直す）。全作業ツリーで1つ |
| 作業ツリーの根の `.tw/local/` | `tw verify`・`tw pause`・`tw step` を打った時点の中身の鍵、`ship` の検証の借り、検証のログ、書き換える道具を使ったサブエージェントの印（`task-agent-writers/<agent_id>`。着手の控えが無くなると消える）、`agent` の出来事を台帳へ残した印（`task-agent-tasks/<agent_id>`。同じく消える。出来事は `commit-guard` が、着手の控えがちょうど1件の作業ツリーでのサブエージェントの最初の Bash に1回だけ `flow/` へ足す〔タスク・`agent`＝agent_id・`session`＝session_id〕。入力に `agent_id`・`session_id` が入る根拠は Agent SDK の `BaseHookInput` の型定義で、実機の hook 入力のダンプではない）。コミットしない。作業ツリーごと。初めて書くときに `tw` が作り、中身 `*` の `.tw/local/.gitignore` を置く |

**プロジェクトごとに変わる値は `.tw/config.toml` に置く**（コミットする。`AGENTS.md`・`CLAUDE.md` には
書かない）。`tw` は `layout.read_config` の1つの口で読み、`tw config` が解けた値を出す（スキルはこれを読む）。
必須は `verify` だけ:

```toml
# タスク運用の設定（tw が読む）
verify = "pnpm check"        # 受け入れ判定に使う。打つものが無ければ "なし"
# format = "pnpm format"     # あれば tw verify が検証の前に打つ
# branch = "既定"            # 既定 / 作業ブランチを切る / 切らない
```

形式は TOML の部分集合。書き間違いは行番号付きの `INVALID`（終了コード3）。

| キー | 値 |
| --- | --- |
| `verify` | 検証コマンド（`sh -c` で打つ）。`"なし"` なら打たない。必須 |
| `verify_before_ship` | 送る前の検証コマンド（下） |
| `format` | 整形コマンド。`tw verify` が検証の前に打つ（`tw-reference.md` の `verify`） |
| `step_check` | 段ごとに安く打つ検査コマンド（無い・`なし` なら打たない）。`tw step` が段の控えを書く前に、タスクの各作業ツリーでその木の設定のものを打ち、落ちたら控えを書かず `STEP_CHECK_FAILED`。最後の段は `tw step` を打たないので、全段の検査は `verify` に任せる（`tw-reference.md` の `step`） |
| `branch` | `既定`・`作業ブランチを切る`・`切らない`（下の表） |
| `base_branch` | 主ブランチの名前（下の順1） |
| `store` | `beads` だけ（ほかの値は `INVALID`。[legacy.md](legacy.md)） |
| `tracker` | `なし`・`github`・`jira`（「Beads とトラッカー」） |
| `github_project` | `"<owner>/<番号>"`（Status 欄を書く Project）。`tracker = "github"` なら必須 |
| `backup` | Beads のバックアップの置き場（git の外） |
| `hook_tally` | 直近30日の hook ごとの拒否の回数を出すコマンド。読むのは `tw` ではなく週ごとの横断の振り返りで、無ければその観点を飛ばす |
| `review_code_globs` | 文書の拡張子（`.md` など）でもコード扱いにして、受け入れの新しい文脈のレビューを掛けるパスの glob の配列。最上位に `review_code_globs = ["skills/**", "agents/**"]` の形で書く。`**` は `/` を越え、`*`・`?` は越えない。空の配列でも書かなくてもよく、無ければ文書の拡張子だけの差分は `SKIP\tdocs-only`。`review_needed.py` が読む |
| `steps` | スキルの並び。最上位に `steps = ["<全名>", …]`（文字列の配列）で書く。1つ以上・重複なし。並びの順が呼ぶ順。無ければ `tw config --schema` の `default`（`tw` と同じ plugin の候補を、`metadata` の `workflow-step-order` の小さい順に並べたもの）。名前は同じ `values`（SKILL.md の frontmatter の `metadata` に `workflow-step: "true"` を持つスキル）の全名。各候補の `title`（日本語の段の名前）は `metadata` の `workflow-step-title` で、無ければ `name` と同じ。書くのは `tw config set steps '<1行の JSON の配列>'` |

欄の形（`steps` の既定と候補）は、ここに書き写さず `tw config --schema` が出す。廃止した `flow` の行と `[parts]` の表は、設定に残っていれば `INVALID`（終了コード3）で止まる。

- `verify_before_ship` があれば、`tw verify` は `verify` の代わりにそれを打ち、`tw verify-check`・`tw pause`・`tw step`
  の鍵もそのコマンドで取る。`tw ship` は主ブランチへ入れる直前に同じコマンドを打つ。ただし控えの木とコマンドが
  今の中身と同じで、付け替えが無く、借りも無いときは飛ばす。付け替えた回は `verify` を打たず、これだけを1回打つ。
  落ちれば `VERIFY_FAILED`（終了コード8）で送らない。全件の E2E のように重い検証を、1件の中で1回に済ませたいときに使う
- `branch` の語彙:

| 値 | 意味 |
| --- | --- |
| `既定` ／ `作業ブランチを切る` | `claim` が主ブランチから `feature/T-xxx` を切って移り、`ship` が送ったあと枝から降りて消す（下の「送り出し」） |
| `切らない` | いまの枝のまま。主ブランチの上ならそのまま積み、作業ツリーの枝なら `ship` で送る |

**設定の判定**（`tw` のどのサブコマンドも打つ前に見る。`config-doctor`・`land` は除く）: `.tw/config.toml` が無ければ
`MISSING`（終了コード6）で止まる。読めなければ行番号付きの `INVALID`（終了コード3）。設定があっても本体の根に `.beads` が
無ければ、`config`・`verify`・`verify-check` を除いて `MISSING\t<.beads のパス>`（終了コード6。`verify`・`verify-check` は台帳の無い
リポジトリでも打て、`verify` はそのとき `## やること` の検査を飛ばす）。設定は `.tw/config.toml` だけから読む。

merge commit を作る運用は選べない。**主ブランチへの ff マージ（`ship` に限らず、タスクの成果として
よそのリポジトリの主ブランチを進める場合も含む）は、人に確認を挟まず自動でやってよい**。push はどのプロジェクトでもスキルからは行わない（この自動化にも
push は含まない）。

**主ブランチの名前は `main` に固定しない**（`master`・`trunk` のリポジトリでも動く）。`tw` は
この順で決める（`gitinfo.base_branch`。1回の実行で1度だけ問い合わせて覚える）:

1. 設定の `base_branch`——**任意**で、保護ブランチや複数リモートの逃げ道
2. `git symbolic-ref --short refs/remotes/origin/HEAD` の枝名。**見るのは `origin` だけ**
   （`upstream` などの別名しか無ければ順3へ落ちる。fork 元を主ブランチの出どころにしないため。
   そういうリポジトリは順1で名指しする）
3. `main`・`master`・`trunk` のうち実在するもの（この順）
4. どれも無ければ `INVALID`（終了コード3）。**黙って `main` を作らない**

以下この文書で「主ブランチ」と書くのはこの枝で、tsukumo-plugins 自身では `main`。

## タスクの本文

書くのは `tw` コマンドだけで、`bd` を直に打って本文や label を直さない。`tw show T-xxx` は1件を
front matter（`id`・`summary`・`status`・`difficulty`・`loopable`・近道の印があれば `direct: Y`・`dependencies` の順の
`key: 値` の行を `---` で挟んだもの）と本文の形で出す。front matter は出力だけの形で、`tw edit` に渡す本文には付けない（付けると終了コード2）。

- `status` は `draft`・`todo`・`hold`・`done`・`dropped`。着手中は `todo` のまま着手の印（Beads の `in_progress` と assignee）が表す。
  着手しない判断で閉じたものは `dropped`。`draft` はエージェントが聞かずに積んだドラフト（下の「ドラフトの課題」）
- ID の形は下の「Beads とトラッカー」（`T-<n>`・`GH-<n>`・Jira のキー）。並びは数字の大きさで比べる

**本文の枠**（7つの見出しを**この順に全部**置く。書くことの無い欄は見出しだけ置いて、中身を空か
「なし」にする。見出しより前に文を置かない。ドラフトだけは見出しを欠いてよい）:

| 節 | いつ・誰が書くか | 空・「なし」 |
| --- | --- | --- |
| `## 目的・背景` | 登録時（登録の入口）。何のためか、コードのどこがどうなっているか。待ち時間・実行時間を縮めるタスクは小見出し `### 実測の内訳`（段ごとの時間と測り方）を置く | 不可 |
| `## 決まっていること（蒸し返さない）` | 登録時（聞いて決まったこと・承認の範囲。検討の経緯は書かない） | 可 |
| `## 解くべき論点` | 登録時（`opus` には必ず） | 可 |
| `## やること` | **登録時**（登録の入口）に、そのときの主ブランチで調べて書く（下の「登録時に書く `## やること`」）。`### 1. …` の形で実行の順に番号を振った段で書き、完了条件の各行をどの段で満たすかが分かるようにする（段の欄 `- 満たす完了条件:` で引ける。「段の形」。段は委譲の単位で、委譲先は1段ずつ返す）。着手時に `tw plan-check` が `PLAN_STALE`（名指したファイルが変わった）・`PLAN_NOT_FIRST missing`・`unrecorded`・`steps` を返したら、委譲先が実装の前に調べ直して書き直す（`tw edit T-xxx --section 'やること' --body-file -` で節の中身だけを渡す。作業より先だったかを `tw plan-check` が見る） | 不可（`--hold` で登録するものだけ可。todo に戻したあと着手時に書く。`--draft` は可。`todo` へ進めるときに書く） |
| `## 完了条件` | 登録時。検証可能な言葉で | 不可（`--draft` は可。`todo`・`hold` へ進めるときに書く） |
| `## 注意` | 登録時・着手時・作業中の知見 | 可 |
| `## 参考情報` | 登録時・作業中（関係する文書・Issue・過去のタスク・URL） | 可 |

`## 結果` は枠の外で、`tw done` が最後に足す（done/dropped で必須）。`tw new`・`tw adopt` は
枠と違う本文（見出しの欠け・順・枠の外の見出し）、空か「なし」の `## 目的・背景`・`## 完了条件`、
空か「なし」の `## やること`（`--hold` を除く）、下の形に沿わない計画、`## 結果` を拒む。
`difficulty` が `opus` で `## 解くべき論点` が空か「なし」のときも拒む（`--hold` でも）。
`tw edit` も枠を検査する（`## やること` は書いてよい）。既存のタスクを壊さないよう、変えた節だけを見る:
`opus` に上げる編集か `## 解くべき論点` を変える編集で論点が空か「なし」なら拒み、`## 目的・背景` を変える編集で
`- 観点:` の行が語彙の外なら拒む（どれも終了コード2。ドラフトを `todo`・`hold` へ進めるときは `tw new` と同じ検査）。
`tw new --draft` の本文は検査を緩める: 見出しは枠の部分列（順は枠どおりで、欠けてよい）で、中身が要るのは
`## 目的・背景` だけ。front matter・見出しより前の文・`## 結果` は拒み、`## やること` に中身があれば下の段の形も検査する。
`## 目的・背景` に `- 観点:` の行があれば、観点が語彙（7観点と、横断の振り返りの3観点）の中で、色が付くなら赤か黄でなければ拒む。
欠けた節は空の欄になり、`tw show` は7節をそろえて出す。ドラフトの本文を直す `tw edit` も同じ緩い検査で、
`## 完了条件` を空のまま `## やること` だけ書く途中の編集を通す。

**段の形**: `## やること` の `### ` 見出しは、段 `### <n>. <名前>`（`n` は `### 1.` から1つずつ増える）と
`### 名指すファイル`・`### 作業先` だけで、段は1つ以上置く（名指すファイル・作業先は段に数えない）。
最初の段より前の行は検査しないので、`## 解くべき論点` への答えは `### 1.` より前に太字の行で書き、小見出しにしない。
並べて走らせてよい段は、段の見出しから次の `### ` 見出しまでに欄を1行ずつ置く:
`- 前の段: <番号>, <番号>`（その段より小さい番号を重ねずに。最初から走れるなら `- 前の段: なし`）と
`- 触るファイル: ` に `` `パス` `` をコンマで並べたもの（名指すファイルと同じくリポジトリの根からの相対。
名指すファイルに無いパスも書いてよい）。前の段の欄の無い段は直前の段のあと（段1は最初から）に走る。
`- 満たす完了条件: 1, 3`（`## 完了条件` の行番号。何も満たさない段は `なし`）は、どの段がどの完了条件の行を満たすかを機械に読ませる欄で、
並列かどうかには関わらない。行は行頭が `1.`・`-`・`*` の項目を上から数え（項目が無ければ空でない行を数える）、
どの段にも引かれていない行と、完了条件に無い番号があれば、`tw new`・`tw adopt`・`tw edit`（`## やること` か `## 完了条件` を変えて中身が入るとき）が終了コード2で拒み、
`tw plan-check` は1行目のあとに `PLAN_UNCOVERED\tT-xxx\t<n,…>`（引かれていない行はそのまま、存在しない番号は `n?`）を出す。
欄を持つ段が1つも無い旧い計画は検査しない（従来どおりメインが読む）。機械が見るのは抜けだけで、
その段で本当に満たされるかは読んで決める。
最後の段は欄によらずほかの段がすべて済んでから走る（合流。`tw verify` を打つのは最後の段だけ）。
どちらも他方のあとと決まっていない段の組が並列の組で、それに入る段は触るファイルの欄が要る。
並列の組の触るファイルが重なれば（同じパスか、片方がもう片方のディレクトリの中）、番号の小さい段を先にした
1本道に直し、それで前後の決まった組も並列から外す（`tw plan-check` の `PARALLEL`・`SERIAL`。段ごとに待つ段は `STEP`）。
`tw new`・`tw adopt` と、`## やること` を変えて中身を入れる `tw edit`（`--section 'やること'` も本文ごとも）は、
この形に沿わない計画を理由つきで終了コード2で拒み、何も書かない。`## やること` を変えない `tw edit` は
段を見ない。入口を通らずに入った段の読めない計画は、`tw plan-check` が `PLAN_NOT_FIRST\tT-xxx\tsteps` で
書き直しへ回す。
段の名前は `## やること` の `### n. 名前` がそのまま帯の段の名前になる。実装のあとの段は計画に書かず、
`steps` の並びのスキルから決まる（既定の並びなら「受け入れ」「振り返り」「送り出し」。`tw plan-phases`。使い方はオーケストレーターの「進み具合の帯（`work_plan`）」）。
いまの `## 目的・背景`・`## 完了条件` と違う本文は `--change-frame` なしでは `FRAME_CHANGED` で拒む
（別のタスクの下書きを渡す事故を防ぐ。この2節を変えるのは `tw show` から作り直した本文のときだけ）。
いまの本文で中身が空か「なし」の節は比べないので、ドラフトの空の `## 完了条件` を初めて書く編集は通る。

**段の中身の書き方**:

- 既存のファイル・設定・控えの形を読み替える作業は、ありうる入力の状態の組み合わせ
  （例: 設定の有無 × 旧い置き場の有無 × 新しい置き場の有無）を表にし、行ごとに期待する結果と
  確かめる自己テストを書く。自己テストは、すでにあるもので確かめられる行はその名前を書き、
  新しく足すのは確かめるテストが無い行だけにする。
- 各段のあとで自己テストが通る順に段を切る。後の段の変更が無いと前の段の自己テストが落ちるなら、
  その変更を前の段に入れる。
- 口・概念・語を消すタスクは、`tw verify` の段より前に、消す語をソース・文書・テストの全体で grep して、
  名指したファイルの外に残った文を直す段を置く。
- 用語の改名を追随するタスクは、置き換えた行ごとに、旧称が指していた範囲と新しい呼び名が指す範囲が同じかを読む
  段を置く。違う行は用語集の別の語で指すか据え置き、読んだ行数と違った行数を報告に件数で書く。
- 型に必須の欄を足す・関数や口の型を変える段は、計画を書く前にその型の値を作る箇所（作り手・疑似の駆動・テストの代役やフィクスチャ）と
  呼ぶ箇所を grep で数え、その段の触るファイルと `### 名指すファイル` に入れる（数え漏れは型検査の落ちで実装中に見つかり、計画の外の変更になる）。
- 文書の写しを畳む（重複した記述を消して正典へ寄せる）タスクは、最後の実装の段のあとに、消した行の一覧を出して
  1行ずつ残る先（正典の表の行・残した文）を対応づける段を置く。一覧は `removed_lines.py` が出す
  （作業を作業ツリーにコミットせず残すなら範囲なし、コミットを積む別の作業ツリーなら `main..<枝>`）。
  委譲先が手で数えない。完了条件に「消した行の全部に残る先を対応づけた表が報告にある
  （残る先の無い行は、消してよい理由を添える）」を入れる。
- 描画を変えるタスクは、組み立てた直後に画を撮って受け入れ役の目視待ち（`- 目視:` の判定）を受ける段を、
  E2E の期待値を撮り直す段と `tw verify` の段より前に置く。
- 本文が前提にする既存の振る舞い（「既存」「いまは〜」「GH-nnn が入れた」）は、段に書く前にコードか実行で確かめ、
  段の冒頭に「前提の裏取り」として、前提1つにつき「前提 | 確かめた場所（ファイルと関数）か打ったコマンド | 結果」を1行書く。
  食い違いが分かったら押し切らず、`## 目的・背景`・`## 決まっていること` を変える理由を報告に書いて止める（`--change-frame` は付けない）。

**登録時に書く `## やること`**（`tw new`・`tw adopt`）は、段のほかに小見出し
`### 名指すファイル` を1つ置き、計画が前提にするファイルを1行1つ `` - `パス` ``（後ろに説明を書いてよい）で並べる。
パスはリポジトリの根からの相対で、登録時の主ブランチの木にあるファイルかディレクトリに限る（新しく作るファイルは
置くディレクトリを名指す）。作業先が別のリポジトリなら、小見出し `### 作業先` を1つ置いてそのリポジトリの根の
絶対パスを1行 `` - `パス` `` で書く（`~` は展開して書く）。そのとき名指すファイルは作業先の根からの相対で、
検査・SHA の控え・着手時の判定は作業先のリポジトリ（の主ブランチ）で行う。
`tw new`・`tw adopt` は `HEAD` と主ブランチの分かれ目の SHA を控え、`tw claim` がその SHA から着手時の主ブランチの先端までに
名指したファイルが変わったかを判定する（`tw plan-check` の `PLAN_REGISTERED`・`PLAN_STALE`）。
変わっていれば、委譲先が実装の前に調べ直して書き直す。

名指したファイルが変わっていても、次の4つがすべて成り立てば古くない（`PLAN_REGISTERED` のまま。`tw claim` は印に `registered` を残す）:
段が `- 満たす完了条件:` の欄を持つ（欄の無い旧い計画は従来どおり変わっただけで古い）・欄が `## 完了条件` を覆っている（`PLAN_UNCOVERED` が出ない）・
名指したパスが主ブランチの先端の木に残っている・控えた SHA から先端までの差分（`git diff -U0`）の追加・削除行に、段の本文のバッククォートで囲んだ識別子が1つも出ない
（識別子は4字以上で `/` と空白を含まず、名指すパスと同じでない語。`### 名指すファイル`・`### 作業先` の節は読まない）。
外れれば `PLAN_STALE\tT-xxx\t<変わったファイル>\t<理由>`。理由は `legacy`（欄の無い旧い計画）・`uncovered`・`path-missing`・`no-identifier`（本文に識別子が1つも無い）・
`touched:<語,…>`（差分に出た識別子）・`unreadable`（作業先・SHA・差分が読めない。バイナリやモードだけの変更で差分に追加・削除の行が出ないときも）。疑わしいときは古いほうに倒す。
「その段で本当に満たされるか」は機械が見ず、人（メインか委譲先）の判断として残る。

**登録時の `## 決まっていること（蒸し返さない）` の裏取り**: 項目が挙動・数え方（「〜すれば〜になる」「〜を除いて数える」など）を
言い切るときは、登録の前に実物（コード・文面・1回の実行）で通ることを確かめ、根拠を項目の後ろに1行添える
（ファイルと関数、または打ったコマンドと結果）。聞いて決まっただけの方針や承認の範囲には要らない。
`tw new` の本文検査（`taskfile.validate_new_body`）は枠・段・名指すファイルの形だけを見て、この節の項目に決まった書式は無い。
言い切りかどうかは文面から機械で決められず、根拠の行を一律に求めると聞いて決まっただけの項目にも要るので、検査には足さない。

**手順を書く文書の変更の計画に順の確かめの段を求める検査**: `tw plan-check`（`tw_edit._print_plan_check`）は印・段の見出しと欄（`- 前の段:`・`- 触るファイル:`）の形・名指すファイルの変わりだけを見て、段の本文の文は読まない（`taskfile.plan_step_specs`）。
計画が機械に渡す欄は `- 前の段:`・`- 触るファイル:` の 2 つだけで、コマンドの手順を書く文書を直す計画かを示す欄も印も無く、
名指すファイルのパスからも手順を書く文書とそれ以外の文書を分けられない。段の文面の判定は自由記述の解釈になるので、`plan-check` には足さず、実装役の決まり（`implementer-brief.md`）に置く。
同じ理由で、検査を置き換える・足す段が弱めた実装で落ちる確認を求めているかも見ない。名指すパス（`test/architecture` など）から検査を扱う計画とは分けられても、段が自己テストを求めているかは本文の解釈になる。

## status と着手の印

```
 (無) ─tw new --draft─▶ draft ─tw done --dropped─▶ dropped（その場で閉じる）
                          │ tw edit --status todo|hold（本文を検査する）
                          ▼
 (無) ─tw new─────────▶ todo ─tw claim─▶ todo＋印 ─tw done＋コミット＋tw ship─▶ done / dropped（印は消える）
                          ▲  │                  │ tw release
                  人が直す │  ▼ 人が直す          ▼
                          hold                 todo
```

- `CLAIMED`（作業中）は「`todo` ＋ 着手の印」（Beads の `in_progress` と assignee。actor は作業ツリーの名前）。
  `hold` は人の判断待ちで、`claim` は拒む。`hold` ↔ `todo` は人（か人がいるセッション）が
  `tw edit T-xxx --status todo|hold` で直す（コミットも `ship` も要らない。ユーザーが直接呼んだ入口が、
  メインで判断を聞いてこの切り替えをすることもある）
- `draft` はエージェントが聞かずに積んだドラフト（下の「ドラフトの課題」）で、承認待ち。`bd ready` に出ず、入口は
  選ばず、`claim` は `NOT_READY\tT-xxx\tDRAFT` で拒む。承認されたら人がいるセッションが
  `## 完了条件`・`## やること` を `tw edit` で書き、`tw edit T-xxx --status todo|hold` で進める（`tw new` と同じ本文の検査が通らなければ
  何も書かずに `NOT_READY\tT-xxx\tDRAFT\t<理由>`。通れば印 `draft` を外し、metadata `from_draft` に
  `## 目的・背景` の `- 観点:` の行の観点（色を除く。行が無ければ `不明`）を残し、`## やること` に中身があれば登録時の計画として
  `task_plan_base` を控える）。却下は理由を `## 結果` にして `tw done T-xxx --dropped` で、`claim` もコミットも `ship` も要らずに
  その場で閉じる
- **見送り（やらない）と決まったら、その場で `dropped` にして閉じる。** 決定を `## 決まっていること`・
  `## 注意` に書くだけで `todo`・`hold` に残さない（残すと入口が READY として選び、委譲先が
  前提を確かめ直すだけの空振りになる）。`claim` していなければ `claim` してから `tw done --dropped`
  で閉じる
- **依存の解決**: `done`・`dropped`（`ship` で `bd close` したもの）と、Beads に無い ID（旧アーカイブ由来）は解決済み。
  `todo`・`hold` は未解決。後から変えるのは `tw edit T-xxx --add-deps T-yyy` と `--remove-deps`（本文の `## 注意` に書くだけでは Beads の依存に入らず、BLOCKED に出ない）
- **委譲先を hook が拒む**: 印を立ててから `done` を打つまで委譲先（サブエージェント。plugin で入れたときは名前を問わず、リンクだけで入れたときは frontmatter に hook を持つ実装役のエージェント定義）に掛かる関門（拒むもの・掛かる口）は `tw-reference.md`「hook の関門」節。コミットは git の hook（`ref-guard`）でも拒み、こちらは呼び手を問わないので、控えがあるうちはメインも `tw` を通さずにコミットしない（`tw finish` で `done` のあとにコミットする）。
  委譲先は `Edit`・`Write` で書き、検証は `tw verify` で打ち、最後でない段は `tw step T-xxx <n>`、止める返却は `tw pause` を返す直前に打つ
- **取り残し**（前提: 1つの作業ツリーでは同時に1セッション）:

| 状態 | 表示 | 誰が何をする |
| --- | --- | --- |
| **自分の**作業ツリーの印が入口の開始時点で残っている | `CLAIMED`（印の列が自分） | 前のセッションが落ちた。着手せず、`tw release T-xxx`（捨てる）か人が続きを見るかを預けて止まる |
| 他の作業ツリーの印で、assignee がどの作業ツリーの名前でもない／`ship:*` が立っていて、metadata `task_shipped` の範囲の先端が主ブランチに入っている（その記録が無い・祖先でないときは、主ブランチに着手より後の `T-xxx:`〔`github` なら `GH-<n>:`〕の件名のコミットがある）／assignee の無い `in_progress` | `STALE:gone`／`STALE:shipped`／`STALE:no-owner` | `tw status` が出すだけ。片付けるのは人（`tw release T-xxx --force` ＝ `bd unclaim --force`） |
| それ以外 | `CLAIMED`（経過時間つき） | 触らない。長さだけで取り残しと言わない |

印を時間で自動的に壊さない。取り残しは人に預ける。**`bd reclaim` を打たない**——`--claim` には5分の lease が付くが、
期限が過ぎても他の actor は `claim` できない（実測）。期限切れの印を外すのは `bd reclaim` だけで、それは長い作業の印を壊す。

## difficulty とモデルの切り替え

**判断の重さ**を3段階で表すラベル。以下の対応表に従い、委譲先サブエージェントのモデルが決まる。

| 値 | 基準 | 例 |
| --- | --- | --- |
| `haiku` | 機械的な作業。判断がほぼ不要で正解が1つに定まる | 型定義を1ファイルに抜き出す |
| `sonnet` | 既定。判断を含む実装はまずこれ。設計判断が要っても、既存の方針・前例と論点の書き出しで決められる | 責務ごとのファイル分割・部品の組み替え |
| `opus` | `sonnet` ではどうしても厳しいときだけ。前例の無い方針そのものを決める・原則どうしが衝突する・並行性やエラー方針を組み立て直す | 並列化の設計 |

**difficulty → 委譲先モデルの対応表**（ラインナップが変わったら**この表だけ**を直す。3段の語彙・
Beads の label・各スキルの本文は触らない）:

| difficulty | Agent ツールに渡す `model` | いまその名前が指すモデル |
| --- | --- | --- |
| `haiku` | `haiku` | Claude Haiku 4.5（`claude-haiku-4-5`） |
| `sonnet` | `sonnet` | Claude Sonnet 5（`claude-sonnet-5`） |
| `opus` | `opus` | Claude Opus 5（`claude-opus-5`） |

渡すのは**世代を含まない短い名前**（`haiku`／`sonnet`／`opus`）で、世代が上がっても指す先が
入れ替わるだけなので、ふだんは右端の列だけが古くなる。`fable` のように3段に割り当てていない
モデルもあるので、**3段の語彙＝実在のモデル名だと読まない**（右端の列が対応の正典）。
右端の列（いまその名前が指すモデル）を直すときは、`/claude-api` で現行のモデルIDを確かめてから書く。記憶で書かない。

- 迷ったら `sonnet`。`opus` は登録の時点で上の条件に当たると言い切れるときだけ付ける。作業量では上げない。
  着手して `sonnet` では厳しいと分かったら、押し切らず `opus` に上げてから再開する
- **メインセッションのモデルは判断材料にしない**（セッションは自分のモデルを途中で変えられないので、
  切り替えの手段は委譲だけ）。**一致していても委譲する**——理由はモデルではなく文脈の隔離
- **委譲しないのは2つだけ**: `loopable: N` に当たるとき（ユーザーへの確認が要る・会話の文脈に依存する）と、
  近道の印があって `tw claim` が `direct=Y` を出したとき（下の「委譲しない近道」）。そのときだけメインが実行し、
  実行モデルは `difficulty` と一致しない
- 本文を prompt に貼らない。ID を渡して `tw show T-xxx` で向こうに読ませる
- 完了報告をそのまま信用せず、受け入れは検証コマンドの結果と、受け入れ役（受け入れの段の中の判定役。契約はオーケストレーターが持つ）の判定で決める。メインは差分を読まず画像を開かず、判定の行で分ける（目視の完了条件は、受け入れ役が画像を開いて見比べる）

**委譲しない近道**: 色1つの直しのような小さいタスクは、段の出入り（計画・委譲・受け入れのレビュー・振り返り）の
ほうが中身の作業より長い。登録時に登録の入口が下の基準に当たるタスクに印（label `direct:Y`。`tw show` の front matter では `direct: Y`。`tw new --direct`・`tw edit --direct Y|N`・`tw adopt --direct`）を付け、
入口と流れは印を見るだけで、着手時に「これは近道か」を判断しない。**基準の値の置き場はこの表だけ**で、
読むコードは `scripts/core/taskfile.py` の定数 `DIRECT_DIFFICULTY`・`DIRECT_MAX_STEPS`・`DIRECT_MAX_PLAN_FILES`
（値を変えるときは表と定数を同じコミットで直す）:

| 条件 | 基準 | 誰が見るか |
| --- | --- | --- |
| `difficulty` | `haiku` | `tw`（登録時と `tw claim`） |
| `## やること` の段の数 | 1 | `tw`（同上） |
| `### 名指すファイル` の数 | 2以下 | `tw`（同上） |
| `### 作業先` | 無い（同じリポジトリ） | `tw`（同上） |
| 登録時の計画が着手時も古くない | `PLAN_REGISTERED` に当たる | `tw claim` |
| 振る舞いの契約（公開の出力・引数・終了コード・正典の規則）を変えない | 変えない | 登録の入口（人の判断） |

- `tw new`・`tw adopt`・`tw edit --direct Y` は、`tw` の見る条件を外れた印を終了コード2で拒む。登録のあとに
  `tw edit` で `## やること`・`difficulty` を変えて外れたら、書き込みは通して印を外し `DIRECT_OFF` を出す
- `tw claim` は条件を測り直し、`CLAIMED` の行末に `direct=Y`（近道で進める）か `direct=N:<理由>`（通常の道）を出す
- 近道で通すのは、`## やること` に沿ったメインの直し・`tw verify`・`tw done`・コミット・`tw ship` だけ。委譲・
  受け入れのレビュー・1件ごとの振り返りは通らない。メインが直し始めるときに `tw lap T-xxx direct` を打つ。
  直しが名指すファイルの外へ広がる・判断が要ると分かったら、近道を降りて通常の委譲に戻る（`lap delegate` が
  残るので、その回は通常に数える）。手順はオーケストレーターの近道の流れが持つ
- 差分の行数は測らない。近道の大きさは、事前に測れる段の数と名指すファイルの数で抑える
- `/loop` での文脈: 近道でメインが読むのは `tw show`・名指すファイル（数は上の表の基準まで）・`tw verify` の出力の末尾だけで、
  検証のログ全文・正典・振り返りは読まない。上の委譲の実測（約7,000文字）と同じ桁に収まり、上限は
  オーケストレーターの `/loop` の続行判断に任せる（送り直すツールがあれば毎回空にする。無ければ文脈は Claude Code の自動の要約に任せる）
- **基準を見直す手がかり**: 週ごとの振り返りで `tw metrics --stages` の道の列（`direct`／`normal`）を同じ
  `difficulty` どうしで比べる。近道の段の合計が通常より縮んでいなければ、基準を狭める（表と定数を直す）

`haiku` を一律の例外にしないのは、着手時に「これは例外か」の判断が毎回1つ増えるため。
近道は印を登録時に付けて着手時は `tw` が測るだけなので、この判断は増えない。

## loopable（`/loop` に載せてよいか）

そのタスクを**ユーザーのいないところで進めてよいか**。`difficulty` とは独立。基準は
「**登録時にユーザーへ聞いても解けなかったもの**」だけを `N` にする:

| `N` にしたくなる理由 | 事前に聞けば解けるか |
| --- | --- |
| 複数案のどれを採るかが未定 | 解ける（決めて `## 決まっていること` に焼く） |
| 会話中の文脈に依存する | 解ける（文脈を本文に書き出す） |
| 元に戻せない／外部へ反映する | 解ける（承認の範囲を本文に書く） |
| 対話的な検証が要る | **解けない** → `N` |

迷ったら聞く。聞けない状況（無人のセッション）のときだけ `N`。`/loop` から回る入口は `N` を
選ばず、ユーザーが直接呼んだときは選んでよい。

**決める前に止まる要因を洗い出す**: `Y` は「実行中に利用者の手が要って止まらない」約束なので、
`loopable` を決める前に本文を次の表に当て、行ごとに解くか `N` にする:

| 実行中に止まる要因 | どうするか |
| --- | --- |
| 利用者への質問が要る判断が残る | 聞いて `## 決まっていること` に焼けば `Y` |
| 対話的な検証が要る | 解けない → `N` |
| 承認の範囲外の外部への反映・破壊的な操作・グローバル設定の書き換え | 承認の範囲を本文に書けば `Y` |
| 作業の途中で人の手が要る（`### 人がやること` のうち検証より前に要るもの） | 解けない → `N`（`ship` のあとでよいものは `Y` のまま `## 結果` に残す） |
| ツールの許可確認 | タスクの性質でなく、セッションの許可モードで決まるので `loopable` の判断に入れない |

取りこぼしは hook（`tw ask-guard`）が実行中の `AskUserQuestion` で捕まえる。境は流れの段で決まり、主のセッションの質問は
作業の段（`direct`・`delegate`・`accept`・`review`）を終えた後なら通し、サブエージェントの質問は段によらず拒む。
段の lap は並びのスキルではなくオーケストレーターが打つので、振り返りを外した流れでも受け入れの後の質問は通る。
拒むもの・捕まえないものは `tw-reference.md`「hook の関門」節で、捕まえないものはこの表で先に防ぐ。

**`hold` との違い**: `N` は「人がいれば誰でも進められる」、`hold` は「人が決めるまで誰も進められない」
（決まっていない判断そのものが待っている）。`hold` は `/loop` から回る入口が選ばない。ユーザーが
直接呼んだときは選んでよいが、判断は**委譲せずメインで** `AskUserQuestion` で聞き、答えを
`## 決まっていること（蒸し返さない）` に焼いて `todo` に戻してから `claim` する（サブエージェントは
ユーザーに聞けないので、委譲すると決める人がすり替わる。手順はオーケストレーターの `hold` を決める流れが持つ）。
frame が実装と合わず人が決め直すまで進められないタスクを `loopable: N` に直して止めるのは誤りで、
`hold` にして外し `/loop` は続ける（手順はオーケストレーターの `/loop` の続行判断が持つ）。
ドラフト（`draft`）は `hold` と違い、やるかどうか自体が未承認で、入口はどちらから呼ばれても選ばない
（承認して `todo`・`hold` に進めるのは登録の入口）。

## kind（種類）

種類は、ID を言わずに「不具合修正のどれか」と頼まれたときに `tw find` が `READY` を絞る手がかり。
付けるのは登録の入口で、下の表の行に当たるときだけ付ける。当たらなければ付けず、種類の無いタスクも語では絞れる。
語彙はこの表に固定し、表の外の語は `tw new`・`tw edit`・`tw adopt` の `--kind` が終了コード2で拒む。

| 種類 | 当てはまる変更 |
| --- | --- |
| `bug` | 不具合の修正 |
| `feature` | 機能の追加・変更 |
| `refactor` | 振る舞いを変えない整理 |
| `docs` | 文書だけの変更 |

置き場は Beads の label `kind:<種類>` で、1つのタスクに0か1つ（`tw edit --kind -` で外す）。
`kind:` の label が語彙の外か2つ以上なら、そのタスクは `INVALID` になる。

**`tw find [<語>…] [--kind <種類>]` の当て方**: `READY` の行だけを `tw status` の並びで見る。

- 語は NFKC と大文字小文字を揃えて、summary か `### 名指すファイル` のパスに含まれれば当たり。語どうしは言い換えとして扱い、どれか1つに当たればよい
- `--kind` を付けると、種類が違うタスクを外す。種類の無いタスクは語だけで決まる（`--kind` だけで語が無ければ当たらない）
- 結果は先頭語で決まり、モデルは summary と語を突き合わせない: 1件なら `FOUND`、2件以上なら `MANY`（先頭4件の `CANDIDATE` と、残りがあれば `MORE`）、0件なら `NONE`。列は `tw find --help`

## 送り出し

`tw ship` はタスクに紐付かない（登録・振り返り・`hold` の切り替えのコミットも同じ `ship` で送る）。

- 主ブランチより遅れていれば `git rebase <主ブランチ>`（付け替えるのは自分の `<主ブランチ>..HEAD` だけ）。衝突したら
  `rebase --abort` して `CONFLICT`
- 送るのは `git -C <本体> merge --ff-only <コミット>`（本体 = 主ブランチを出している作業ツリー）か、
  本体が無ければ比較付きの `git update-ref`。先を越されたら rebase からやり直し、3回で `RACE`
- **merge commit は作らない**。本体が汚れていれば `MAIN_DIRTY` で送らない
- 送り終えたあと（`SHIPPED`・`NOTHING` のどちらでも）、自分の印のうち `ship:*` の立ったものを `bd close` する
  （依存はここで初めて解決する。主ブランチに作業が入る前に後段を開けない）。閉じられなかったものは
  `NOT_CLOSED\tT-xxx\t<理由>` の行。続けて `TRACKER`・`BACKUP` の行が付く（`TRACKER.md`「トラッカー」「バックアップ」）
- 主ブランチを出している作業ツリーで起こしたときは送る段が無く、印を消して `SHIPPED <主ブランチ>` を返す
- `bd close` の前に、送った範囲を課題の metadata `task_shipped`（`<送る前の主ブランチの先端>..<送ったコミット>`）に書く。
  `tw status` の `STALE:shipped` と振り返りの `material.py` が、記録の先端が主ブランチの祖先のときだけ、件名でなくこの範囲でコミットを引く
  （形が壊れている・先端が無い／祖先でないときは記録が無いのと同じに扱い、件名へ戻る。判定は `beads.shipped_range_on_base` の1つ）。
  送る段が無いときは `task_claim_head..HEAD`。`NOTHING` では何も送っていないので書かない。作業先が別のリポジトリのタスクは
  本体側の `ship` が `NOTHING` になるのが普通で、書かれない。1回の `ship` が複数のタスクを閉じると同じ範囲が各タスクに付く。
  記録の無い課題（この項の前に閉じたもの・`NOTHING`・別リポジトリ）は従来どおり件名の `T-xxx` で引く。`claim` が前回の記録を消す

`tw verify` が検証の前に主ブランチを取り込むので、`ship` が付け替えるのは、受け入れから送るまでの間に
主ブランチが進んだときだけ。

| 検証コマンドを打つ時点 | 誰が | なぜ |
| --- | --- | --- |
| 受け入れ（`tw done` の前） | スキル | 作業の合否そのもの。主ブランチを取り込んだあとの中身で打つ。整形（設定の `format`）もここ。委譲先が `tw verify` で控えた中身と同じなら省く（`tw verify-check`。控えは cwd の作業ツリーごとなので、別のリポジトリが作業先ならそのリポジトリの作業ツリーで打つ） |
| `ship` の中で rebase が実際に付け替えたとき | `tw` | 両側の変更が初めて同じ木に乗る |
| 主ブランチへ入れる直前（設定に `verify_before_ship` があるときだけ） | `tw` | 付け替えた回・借りがある回・控えの木とコマンドが今の中身と違う回に打ち、`SHIPPED` の行に `preship=ran` が付く。同じなら飛ばして `preship=skipped`。控えの木は `.tw/local/` を外す |
| 主ブランチへ送ったあと | 打たない | fast-forward なので、主ブランチの木は直前に検証した木と同じ |

検証コマンドについて `ship` は `tw verify` の控えを読まない（付け替えで中身が変わるので、付け替えた回は控えがあっても検証する）。
`verify_before_ship` があれば、`ship` は控えの `tree` と `verify_command` だけを今の中身と照らし（`head` は比べない。コミットで変わる）、同じなら打たない。付け替えた回は検証コマンドの代わりにこれを打つ（落ちたときの借りの扱いも `VERIFY_FAILED` と同じ）。

`VERIFY_FAILED` で終わったあとは、枝は付け替え済みのまま検証の借りが残る（作業ツリー固有の印。
`git worktree` を消すと一緒に消える）。次に打った `ship` は、その回で付け替えが起きなくても
検証コマンドを打ち直す。通れば借りは消え、以後は今までどおり付け替えた回だけ検証する。

**作業ブランチの後始末**（`branch` が `既定`／`作業ブランチを切る` で、いまの枝が `feature/T-xxx`
のとき）: 送ったあと、**`claim` した時点の枝**（印に記録）→ 主ブランチの順に移り、`feature/T-xxx` を
消す。別の作業ツリー（本体）が主ブランチを出していると主ブランチには移れないので、作業ツリー固有の枝へ
戻して主ブランチまで追い付かせる。どちらにも移れなければ主ブランチの位置で detached HEAD にする
（次の `claim` は主ブランチから切るので困らない）。**どこに降りたかは `SHIPPED` 行末の `branch=`**
（`branch=wt1-branch`／`branch=<主ブランチ>`／`branch=detached`）に出る。`kept=feature/T-xxx` が付いたら
枝を消せなかった合図で、完了報告に書いて人に預ける（消すかどうかは人が決める）。

## 段の申し送り

流れの段は、前の段の結果を会話の文脈からではなく Beads から読む。置き場は課題の comment で、
`## 申し送り: <鍵>` の1行で始まり、空行のあとに本文が続く。書くのも読むのも `tw relay`（`tw-reference.md`）で、`bd` を直に打たない。

- 書く: `tw relay T-xxx <鍵> --body-file <path|->`。書けるのは着手の印の持ち主だけ。空の本文は、その鍵を消した扱いになる
- 読む: `tw relay T-xxx <鍵>`。着手の印によらず、その鍵の最後の comment の本文を出す。無いか空なら `NONE`
- 同じ鍵は最後に書いたものが正で、前のものは comment の履歴に残る。`tw release`・`tw claim`・`tw done` では消えない。
  comment は Beads だけに置き、トラッカーには出さない（`TRACKER.md`「タスクの要素と Beads の置き場」）
- 各段は自分の鍵を、自分の段の終わりに書く。済ませた（`finished`）ときも飛ばした（`skipped`）ときも書き直し、
  飛ばしたときは飛ばしたわけを本文にする（止まったあとの呼び直しで、前の試みの値を後の段が読まないため）
- 鍵は自由な語（空・タブ・改行は不可）で、役の名で付け、スキルの名前を持たせない。並びの外の流れは自分の鍵で同じ口を使える
- 止まった段から再開するための位置も、同じ口で下の表の鍵 `再開` に置く（書く時点と消す時点は並びを進める手順が決める）

既定の並びが使う鍵:

| 鍵 | 書く段 | 本文 | 読む段 |
| --- | --- | --- | --- |
| `実装` | 実装 | 実装役の段ごとの返却の friction log・`- ドラフト:` の行と、最後の段の返却の `- 規約:` の行。委譲しない経路（近道・メインで行う）では `- 規約: 委譲なし` | 受け入れ・振り返り・送り出し |
| `受け入れ` | 受け入れ | 判定の語と、受け入れ役の最後の返却の `- 材料:`・`- 指摘:`・`- 付随:`・`- 目視:`・`- 預けること:` の行 | 振り返り・送り出し |
| `振り返り` | 振り返り | `## 結果` に入れる `- 振り返り:` の1行と、積んだドラフトの ID | 送り出し |
| `再開` | 並びを進めるオーケストレーターが、各段を呼ぶ直前 | 呼ぶ段のスキルの全名。並びの最後の段が済んだら空の本文で消す | 並びを進めるオーケストレーター（呼び直したとき） |

## 結果の書き方と知見の置き場

`## 結果` は `tw done --result-file` に渡す**3行程度**。宣言ではなく後から検証できる形で書く:

- 検証コマンドの通過件数（増減が分かる形。`1204 pass / 0 fail（+9）`）
- 生成物・検証ログへの具体的な参照、よそのリポジトリのコミットハッシュ
- 1件ごとの振り返りの印（既定の流れを通したタスク）: `- 振り返り: 兆候なし` か
  `- 振り返り: <当たった兆候・観点>（ドラフト N件: <積んだ ID, …>）`。委譲しない近道で進めたタスクは振り返りを通らないので
  `- 振り返り: 近道（省いた）`、並び（`steps`）から振り返りの段を外したタスクは `- 振り返り: 設定で外した`
  （どちらも `--reflection skipped` を打ち、`tw metrics` の `reflection_none_ratio` の分母に入らない）。**`flow/` の `reflection` は `tw done`・`tw finish` の
  `--reflection none|some|skipped` が決め、`- 振り返り:` の行は人向けの表示**（フラグが無いときだけ従来どおりこの行から読む。旧い手順と旧記録の読み）
- ドラフトから進めたタスク・ドラフトのまま閉じたタスク: 採用・却下の理由を1行（却下は `- 却下: <理由>`）
- **自分の完了のコミットのハッシュは書けない**（`## 結果` がそのコミットに入り、rebase で変わる）。
  そのタスクのコミットは `git log --grep=T-xxx` で引く

**必須行**: `tw done`・`tw finish` は、`--dropped` でなければ `## 結果` の行頭に次の行があるかを検査し、欠ければ何も書かず
欠けた行の名前を標準エラーに出して終了コード 2 で拒む（`dropped`・ドラフトの却下は検査しない）。

| 行 | 通常 | 近道（`lap direct`） | `--dropped`・ドラフトの却下 |
| --- | --- | --- | --- |
| `- 検証コマンド:` | 必須（無く、台帳の直近の `verify` が `VERIFIED`・`VERIFIED_UNSTAMPED` なら tw が件数なしで補う） | 同左 | 要らない |
| `- 規約:`・`- 規約の指摘:`・`- 振り返り:` | 必須 | 必須 | 要らない |
| `- 目視:` | 完了条件に「目視」を含むときだけ必須 | 同左 | 要らない |
| `- 預けること:`・`- 取り下げた指摘:` | あるときだけ | あるときだけ | 要らない |

台帳の `verify` の出来事は通過件数を持たないので、件数を書く行は引数のまま。

書かないこと: 設計の物語、撤回した案、手順の詳細、変更したファイルの列挙。

**知見は done の前に、正典かタスクへ置く。**

| 中身 | 置き場 |
| --- | --- |
| 何を・なぜ・どう検証したか | そのタスクの `## 結果` |
| 後の段へ渡す段の結果 | 段の申し送り（上の「段の申し送り」。`tw relay`） |
| 判断待ち | `hold` のタスク（人の判断待ち）か `todo` のタスク（直すもの） |
| 長く効く前提 | プロジェクトの正典の docs の該当節（「既知の制約」など） |
| 一時的な注意 | 関係するタスクの `## 注意`、または行き先のタスクが無ければドラフト（`tw new --draft` の課題） |

## コミットメッセージ

- タスクのコミットは**件名の先頭にタスクID**（`T-110: コミットメッセージにタスクIDを振る`）。
  1タスク＝1コミットは送り出しの段（`tw finish`）で守られる。分けられない場合だけ
  `T-105, T-108: 〜`
- **IDを持たない作業には付けない**（登録・振り返り・`hold` の切り替え・移行・typo修正）
- 過去のコミットは書き換えない。末尾の署名は、利用者の `CLAUDE.md`（グローバル・プロジェクト）に定めがあればそれに従い（署名を省く定めなら付けない）、無ければセッションの attribution の指示に従う

## ドラフトの課題

まだタスクになっていない指示の入口は、会話の明示の指示・登録の入口に渡す引数のファイル・ドラフトの課題の3つで、
指示を溜めておくファイルは持たない。ドラフトの課題（`tw status` の着手可否が `DRAFT` の行）は、エージェントが
作業中の「これも直したい」や流れの中の1件ごとの振り返りで積む（後者は `/loop` からも、材料が観点に当たり
物差しを通ったときだけ）。**対話セッションでユーザーの承認を得たものだけ**タスク化し、`/loop` からはタスク化しない。

- **ドラフトは聞かずに積んでよい。積むのは `tw new --summary '<何を変えるか>' --difficulty <見立て> --loopable <Y|N> --draft --body-file -`**
  （Beads の課題を作るだけで、作業ツリーのファイルもコミットも要らない）。`--difficulty`・`--loopable` は見立てで付け、
  承認して計画するときに `tw edit` で直す。承認の関門は「ドラフトのあいだは誰も着手しない」で保つ
  （`bd ready` に出ず、`/loop` が選ばず、`claim` が拒む。上の「status と着手の印」）
- **承認されたら** `## 完了条件`・`## やること` を `tw edit` で書き、`tw edit T-xxx --status todo`（判断待ちなら `hold`）で進める。
  進めると metadata `from_draft` に `- 観点:` の観点（無ければ `不明`）が残り、完了・却下のあとも振り返りが出自として数える。
  **却下は**理由を `- 却下: <理由（1行）>` で始めた `## 結果` にして `tw done T-xxx --dropped` で閉じる（その場で閉じ、却下の記録が課題に残る）
- 本文の書式（`## 目的・背景` だけ書けばよい。ほかの節は欠けてよい）:

  ```markdown
  ## 目的・背景

  - 出どころ: <振り返り: T-302, T-318 ／ 作業中: T-410 など>
  - 観点: <色> <観点>
  - 根拠: <材料のどこにどう出ていたか。数で言えるものは数で>
  - 出し先: <どのファイルのどの節に足すか / タスクにするなら何をするタスクか>
  ```

  `- 観点:` の行は振り返りから積むドラフトだけが持つ（色と観点の語彙は振り返りの段のスキルの `detail.md` が正典で、`taskfile.py` が検査に写し、自己テストが食い違いを見張る）。何を変えるかの1行は `--summary` に書く

- **会話入口**: チャットでの明示の指示（「これタスクにして」「それでいいよ」）を拾う。検討中の発言・
  思いつきは拾わない。迷ったら拾わない。`/loop` から回っているときは使わない
- **登録する数に上限は置かない**（`READY` が何件あっても `tw new` は拒まない）。登録から着手まで
  間が空いたタスクは主ブランチとずれうるので、登録時に書いた `## やること` が名指したファイルが
  変わったかを着手時に `tw` が判定し、変わっていれば委譲先が実装の前に書き直す
- ドラフトの課題は `todo`・`hold` へ進めるか閉じるだけで、取り除くものは無い

## Beads とトラッカー

着手の印・採番と本文・履歴を Beads（`bd` 1.3.0 で確かめた）に置き、`tw` は Beads と
トラッカーと git をつなぐ薄い包みになる。

**ID はトラッカーで決まる。** トラッカーが `github` なら **GitHub の Issue 番号がタスクID**で、`tw` の
入出力とコミットの件名は `GH-<番号>`（ゼロ埋めしない）、Beads の中は `gh-<番号>`。`なし`・`jira` なら
`tw` が採番し、外は `T-<n>`（3桁以上）、Beads の中は `t-<n>`。ただし `jira` で取り込んだ課題は
**Jira のキーがタスクID**（外は `PROJ-123`、Beads の中は `proj-123`。`TRACKER.md`「トラッカー」）。どちらの方式かは Beads の `issue_prefix`
（`gh` か `t`）で決め、`tw` は両方の形を読む（切り替えの途中は `t-<n>` と `gh-<n>` が混ざる）。
加えて **Jira のキー**（`PROJ-123`。プロジェクトキーは2文字以上・英大文字始まり `[A-Z][A-Z0-9_]+-\d+`、
Beads の中は `proj-123`）も同じ ID として読む。読む形はトラッカーで切り替えず常に3つを受け、`T-<n>`・
`GH-<n>` を先に当てるので Jira のキーとは取り違えない。`status` の並びは `T-<n>` → `GH-<n>` → Jira のキー
（キー名・番号の順）→ 仮の ID。`tw` が採番する番号（`last-id` の候補）に Jira のキーは数えない。
過去の `T-xxx`（git の履歴と旧いアーカイブ）は動かさない（[legacy.md](legacy.md)）。

**設定のキー**は `tracker`・`github_project`・`backup`（値は「ファイル配置と設定ファイル」の表）。

**トラッカーの失敗はタスクの操作を止めない。** `new`・`claim`・`release`・`edit`・`adopt`・`done`・`ship` は
`TRACKER\tFAILED\t…` の行を足して終了コードはそのままで、打ち直しは `tw sync`。

用意・タスクの要素と Beads の置き場・サイクルの各段で Beads に起きること・トラッカー（GitHub・Jira）・
Status 欄の控え・GitHub との双方向・Jira の方式との違い・バックアップは [TRACKER.md](TRACKER.md)。
タスクの要素と Beads の置き場の対応は `beads.py` の docstring にも抜粋がある。
