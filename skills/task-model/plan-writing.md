# 計画（`## やること`）の書き方

[WORKFLOW.md](WORKFLOW.md)「タスクの本文」から切り出した。`## やること` を書く・直す・点検するとき（登録の入口・委譲先・受け入れ役）に読む。
断りのない「…」の節名は WORKFLOW.md の節を指す。

**段の中身の書き方**:

- 既存のファイル・設定・控えの形を読み替える作業は、ありうる入力の状態の組み合わせ
  （例: 設定の有無 × 旧い置き場の有無 × 新しい置き場の有無）を表にし、行ごとに期待する結果と
  確かめる自己テストを書く。自己テストは、すでにあるもので確かめられる行はその名前を書き、
  新しく足すのは確かめるテストが無い行だけにする。
- 変換・写し・組み立ての関数（入力の構造を別の表記へ畳むもの。JSON Schema から文字列を組む・
  型を別の形に写す・一覧を別の一覧へ変えるなど）を作る段は、`## やること` に「入力側の要素を再帰で集め、
  出力に全部残ることを確かめる自己テスト」を含める。落ちる入力を 1 つ与えて、集めた要素が出力から欠けたら
  落ちることまで確かめる。確かめるテストがすでにあるときは、上の表の箇条と同じく名前を書く。
- 各段のあとで自己テストが通る順に段を切る。後の段の変更が無いと前の段の自己テストが落ちるなら、
  その変更を前の段に入れる。
- 口・概念・語を消すタスクは、`tw verify` の段より前に、消す語をソース・文書・テストの全体で grep して、
  名指したファイルの外に残った文を直す段を置く。
- 用語の改名を追随するタスクは、置き換えた行ごとに、旧称が指していた範囲と新しい呼び名が指す範囲が同じかを読む
  段を置く。違う行は用語集の別の語で指すか据え置き、読んだ行数と違った行数を報告に件数で書く。
- 型に必須の欄を足す・関数や口の型を変える段は、計画を書く前にその型の値を作る箇所（作り手・疑似の駆動・テストの代役やフィクスチャ）と
  呼ぶ箇所を grep で数え、その段の触るファイルと `### 名指すファイル` に入れる（数え漏れは型検査の落ちで実装中に見つかり、計画の外の変更になる）。
- 検査（lint・自己テスト・構造の規約テスト）を足す・変えるタスクの `## やること` の最初の段は、検査と同じ読み
  （構文木・import の読み）で既存の該当（検査が拒む形をしている既存の箇所）を数え、
  数えた件数を段の報告に書く。そのうち、この段で直さず検査の除外の一覧に載せる件数が、そのタスクの `## 注意` に書いた除外の上限件数を超えるなら、
  検査を入れる段より前に止めて報告する。`## 注意` に上限が無いときは止めず、上の件数を報告に書いて進む。
  登録時の単語一致の概算を、数え直した件数の代わりに使わない（単語一致は import を読む検査と数え方が違い、桁が外れて計画の段が使われずに終わる）。
- 文書の写しを畳む（重複した記述を消して正典へ寄せる）タスクは、最後の実装の段のあとに、消した行の一覧を出して
  1行ずつ残る先（正典の表の行・残した文）を対応づける段を置く。一覧は `removed_lines.py` が出す
  （作業を作業ツリーにコミットせず残すなら範囲なし、コミットを積む別の作業ツリーなら `main..<枝>`）。
  委譲先が手で数えない。完了条件に「消した行の全部に残る先を対応づけた表が報告にある
  （残る先の無い行は、消してよい理由を添える）」を入れる。
- 大きいファイルを子ファイルへ割るタスクは、移す段と、移したことで迷子になる参照を直す段を分けず、1つの段にする
  （移すだけの段では参照が迷子になり、`tw step` の step_check が落ちる。
  主ブランチが参照する側のファイルを変えたときも、同じ段でその変更を拾う）。
  対象を主ブランチが書き換えたら（`tw verify` が `CONFLICT` を返す）、対象を主ブランチの版へ戻して `tw verify` で取り込み、
  主ブランチが足した・直した行を子ファイルへ移してから、スタブを置き直す。子ファイルの名前は `report` で始めない（サブエージェントが Write できない）。
  概念の名前に照らした表に「概念を完全には表さない」「最も近い」と実装役が書いた群があれば、次の段へ進む前に、その群を別の置き場へ移すか、ファイル名を直す。
- 文書を分けて、本文の句を引く参照を子のパスへ向け直すタスクは、向け直しの段で、引いた句を向け先の子で `grep -nF` し、
  当たった行が本文の行か、冒頭・参照の一言（「（13.4「…」）」のように別の節を指すだけの行）かを、行の中身で見る。
  ほかの子にも当たる句は、どの子の本文が持ち主かを特に見る。
  文字の一致だけを見る検査は、本文として当たるかまでは見ず、冒頭の一言にしか無い句も通すため。
- 計画が新しく作るファイルの名前（`## やること`・`## 完了条件` のバッククォートで囲んだパス。大きいファイルを割る項の子ファイルもこの一例）は、
  basename を `report` で始めない。ハーネスはサブエージェントが `report` で始まる名のファイルを Write するのを拒み、
  委譲先は本文を返却に入れ、メインが置き直す往復になる。`tw new`・`tw adopt`・`tw edit`・`tw brief implementer` は、
  そういうパス（バッククォートで囲んだ、basename に `.` を含む拡張子つきのファイル名。`report`・`reportBody`・`report-chart` のような裸の語・識別子・テスト ID と、末尾が `/` のディレクトリは数えない）があれば標準エラーに `WARN_REPORT_NAME\t<パス,…>\t<理由>` を1行出す（拒まない。既存の `report*` を Edit できるかは未確認なので、存在を問わず名指しで当てる）。
  出たら名前を変えるか、そのファイルを書く段をメインが置く段にして計画に書く。
- 描画を変えるタスクは、組み立てた直後に画を撮って受け入れ役の目視待ち（`- 目視:` の判定）を受ける段を、
  E2E の期待値を撮り直す段と `tw verify` の段より前に置く。目視で確かめる完了条件の項目には、頭に印 `[目視]` を付ける
  （`tw done` が `- 目視:` を求めるのは印のある項目があるときだけ）。
- 既存の祖先要素の下へ新しい面（dialog・ポップオーバー・前後の面）を置く段は、計画の「前提の裏取り」に、祖先の CSS の規則（子孫の `:is(p, …)`・`img`・枠・角丸など）が面の中の要素に当たるかを実ブラウザの計算済みスタイル（`getComputedStyle`）で測る行を書く。
  単体は CSS を当てないので測れない。当たるなら、面を祖先の外へ出すか、面の中で打ち消す手を計画に書く。
- 本文が前提にする既存の振る舞い（「既存」「いまは〜」「GH-nnn が入れた」）は、段に書く前にコードか実行で確かめ、
  段の冒頭に「前提の裏取り」として、前提1つにつき「前提 | 確かめた場所（ファイルと関数）か打ったコマンド | 結果」を1行書く。
  食い違いが分かったら押し切らず、`## 目的・背景`・`## 決まっていること` を変える理由を報告に書いて止める（`--change-frame` は付けない）。
  不具合の直しは、症状の再現に加えて、直し方を決める原因の仮説も測って確かめた行にする。測っていない原因は結果の欄に「推測」と書き、
  その原因に頼る段は「原因が A なら…、B なら…」の分岐の形にする（推測を1つに決めて書くと、着手時に食い違ったとき直し方まで書き直しになる）。
- git の submodule を進める（gitlink を新しい版へ更新する）タスクは、計画を書く前に、進める先の版が origin にあるかを確かめ、
  「前提の裏取り」の行にする。手元の主ブランチの内容だけを見ると、origin に無い版を指す計画になる。
  確かめる手は、先に `git -C <submodule> fetch origin` で追跡参照とオブジェクトを新しくし
  （`ls-remote` は先端を表示するだけで `origin/<既定の枝>` を更新しないので、fetch せずに調べると、
  別の場所から push 済みの版を「origin に無い」と誤る）、
  `git -C <submodule> ls-remote origin` で origin の先端を読み、
  `git -C <submodule> merge-base --is-ancestor <進める先の版> origin/<既定の枝>` の終了コードを読む。
  一時のコピーで各場合を打って読んだ結果は次のとおり（`submodule update --init` は、その版を指した親を clone し直して打った）。
  - 0（既定の枝の祖先）: origin にある。`update --init` は通る。
  - 1 で、`git -C <submodule> branch -r --contains <版>` が `origin/<別の枝>` を出す: origin の既定の枝には入っていない別の枝の版。
    origin にはあるので `update --init` は通り、push も人の承認も要らない。既定の枝に入っていないことだけを裏取りの行に書く。
  - 1 で、`branch -r --contains` が何も出さない（手元の主ブランチが origin より先行している）: origin に無い。別の clone では
    オブジェクトが無く `update --init` が終了コード128で落ちる。
  - 128（`merge-base`）または 129（`branch -r --contains`）: fetch のあとも手元にオブジェクトが無い。origin に無い。`update --init` が落ちる。
  なお fetch の前は、別の場所から push 済みの版も 128 になるので、必ず fetch のあとに読む。
  origin に無いときだけ push が要り、push は人の承認を要する操作なので、承認の範囲を本文に書けるなら `loopable` は `Y` のまま、
  書けないなら `## 注意` の `### 人がやること` に分けるか `loopable` を `N` にする（`loopable` の表の「承認の範囲外の外部への反映」）。

**登録時に書く `## やること`**（`tw new`・`tw adopt`）は、段のほかに小見出し
`### 名指すファイル` を1つ置き、計画が前提にするファイルを1行1つ `` - `パス` ``（後ろに説明を書いてよい）で並べる。
パスはリポジトリの根からの相対で、登録時の主ブランチの木にあるファイルかディレクトリに限る（新しく作るファイルは
置くディレクトリを名指す）。作業先が別のリポジトリなら、小見出し `### 作業先` を1つ置いてそのリポジトリの根の
絶対パスを1行 `` - `パス` `` で書く（`~` は展開して書く）。そのとき名指すファイルは作業先の根からの相対で、
検査・SHA の控え・着手時の判定は作業先のリポジトリ（の主ブランチ）で行う。
`tw edit` で `## やること` を書き直すとき（`--section 'やること'` でも本文ごとでも）、書き直し前にあった `### 作業先`・`### 名指すファイル` が
新しい本文に無ければ、落とした見出しを理由に終了コード2で拒む。理由は見出しごとの影響を言う:
`### 作業先` が落ちると `tw accept` が作業先を引けず `NO_RANGE` になり、`### 名指すファイル` が落ちると `tw claim` の `plan-check` が
名指したファイルの変わりを判定できず `unreadable`（古い計画）になる。書き直し前に無い節は見ない。
`tw new`・`tw adopt` は `HEAD` と主ブランチの分かれ目の SHA を控え、`tw claim` がその SHA から着手時の主ブランチの先端までに
名指したファイルが変わったかを判定する（`tw plan-check` の `PLAN_REGISTERED`・`PLAN_STALE`）。
変わっていれば、委譲先が実装の前に調べ直して書き直す。

名指したファイルが変わっていても、次の4つがすべて成り立てば古くない（`PLAN_REGISTERED` のまま。`tw claim` は印に `registered` を残す）:
段が `- 満たす完了条件:` の欄を持つ（欄の無い旧い計画は従来どおり変わっただけで古い）・欄が `## 完了条件` を覆っている（`PLAN_UNCOVERED` が出ない）・
名指したパスが主ブランチの先端の木に残っている・控えた SHA から先端までの差分（`git diff -U0`）の追加・削除行に、段の本文のバッククォートで囲んだ識別子が1つも出ない
（識別子は4字以上で `/` と空白を含まず、名指すパスと同じでない語。`### 名指すファイル`・`### 作業先` の節は読まない）。
外れれば `PLAN_STALE\tT-xxx\t<変わったファイル>\t<理由>`。理由は `legacy`（欄の無い旧い計画）・`uncovered`・`path-missing`・`no-identifier`（本文に識別子が1つも無い）・
`touched:<語,…>`（差分に出た識別子）・`unreadable`（作業先・SHA・差分が読めない。バイナリやモードだけの変更で差分に追加・削除の行が出ないときも）。疑わしいときは古いほうに倒す。
「その段で本当に満たされるか」は機械が見ず、人（メインか委譲先）の判断として残る。

**登録時の `## 決まっていること（蒸し返さない）` の裏取り**: 項目が挙動・数え方（「〜すれば〜になる」「〜を除いて数える」など）を
言い切るときは、登録の前に実物（コード・文面・1回の実行）で通ることを確かめ、根拠を項目の後ろに1行添える
（ファイルと関数、または打ったコマンドと結果）。聞いて決まっただけの方針や承認の範囲には要らない。
`tw new` の本文検査（`taskfile.validate_new_body`）は枠・段・名指すファイルの形だけを見て、この節の項目に決まった書式は無い。
言い切りかどうかは文面から機械で決められず、根拠の行を一律に求めると聞いて決まっただけの項目にも要るので、検査には足さない。

**手順を書く文書の変更の計画に順の確かめの段を求める検査**: `tw plan-check`（`tw_edit._print_plan_check`）は印・段の見出しと欄（`- 前の段:`・`- 触るファイル:`）の形・名指すファイルの変わりだけを見て、段の本文の文は読まない（`taskfile.plan_step_specs`）。
計画が機械に渡す欄は `- 前の段:`・`- 触るファイル:` の 2 つだけで、手順を書く文書を直す計画かを示す欄も印も無く、名指すファイルのパスからも手順を書く文書とそれ以外の文書を分けられない。段の文面の判定は自由記述の解釈になるので、`plan-check` には足さず、実装役の決まり（`implementer-brief.md`）に置く。
同じ理由で、検査を置き換える・足す段が弱めた実装で落ちる確認を求めているか（段が自己テストを求めているかは本文の解釈になる）、計画が頼る印・値・イベントを実機で確かめたか（「前提の裏取り」の行は書式の決まった欄ではなく、2列目が読んだ場所か打ったコマンドかは本文の解釈になる）も見ない（決まりは `implementer-brief.md` の「作業の作法」）。
