## `tw` コマンドの参照

`tw <サブコマンド>` で打つ。`tw` は plugin の `bin/tw`（plugin が有効なあいだ Bash の PATH に入る。端末で人が打つときは README の wrapper）で、ロジックは持たず `scripts/tw/task.py` を呼ぶ。
PATH に無ければ plugin を入れる。どのディレクトリから打ってもリポジトリの根で動く。
出力は常に stdout の TSV で、1行目の先頭語が種類。
表は「いつ打つか」と出力の先頭語だけを持ち、引数・内部の動き・例外・出力の列は `tw <サブコマンド> --help` が持つ。

| サブコマンド | すること | 主な出力 |
| --- | --- | --- |
| `status [--all] [--check]` | 一覧と判定を読むだけで見るとき（`--check` は課題の形の判定） | 行 `id/status/…`、`---` の後に `counts`・`ready`・`todo_loopable`・`stale`・`invalid`・`triage`・`CANDIDATE`（候補のドラフト。行と `counts` には出さない）・`jira_close`・`retrospect_due`。`--check` は `OK`・`INVALID` |
| `status --claims` | この作業ツリーが着手の印を持つタスクの ID・最後の段・着手の鍵を、呼び手が表の文字列を割らずに読むとき（読むだけ。`--claims` を付けると一覧の旗は読まない） | 1行の JSON（TSV の例外）`{"claims": [{"task", "stage", "claim"}, …]}`。着手なしは `{"claims": []}`、2件以上なら全部。`task` は表示のタスクID、`stage` は最後の `claim` 以降の最後の `lap` の段（無ければ `null`）、`claim` は Beads の `started_at`（`claim` のたびに変わるので、`release` して `claim` し直すと別の値になる） |
| `new --summary … --difficulty … --loopable Y\|N [--deps …] [--hold\|--draft] [--candidate <SIGNAL の種類> <場所>] [--direct] [--kind <種類>] [--fixes <ID,…>] --body-file <path\|->` | タスクやドラフトを登録するとき（`--candidate` は黄1件のドラフトを候補で積み、同じ観点・SIGNAL の種類・場所の候補が28日以内にあれば課題を作らずにその候補を承認の列へ上げる〔WORKFLOW.md「ドラフトの課題」〕。`--draft` が無い・色が黄でなければ終了コード2。`--fixes` は直しが結ぶ送り出し済みの元のタスクを metadata `fixes` に置き、存在しない・形の違うIDは終了コード2。`opus` で `## 解くべき論点` が空か「なし」、ドラフトの `- 観点:` が語彙の外なら終了コード2。`- 観点:` の行を持つ本文と、`### 名指すファイル` が harness の面に当たる計画〔`--draft` を除く〕で `## 介入` が無いか形が違っても終了コード2〔WORKFLOW.md「タスクの本文」の「介入の節」〕。`adopt` も論点と `## 介入` は同じ。`--hold`（`--batch` の `hold` も）は `## 解除の条件` が無い・空・「なし」・4行以上なら終了コード2。計画の警告 `WARN_REPORT_NAME`・`WARN_LARGE_PLAN\t<ID>\t<理由>` は書き込みのあと標準エラーに出し、拒まず終了コードも変えない〔plan-writing.md「段の中身の書き方」・「登録時に書く `## やること`」〕） | `CREATED`・`PROMOTED`・`LOCKED` |
| `new --batch <JSON のパス>` | 複数件をまとめて登録するとき（単件の引数〔`--summary` など〕とは同時に使えず、打てば終了コード2）。JSON は要素の配列で、要素は `summary`・`difficulty`・`loopable`・`body_file`〔JSON のあるディレクトリからの相対か絶対。`-` は不可〕と、あれば `deps`・`fixes`〔文字列の配列〕・`hold`・`direct`・`kind`。`deps` には既存のIDと、同じ配列の前の要素を指す `@<n>`〔1始まり〕を混ぜてよい。先に全要素を単件の `new` と同じ検査にかけ、1つでも落ちれば何も作らず終了コード2（標準エラーに何件目か）。通れば順に作り、トラッカーへの反映は最後に1回だけ行う（`github` では Issue を立てる・`gh-<Issue 番号>` へ付け替える・Status 欄を書くのを全件まとめて行う）。作る途中で失敗したら、作った分は残して反映し、続きは作らず `NOT_CREATED\t@<n>\t<題>` を出して終了コード4。`--draft`・`--candidate` は使えない | 要素ごとの `CREATED`・`TRACKER`（1回）・`NOT_CREATED` |
| `claim T-xxx` | 作業を始めるとき（着手の印を立て、git の hook `ref-guard` を置く。置けなければ標準エラーに `ref-guard:` の1行。作業先が別のリポジトリなら、その本体の汚れたパスを控える。控えられなければ標準エラーに `main-dirty:` の1行） | `CLAIMED`・`TAKEN`・`NOT_READY`・`DIRTY`・`UNSHIPPED`・`GIT_READ_ONLY` |
| `release T-xxx [--force]` | 着手の印を外すとき（GitHub へ押し出さず、次の `sync` が送る） | `RELEASED`・`NOT_CLAIMED`・`NOT_OWNER` |
| `hold T-xxx --reason-file <path\|-> [--unlock-file <path\|->]` | 判断待ちのタスクを外すとき（自分の着手中なら印も外し、`hold` にして `## 注意` の最後に論点を足し、台帳に `hold` を1行足す。todo・すでに `hold` にも打てる。`--unlock-file` は `## 解除の条件` を置き換え、省けばいまの節を使う。書いたあとの節が無い・空・「なし」・4行以上なら何も書かず終了コード2。両方 `-` 不可。GitHub へ押し出さない） | `RELEASED`（外したとき）に続けて `HELD`・`CONTINUE\tY\|N\t<READY かつ loopable: Y の件数>`・`NOT_OWNER`・`NOT_READY` |
| `done T-xxx [--dropped] [--reflection none\|some\|skipped] --result-file <path\|->` | 結果を書いて作業を閉じるとき（コミットも送りもしない）。ドラフトの却下にも使う。`--dropped` でなければ `## 結果` に必須行（`- 検証コマンド:`・`- 規約:`・`- 規約の指摘:`・`- 振り返り:`、完了条件の項目の頭に印 `[目視]` があれば `- 目視:`）が要り、欠ければ終了コード 2 で何も書かない（`- 検証コマンド:` だけは、台帳の直近の `verify` が通っていれば件数なしで tw が補う。`finish` も同じ） | `DONE`（`REPLAY_DIFF_MISSING`・`COMMITS_SINCE_CLAIM` が続くことがある。前者は `## 介入` の `- タスクの再試の差:` の行を見る。古い名前 `- 再演の差:` も同じに読む）・`NOT_OWNER`・`NOT_READY`・`ALREADY_DONE\tT-xxx\t<done\|dropped>`（`done` 済みの再実行。終了コード4。何も書かない）・`INVALID` |
| `ship` | コミットを主ブランチへ送るとき（rebase・検証・ff-only・送った範囲を metadata `task_shipped` に書いて印を閉じる・トラッカーへ送る） | `SHIPPED`・`NOTHING`（`NOT_CLOSED`・`TRACKER`・`BACKUP`・`SUBMODULE_NOT_SYNCED` が続くことがある）・`MAIN_DIRTY`・`CONFLICT`・`VERIFY_FAILED`・`RACE`・`GIT_READ_ONLY` |
| `land <枝> [--fold]` | 作業先が別のリポジトリのタスクの受け入れで、その枝を主ブランチへ ff で合流し、作業ツリーと枝を消すとき。`--fold` は合流の前に、枝の作業ツリーで主ブランチをマージコミットで取り込み（サブモジュールも取り込んだ版へ揃える）、検証を多くて1回打つ（取り込みが要らず控えが今の中身と同じなら省く） | `--fold` のときは先に `FOLDED`・`VERIFIED_SAME …verify=skipped`／`verify` の判定行・`CONFLICT`・`SUBMODULE_NOT_SYNCED`（`NOT_LANDED` が続く）。続けて `LANDED`（`SUBMODULE_NOT_SYNCED`・`REMOVED`・`DELETED` が続く）・`NOT_REMOVED`・`NOT_LANDED`・`GIT_READ_ONLY` |
| `show T-xxx` | 読むだけで見るとき | 日時つき本文。無ければ `NOT_READY` |
| `find [<語>…] [--kind <種類>]` | ID の無い頼み文の語と種類で `READY` を1件に絞るとき（読むだけ。当て方は WORKFLOW.md「kind（種類）」） | `FOUND`・`MANY`（`CANDIDATE`・`MORE` が続く）・`NONE`（どれも終了コード0） |
| `edit T-xxx [--body-file <path\|->] [--section <節名>]（組は繰り返せる） [--after-work] [--change-frame] [--summary …] [--difficulty …] [--loopable Y\|N] [--status todo\|hold] [--add-deps …] [--remove-deps …] [--direct Y\|N] [--kind <種類>\|-]` | 本文・属性・依存を直すとき（`--section` で節だけ。`--section`・`--body-file` の組を繰り返すと複数の節が1回で書ける。ドラフトを `todo` に進めるのも `--status`。変えた節だけを見て、`opus` に上げる編集か論点を変える編集で `## 解くべき論点` が空か「なし」、`## 目的・背景` を変える編集で `- 観点:` が語彙の外、`## 介入` を変える編集で節の形が違えば終了コード2。`## やること` を書き直す編集で、書き直し前にあった `### 作業先`・`### 名指すファイル` が新しい本文に無ければ終了コード2。`--section '介入'` は節が無ければ `## 参考情報` の後ろに足す。自分の着手中の `loopable: Y` への `--loopable N` は、ほかの旗ごと書かずに終了コード2で `tw hold` を案内する。ドラフトを進めるときは `new` と同じ検査で、`## 介入` が要るのに無ければ `NOT_READY`。`--status hold` は `## 解除の条件` が無ければ終了コード2） | `EDITED`（`PLAN_AFTER_WORK`・`DIRECT_OFF` が続くことがある。`## やること`・`## 完了条件` を変えて basename が `report` で始まるパスが入れば標準エラーに `WARN_REPORT_NAME\t<パス,…>\t<理由>`。書き込みも終了コードも変えない）・`NOT_READY`・`WORK_BEFORE_PLAN`・`FRAME_CHANGED` |
| `adopt <ID> --difficulty … --loopable … [--summary …] [--direct] [--kind <種類>] --body-file …` | 振り分け前の課題をタスクにするとき | `ADOPTED`（`new` と同じく標準エラーに `WARN_REPORT_NAME`・`WARN_LARGE_PLAN`） |
| `sync` | トラッカーと同期するとき | `TRACKER\tOK\|FAILED`・`NOTHING`・`BUSY`（終了コード5） |
| `backup` | Beads のバックアップを取るとき | `BACKUP\tOK\|FAILED` |
| `jira-closed T-xxx…` | `jira:close` を外すとき | `CLEARED` |
| `plan-check T-xxx` | `## やること` を作業より先に書いたかを読むだけで確かめるとき（受け入れと返却の前） | `PLAN_FIRST`・`PLAN_REGISTERED`・`PLAN_NOT_FIRST\t…\t<理由>`・`PLAN_STALE\tT-xxx\t<変わったファイル>\t<理由>`（理由は `legacy`・`uncovered`・`path-missing`・`no-identifier`・`touched:<語,…>`・`unreadable`。どれも終了コード0）、段が `- 満たす完了条件:` の欄で完了条件を覆わなければ続けて `PLAN_UNCOVERED\tT-xxx\t<n,…>`、並列の計画では続けて `PARALLEL`・`SERIAL`・`STEP`。字数表の文書は `DOC_BUDGET\t…\t<文書>\t<残り>\t<上限>`。`NOT_OWNER` |
| `plan-phases T-xxx [--through <段>] [--also <n,…>] [--skipped <段,…>]` | tsukumo の `work_plan` に渡す段の並びと位置を読むだけで出すとき（実装のあとの段は `steps` の並びの2つ目以降のスキルから組む。既定の並びなら「受け入れ」「振り返り」「送り出し」。`--skipped` は飛ばした段で、出力の `skippedPhases` に入る。使い方はオーケストレーターの「進み具合の帯（`work_plan`）」） | `PHASES\tT-xxx\t<JSON 1行>`。`NO_PHASE`（終了コード2）・`NOT_OWNER` |
| `verify [T-xxx]` | 検証コマンドを打つとき（主ブランチの取り込み・整形・中身の鍵の控えも担う。ID は基本付けない） | `FOLDED`（取り込んだとき先頭）・`VERIFIED`・`VERIFIED_UNSTAMPED`・`VERIFY_NOT_PASSED`・`FORMAT_FAILED`・`PLAN_MISSING`・`CONFLICT`・`GIT_READ_ONLY`・`NOTHING`。末尾40行のあとに判定行をもう一度出すので、`tail` で切っても最後の行（取り込んだときは最後の2行）で判定が取れる。task-model の自己テストは単独で約 6 分かかる。前景の上限（Bash 1回あたり 600 秒）を超えると背景に回るので、判定行が出るまで待ってから返す（待つあいだ別の `tw verify` を打たない） |
| `verify-check` | 中身が `verify` の控えと同じかを読むだけで見るとき（同じなら検証を省く） | `VERIFIED_SAME`・`NOT_VERIFIED\t<理由>`（終了コード0）・`NOTHING` |
| `accept T-xxx [--after-review]` | 受け入れの機械的な並び（機械的な判定と `verify-check`）を打つとき。判定の `REVIEW\tcode` は、差分に文書の拡張子でないパス、または設定 `review_code_globs`（WORKFLOW.md の設定の表）の glob に当たるパスがあるとき。全部文書なら `SKIP\tdocs-only`。テストの削除・skip・`expected/` だけの差分は判定の行のあとに `MARK\t<種類>\t<パス>` を足す（止めない。受け入れ役の依頼文へ印として渡す）。段が2つ以上の計画で途中の段の控えが欠ければ、lap の前に `NOT_LAST_STEP` で止まる（`loopable: N` は見ない）。作業先が別のリポジトリなら、判定（主ブランチから枝までの範囲つき）・木の控え・`verify-check` を作業先の作業ツリーで打ち、整形は打たず、作業先の本体の汚れを `claim` の控えと比べて `MAIN_DIRTY_*` の行で出す（読み方はオーケストレーターの、作業先が別のリポジトリのときの手順） | `REVIEW`・`SKIP`・`NOTHING`・`NO_RANGE`・`MARK`・`SNAPSHOT`・`FORMATTED`・`FORMAT_FAILED`・`NOT_LAST_STEP`・`MAIN_DIRTY_FROM_DELEGATE`・`MAIN_DIRTY_UNKNOWN`・`MAIN_DIRTY_BEFORE`・`MISSING`・`INVALID`・`NOT_CLAIMED`・`NOT_OWNER` |
| `brief implementer T-xxx [--step <n>] [--rewrite] [--visual]`（実装役）・`brief acceptor T-xxx [--accept-file <path\|->] [--image <パス>]… [--visual] [--visual-wait] [--round <n> --since <前の木>]`（受け入れ役） | 実装役・受け入れ役への依頼文を手で組まずに出すとき（メインが打ち、出力の2行目以降をそのまま渡す）。文面は並びのスキルの `metadata` の `workflow-brief-<役>` が指す型にあり、tw は場合（計画どおり・書き直し・別のリポジトリ・並列の段・目視、受け入れ役は判定・目視待ち・2回目以降）に当たる節を選んで、パス・枝・作業ツリーの道を埋める（節と値は `tw brief --help`）。目視はタスクの本文の語では決めず、`--visual`・`--image` の旗だけで決める | `BRIEF\tT-xxx\t<役>\t<節,…>`（受け入れ役の `--round` は末尾にいまの木）に続けて依頼文。実装役は計画に basename が `report` で始まるパスがあれば、標準エラーに `WARN_REPORT_NAME`（標準出力は変えない）。`NOT_OWNER`・`MISSING`（終了コード6）・`INVALID`（終了コード3） |
| `finish T-xxx [--dropped] [--reflection none\|some\|skipped] --result-file <path\|-> --message <本文> [--add <ファイル>]… [--resume]` | 結果・コミット・送りを一度に打つとき（`done` → `git add` → コミット → `ship`）。件名の `T-xxx:` は tw が一度だけ付ける（`--message` は本文のみ。旧形式も二重にならない）。`--add` を省くと、作業ツリーの変更のうち通常のファイル（`.tw/local`・symlink・サブモジュール〔索引に載った分は戻す〕と、その `.gitmodules` は除く。入れたいときは `--add`）を個別に `git add` する（`git add -A` は打たない）。`--resume` は `done` 済みの自分の着手のタスクで `done` を飛ばし、`RESUMED` を出してコミット→`ship` だけ行う（`--result-file` は省ける） | `done` の行、`RESUMED`、`SKIPPED\t<パス>\t<symlink|submodule>`（省略時に除いたもの）、`COMMITTED`・`NO_COMMIT`、`WARN_FIX_LINK\t<ID>`（件名・本文が直近7日に送った ID を含むか、「戻す」「撤去」「revert」の件名の戻し先がその ID。警告のみ）、`UNADDED\t<パス>`（残った変更。残れば `ship` が `DIRTY`）、`ship` の行。`COMMITS_SINCE_CLAIM` が出れば終了コード12で止まる。`done` 済みに `--resume` なしで打てば `ALREADY_DONE`（終了コード4） |
| `metrics [--days N] [--stages]` | 流れの数と段ごとの所要時間を読むだけで見るとき（振り返り） | `PERIOD`、続けて `shipped`・`lead_median_seconds`・`verify_per_task` など。落ちた `verify` の内訳は `verify_real`・`verify_flaky`（次の着手までに同じ木で通った落ち）・`verify_infra`（検証コマンドの終了コードが 2。E2E の回数の上限）で、和が `verify_failed`。`verify_unobserved`・`_blocked`も。`fix_within_7d` は、期間内の `SHIPPED` の件数に対する、送り出しから7日以内に `tw new --fixes` で結ばれた直しのタスクの数（`NN% (n/m)`）。`--stages` は先頭に `OPEN_TOTAL`（5超で `INTEGRITY\tWARN\t<内訳>`）、続けて `STAGE`・`OPEN`。`SKIPPED`・`EMPTY` |
| `config` | 解けた設定を読むだけで見るとき | `CONFIG`、続けて `<キー>\t<値>\t<config\|default>`（`steps` の値は詰めた JSON の配列）。設定が無ければ `MISSING`（終了コード6） |
| `config --json` | 解けた設定を JSON で読むとき（`config` と同じキー・値・出どころ） | 1行の JSON（TSV の例外）`{"config": "<パス>", "keys": [{"key", "value", "source"}, …]}`。`steps`・`review_code_globs` の `value` は配列。`MISSING`（終了コード6）・`INVALID`（終了コード3）は JSON にせず `config` と同じ行。`--schema`・`set` とは一緒に打てない（終了コード2） |
| `config --schema` | 設定の欄の形（並び `steps` の既定と候補、`shell_write_guard` の選択肢）を読むだけで見るとき（設定画面が欄を描く口。設定にはよらない） | 1行の JSON（TSV の例外）`{"schema": 2, "keys": [...]}`。`values[]` は `{value, label, title, description}` で、`title` は日本語の段の名前（SKILL.md の `metadata` の `workflow-step-title`。無ければ `label` と同じ） |

### hook の関門

hook 4種（Claude Code の hook 3種と git の hook `ref-guard`）の仕様の正典はこの節。判定の細部（何をコミット・書き換えとみなすか、通す書き方、読む控えの順）は `tw commit-guard --help`・`tw handback-guard --help`・`tw ask-guard --help`・`tw ref-guard --help` が持つ。同じ `hooks/hooks.json` から呼ぶ `lap-hook`（下の lap の段落）と `heartbeat`（委譲先の鼓動 `.tw/local/task-agent-beats/<agent_id>` を書く。`bin/tw-hook`）は拒まない記録で、関門に数えない。

| hook | 掛かる場面 | 拒むもの | 拒まれた側の次の一手 |
| --- | --- | --- | --- |
| `commit-guard` | 着手の印（`.tw/local/task-open-claims/T-xxx`）が立ってから `done` を打つまでの作業ツリーで、サブエージェント（入力に `agent_id` がある。名前は問わない）の Bash | コミットを作る git のサブコマンド（その作業ツリーで `ref-guard` が効いていないときだけ。効いていれば git の hook に任せる）・`ref-guard` を外す書き方のコマンド（`TW_REF_GUARD_ALLOW=`・`export TW_REF_GUARD_ALLOW`・`core.hooksPath` を書き換える形。読むだけのコマンドは通す。形は下の「掛かる口」の段落）・シェルでのファイルの書き換え（設定 `shell_write_guard = "project"` なら見ない）・設定の検証コマンドの直打ち（段を流さない読むだけの旗 `--plan`・`--help`・`-h` を含む打ち方は通す）。タスクの `### 作業先` が別のリポジトリなら、作業先の作業ツリー（枝の名前がタスクIDの小文字）での書き換えと検証コマンドの直打ちも拒む（そこでのコミットは拒まない）。さらに委譲先には、`git stash`（`list`・`show`・`--help` は通す）・`git add -A`/`--all`/`.`（`--` の後ろの `-A` はファイル名として通す。`-n`/`--dry-run` も通す）・`git push`（`-n`/`--dry-run` を除く）・`git worktree remove|prune`・`git branch -d|-D|--delete` を拒む（`tw land`・`tw ship` は Python から git を打つので Bash の hook を通らず、この拒否の対象外）。書き込みの `bd`（`update`・`close`・`create`・`reclaim`・`unclaim`・`reopen`・`delete`・`label`・`dep add\|remove`・`kv set\|clear`・`config set` など。`show`・`list`・`ready`・`kv get`・`dep list`・`--readonly` 付きは通す）は、主のセッションにも拒む（コマンドに `bd` の語があるときだけ解析する）。受け入れ役（`agent_type` の最後の `:` より後ろが受け入れ役のエージェント名、または手で付ける `--acceptor`）には、`tw` を打つ単純コマンドと検証コマンドの直打ちを拒む（`tw verify` は案内しない）。判定は書き方の文字列で、`sh -c '…'` の中は見ない | 回避しない。書き換えは `Edit`・`Write` で、検証は `tw verify` で打つ。コミットはせず、変更を作業ツリーに残して返す。`stash` の代わりは `git show HEAD:<path>`、片付けは `tw land`、Beads の書き込みは `tw` が打つ。受け入れ役は出力を読んで判定だけを返す |
| `handback-guard` | 同じ作業ツリーで、その中かタスクの作業先の中へ `Edit`・`Write`・`NotebookEdit` を使ったサブエージェント（名前は問わない。外への書き込みは印を残さない。印は `agent_id` ごとの `.tw/local/task-agent-writers/<agent_id>` に残り、着手の控えが無くなると消える）の返却（`SubagentStop` と、`PreToolUse` の `SubagentHandback`）。受け入れ役の返却には掛からない | 作業（着手より後のコミットか、タスクのファイル以外の変更）があるのに、`plan-check` が `PLAN_FIRST`・`PLAN_REGISTERED` でないか、`verify-check` が `VERIFIED_SAME` でない返却。段が2つ以上の計画で `tw step` の控えが1つも無い返却（作業先の作業ツリーの判定では、着手した作業ツリーの段の控えも数える）。作業の無い返却（前提が誤り・`dropped`・計画だけの回）は通す。作業先が別のリポジトリなら、枝の名前がタスクIDの小文字の作業先の作業ツリーにも同じ判定を当てる（作業先で `tw verify` が `MISSING`・`INVALID` を返すか、設定に検証コマンドが無ければ検証を求めずに通す）。最後の段の返却の本文（`SubagentHandback`）の `## 構造の変更` の節の欠けは拒まず `additionalContext` で知らせる（`hook-rationale.md`） | 理由に従って直してから返す（`NOT_VERIFIED` で `tw verify` が背景に回っているなら完了まで待つ。計画は `tw edit`、検証は `tw verify`、途中の段は `tw step`、止める返却は `tw pause`）。`NOT_VERIFIED scheme <パス>` なら、第3列（照らした側のチェックアウトの `tw_verify.py` のパス）のチェックアウトの `bin/tw`（またはそこへ解決される PATH の `tw`）で `tw verify` を打ち直す |

| `ref-guard`（git の `reference-transaction`） | 着手の印が立ってから `done`・`release`・`ship` で控えが消えるまでの作業ツリーで打たれた git の参照の更新。呼び手（主のセッションかサブエージェントか）もシェルの書き方（`sh -c`・スクリプト越し・`--no-verify`）も問わない | `HEAD` か今の枝を、主ブランチの祖先でないコミットへ動かす更新（`commit`・`commit --amend`・`merge`・`cherry-pick`・`rebase`・`reset` など）。`tw` 自身の git（`ship`・`verify` の取り込み・`claim` の枝切り・`finish` のコミット）は変数 `TW_REF_GUARD_ALLOW` を付けるので拒まない。控えの無い作業ツリー・ほかの枝の更新・主ブランチへの早送り・同じコミットへの更新（`stash` など）は通す | 回避しない。コミットはせず、変更を作業ツリーに残して返す。メインは `tw finish`（`done` で控えを消してからコミットする）で送る。控えがあるうちにメインが `tw` を通さずにどうしてもコミットするときだけ、`TW_REF_GUARD_ALLOW=1` を付けて打つ |

**拒否の記録**: 4つの関門が拒むたびに、共有の git dir の `hook-denials/<年-月>.jsonl` へ `{at, hook, rule, actor}` の1行を足す（tsukumo の `hook-denial-record.ts` と同じ形。`hook` は `tw-commit-guard` など、`rule` は `GIT_COMMIT`・`DISARM_REF_GUARD`・`GIT_STASH`・`GIT_ADD_ALL`・`GIT_PUSH`・`GIT_WORKTREE_REMOVE`・`GIT_BRANCH_DELETE`・`BD_WRITE`・`ACCEPTOR_TW`・`SHELL_WRITE`・`DIRECT_VERIFY`・`PLAN_OR_VERIFY_MISSING`・`STRUCTURE_SECTION_{MISSING,EMPTY,NO_MARK,OTHER}`・`LOOPABLE_ASK`・`MOVE_REF`、`actor` は `agent_id` の有無で `subagent`・`main`。`ref-guard` は常に `main`）。`subagent` の行にだけ `agent`（その `agent_id`。トランスクリプト `agent-<agent_id>.jsonl` と同じ名前で、振り返りの `material.py` がそのトランスクリプトのエラーから引く）を足す。`STRUCTURE_SECTION_*` は通した返却の行で `mode: "log-only"` を持つ。コマンド・パス・会話は入れず、書けなくても関門の出力と終了コードは変えない。

**掛かる口**: plugin で入れると、`hooks/hooks.json` が exec 形で殻 `${CLAUDE_PLUGIN_ROOT}/bin/tw-hook` を呼び、殻が `bin/tw` を呼ぶ。
`commit-guard`・`handback-guard` は `--agent-scoped` 付きで、入力に `agent_id` があるときだけ掛かる（`agent_type` は `--agent` で起こした主のセッションにも入るので見ない）。例外が2つあり、`commit-guard` は `agent_id` が無い主のセッションでも書き込みの `bd` だけは判定し（コマンドに `bd` の語が無ければ解析しない）、`agent_id` があるときは `agent_type` が受け入れ役のエージェント名で終わるなら受け入れ役の規則を足す（この `agent_type` が PreToolUse の入力に入るかは実物で確かめていない。`SubagentStart` の `agent_type` は `lap-hook` が使っている）。`handback-guard` は `Edit`・`Write`・`NotebookEdit` の `PreToolUse` でも呼ばれ、書いた印を残す。`commit-guard` は、入力に `agent_id`・`session_id` があり `cwd` の作業ツリーの着手の控えがちょうど1件なら、拒否の判定とは別に、台帳の `flow/` へ `agent` の出来事（`agent`・`session`）を最初の1回だけ足す（`WORKFLOW.md`「ファイル配置と設定ファイル」）。`ask-guard` は付けずに呼び、主のセッションにも掛かる。`lap-hook` も付けずに `SubagentStart`・`SubagentStop`（matcher で実装役・受け入れ役に絞る）と matcher `Skill` の `PreToolUse` で呼ばれる（下の lap の段落）。
導入は plugin の 1 経路だけ（GH-771 で決めた）。関門は `hooks/hooks.json` だけが掛け、エージェント定義の frontmatter に `hooks` は置かない。
`ref-guard` は `tw claim` が共有の git dir の `hooks/reference-transaction` に置く薄い殻で、全作業ツリーに1つ。控えの無い作業ツリーでは何もしないので、`done`・`ship` では消さない（消してよい。次の `claim` が置き直す）。
`commit-guard` は打つたびに `ref-guard` が効くかを確かめ（`ref_guard.inactive_reason`）、効かなければコミットを自分の文字列の判定で拒む。
効かない場面は次のすべてで、`tw claim` も置いたあとに同じ判定をして、効かなければ標準エラーに `ref-guard:` の1行を出す:
`core.hooksPath` がある・共有の hooks の `reference-transaction` が無い・印の無い利用者の hook である・殻がこの `tw` の `task.py` を指していない（指す `task.py` が無い・別のチェックアウトを指す）・殻が実行できない・git が 2.28 より古いか版が読めない・`python3` が PATH に無い・環境に `TW_REF_GUARD_ALLOW` がある。
このとき `sh -c`・スクリプト越しのコミットは、`commit-guard` の文字列の判定でも拾えない。
効いていても、コマンドの文字列に見える hook を外す書き方は `commit-guard` が拒む（`sh -c '…'` の中も見る）:
`TW_REF_GUARD_ALLOW=`・`export TW_REF_GUARD_ALLOW`・`-c core.hooksPath=…`・`--config-env=core.hooksPath=…`・`GIT_CONFIG_KEY_<n>=core.hooksPath`・`GIT_CONFIG_PARAMETERS` に `core.hooksPath` を含む代入・値を渡す `git config [<旗>] core.hooksPath <値>`（`set` を含む）。
`hooksPath` を読むだけのコマンド（`grep`・`rg`・`git config --get`・`get`・`--list`・値を渡さない `git config core.hooksPath`）と、既定に戻す `git config --unset core.hooksPath` は通す。
スクリプトの中で外した git・`git -C <控えの無い作業ツリー>`・今の枝でない参照の `update-ref` は拒まない。
これらと、`Edit`・`Write`・`NotebookEdit` を使わずに書き換えたサブエージェントの返却は、`finish`・`done` の `COMMITS_SINCE_CLAIM` と受け入れの `plan-check`・`verify-check` が事後に拾う。

**lap は並びのスキルではなく、オーケストレーターと `tw` と hook が段の前後で書く**（段の名前は `direct`・`delegate`・`accept`・`review`・`retro`・`land`・`sync` で固定）。`ask-guard` はこの段で境を決め、誰が書いたかも並びのスキルの名前も見ない。

| 段 | start を書くもの | end を書くもの |
| --- | --- | --- |
| `direct` | メイン（`tw lap`。端なし） | — |
| `delegate` | `lap-hook`（委譲先の起動）。委譲しないメインの流れはメイン。委譲先のモデルが `difficulty` と違う分業と、そこから戻す引き上げでは、メインが委譲の直前に `--model` 付きで打つ（hook はモデルを知らず、開いた段には書かない） | `accept` の start（`tw accept` が打つものも手で打つものも） |
| `accept` | `tw accept`（作業先が別のリポジトリのタスクも） | `tw accept`（開いているときだけ書くので、`--after-review` を打ち直しても1つ） |
| `review` | 1回目は `tw accept`、2回目からはメイン | `lap-hook`（受け入れ役の停止。開いているときだけ） |
| `retro` | `lap-hook`（振り返りのスキルの呼び出し） | `tw finish`（`done` の前） |
| `land`・`sync` | メイン | メイン |

`lap-hook` は関門ではなく記録で、何も拒まず何も出さない。書くのは控えがちょうど1件の作業ツリーだけで、start は段が閉じているとき（細部は `tw lap-hook --help`）。
end は手打ちも `tw`・hook も、最後の `claim` 以降でその段が開いているときだけ記録する（手打ちは開いていなくても `LAPPED` を出すが記録しない）ので、閉じた段に重ねても end は1つ。
メインの `--model` 付きの手打ちと hook が重なって同じ段の start が続いても、所要の集計（`tw metrics --stages`・振り返りの段の所要時間）は閉じていない同じ段の2つ目の start を数えない。
**`commit-guard`・`handback-guard`・`ask-guard` は Claude Code の hook の取り決めに従う**: 出力は TSV でなく JSON で、終了コードはいつも0（`ref-guard` は git の hook の取り決めに従い、拒むときだけ終了コード1）。
読めない入力も何も出さずに通す。タスク運用を始めていないリポジトリ・git の外でも打てる。
**落ちたときの扱い**（殻 `bin/tw-hook`）: `tw` が 78・127 で終われば案内して 0（通す）。ほかの非 0 は、`--fail-closed` を付けた `PreToolUse` の関門 4 つでサブエージェント（入力に `agent_id`）なら終了コード 2 で止め、主のセッション・`SubagentStop`（2 は「止まるな」になる）・`lap-hook` では 1 で通す。殻が起動できなければ非ブロッキングのエラーで通る。

tools・`permissions.deny`・git の hook で置き換えられない理由は `hook-rationale.md`（hook を足すか迷ったときだけ読む）。
