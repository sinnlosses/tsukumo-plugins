# 振り返り

タスクを1件やり終えるたびに得た「次はこうしたい」は、その場で言わないと消える。このスキルは
**`/next-task` が受け入れのあとに1件のタスクだけ**を材料に、**次に同じ状況が来たときに
エージェントの振る舞いが変わる、環境（道案内・機械の検査・コーディング規約・常に読み込まれる設定ファイル・
道具）の改善だけ**を書き留める。
7日おきに1回は、複数のタスクにまたがる形を材料の数から見直す（下の「週ごとに振り返る」）。

守ることが3つある。

1. **印は `## 結果` の `- 振り返り:` の1行。** 1件ごとの振り返り（下の「1件だけ振り返る」）は
   `/next-task` の手順6aで `tw done` の前に1回だけ行い、その1行が済んだ印になる。週ごとの振り返りの
   印は `docs/history/retrospect.md` の見出し1つ（`tw status` が読む）
2. **承認ゲートを通す。** 出力は `draft` の行のディレクトリ（例 `.tw/draft/`）にドラフトのファイルとして積む
   だけ。`docs/` も `CLAUDE.md` もタスクの本文も直接は書き換えない（1件ごとの印は
   `/next-task` が `tw done` の結果に入れ、週ごとの印は記録のファイルに足すだけ）。振り返りは
   「気づき」であって決定ではなく、正典を変えるかどうかはユーザーが決める
3. **会話の中身を写さない。** トランスクリプトから取るのはツール名・ファイルパス・
   コマンドの先頭2語・件数・時刻だけ。トランスクリプトには利用者と Claude の生の会話が
   入っているので、記録にもドラフトにも写さない（プロジェクトに会話内容の扱いの規約が
   あるなら、それが優先する）。`material.py` がこの線を引いているので、生の jsonl を
   自分で開かない

## 改善の7観点

改善の候補はこの7つの観点で探す（1件ごとの振り返りも、`retro` も）。観点の一覧はこの節にしか
書かない。直す相手はエージェントの**環境**で、タスクで書いたコードそのものの形ではない。
各観点の「使うとき」に当たるものを見る。

- **道案内**: エージェントが正しいファイルにどれだけ楽に辿り着けたか。ファイル間に隠れた依存が
  あるか。**文脈のポインタ**（「こういうときはここを読む」の1行）があれば楽になったか。
  _使うとき_: ある情報を見つけるのにセッションが長くかかった
- **機械の検査**: エージェントの誤りを捕まえられた自動の検査（lint・型・テスト・ファイル配置の
  検査）はあるか。まずリポジトリ自身の検査のコマンドを読む。既にあるのに配線されていない・
  黙って壊れている検査は、それ自体が発見になる（作り直すのではなく配線し直す）。**ガードレール**
  （lint・型検査・テストを走らせる pre-commit hook か CI のジョブ）が無いリポジトリは、それ自体が
  発見になる。検査の無いリポジトリは中立の既定値ではなく、取り逃し続けている機会である。
  _使うとき_: 自動の検査で捕まえられた誤りをエージェントがした、またはガードレールがまったく無い
- **コーディング規約**: **レビューのエージェント**に新しい規則を守らせるべきか。既存の規則を
  消す・はっきりさせるべきか。まず違反を分類する: **機械的な**違反（決まった構文の形・禁止の
  API・import の形・ファイルの置き場所の規則）には決定的な検査を作る、それで終わり（リポジトリの
  lint の自前の規則、新しい pre-commit hook、新しい CI のジョブ、PreToolUse の hook のうち、
  リポジトリの言語と既存のガードレールでいちばん安いもの）。規則を書くより検査を作るのを既定にする。
  規約の文書は本当の**判断もの**（ファイルをまたぐ一貫性、「周りの書き方に合わせる」など、どの
  ガードレールにも置き換えられないもの）のために取っておく。
  _使うとき_: レビューのエージェントが誤りを捕まえ損ねた
- **常に読み込まれる設定ファイル**: 規約（か機械の検査）へ移すべき指示はあるか。
  _使うとき_: `CLAUDE.md`・`AGENTS.md` が特に大きい（リポジトリでもユーザー単位でも）
- **道具の経済**: エージェントが高くつくツール呼び出しをしたか。それを縮められるか。トークンの
  効率が特に悪い自前の道具（CLI・MCP・スキル）はあるか。
  _使うとき_: エージェントが高くつくツール呼び出しをした（使用量の記録を集計するスキル
  （`token-usage-diet` など）が一覧にあれば、その数を根拠にしてよい）
- **空振り**: 設定ファイルの中で、エージェントの振る舞いを既定から変えていない指示を探す
  （`writing-for-agents` があれば、その「剪定」を試金石にする）。
  _使うとき_: 設定ファイルが大きく扱いにくい
- **情報への手の届き**: エージェントが手にできる情報を増やす機会を探す（開発サーバのログを
  ファイルにも流す、外部サービスへの読み取り専用の口など）。
  _使うとき_: 決め手になる情報がエージェントの手に無かった

## 色と1行の書式

振り返りで拾う引っかかりと改善の候補には、下の**色**を1つ付ける。色と1行の書式はこの節にしか
書かない（材料の表・ドラフト・`/next-task` の依頼文・`retro` はここを指す）。

| 色 | 目安 |
| --- | --- |
| `赤` | 止まった・人に預けた・壊れたまま先へ進みかけた（受け入れで落ちた・報告が実物と違った） |
| `黄` | 手間取ったが、その場で自分で戻せた |

候補を並べるときは `赤` を先に、`黄` を後に置く（重い順）。
「うまくいった」（緑）は書かない。次に振る舞いを変えないので、物差し（次に同じ状況が来たときに、
誰かの振る舞いが変わるか）で落ちる。`赤` は1件でもこの物差しにかける。

**1件の1行**（委譲先が作業中に書き留め、報告に載せる friction log）:

```markdown
- <色>: <何が起きたか（1文）>（<根拠の場所: ファイルパス・コマンドの先頭2語・節の名前>）
```

例: `- 黄: 検証コマンドが1回落ち、打ち直すと通った（pnpm run check）`

1行にはどの観点に当たるかを書かない（振り返るメインが、節「1件だけ振り返る」の材料の表で当てる）。
根拠の場所に会話の中身（発言・返答の文）を写さない（上の「守ること」3）。

## 1件だけ振り返る（`/next-task` の中から）

`/next-task` が受け入れ（手順6）のあと・`tw done` の前に、**メインが**まず判定の口を打つ
（`/next-task` の手順6a。5つの値の決め方もそこにある）:

```bash
python3 ${CLAUDE_SKILL_DIR}/../retrospect/scripts/material.py . T-XXX --gate --friction … --reverify … --fixes … --human … --review …
```

出力が `QUIET` の1行なら、この節も節「改善の7観点」「色と1行の書式」も読まずに、`## 結果` に
`- 振り返り: 兆候なし` を足して済ませる。`SIGNAL` の行が1つでもあれば、この節と節「改善の7観点」
「色と1行の書式」を読んで下の手順で行う。`/loop` から回っているときも走る。範囲は `material.py` に渡すタスクID 1つ。
材料はこのタスクの手数・差分・報告・受け入れだけで、過去のドラフト（`draft` の行のディレクトリ）と
`docs/history/` は読まない。上の「守ること」2・3はそのまま効く。

1. **数を取る**。本文と diff は受け入れで読み終えているので、判定の口が出した `SIGNAL` の行と
   手数の節を材料にする（打ち直さない）。
   手数の節が `-`（トランスクリプトが無い。委譲せずメインで進めたときなど）なら、受け入れで自分が見たことだけで判定する
2. **材料を観点に当てる**。材料ごとに当たりの目安を見て、当たったものを「当てる観点」の
   「使うとき」（節「改善の7観点」）と照らし、何を足す（直す・消す）かの候補にする:

   | 材料 | 見る場所 | 当たりの目安 | 当てる観点 |
   | --- | --- | --- | --- |
   | 検証の打ち直し | `よく打ったコマンド`／受け入れで自分が打った回数と一言メモ／friction log | 検証コマンドが3回以上／打ち直したら通った・単独で実行したら通った、が1回でもある | 機械の検査（揺れている・黙って壊れている検査） |
   | ツールのエラー | `エラー` | 3件以上 | 道具の経済・情報への手の届き |
   | 同じファイルの直し直し | `同じファイルを2回以上直した` | 同じパスが `×3` 以上（差し替え箇所の数ではなく、直し直した疑いがあるかで見る） | 情報への手の届き・道案内 |
   | 本文と差分のずれ | `tw show` のタスク本文と、受け入れ役の `- 指摘:` と `- 付随:` の行 | 本文が名指ししたファイル・節と、実際に直したものが違う／`## やること` が「前提が誤り」を報告した・`## 目的・背景` と違う前提で書かれている | 道案内 |
   | 受け入れでの直し | 受け入れ役の `- 指摘:` と `- 材料:` の行・自分の一言メモ | `## 完了条件`・`## やること` のどれにも当たらない変更がある／当たる指摘を差し戻した／メインが直した、が1つでもある | コーディング規約（機械的な違反なら機械の検査） |
   | 人の差し戻し | このセッションで人が止めた・直させた・やり直させたこと（委譲から `tw done` まで） | 1回でもある（人が止めたので色は `赤`） | 差し戻しで直した差分に合う観点（節「人に差し戻されたとき」） |
   | friction log | 委譲先の報告に載った friction log（節「色と1行の書式」の1行。「なし」なら何も起きていない）・受け入れで自分が気づいて直さなかったこと | `赤` の行が1件でもある（完了報告に書くだけで終えず、手順3の物差しにかける。既存のタスクが扱っているものは落とす）。`黄` だけなら他の材料と合わせて判断する。行自体が無ければ書き忘れとして扱う | 行の中身に合う観点 |
   | 付いてきた文書の変更 | 受け入れ役の `- 指摘:` と `- 付随:` の行 | 同じ事実を2か所以上の文書で直した／文書に写したパス・値・数・ファイル名を追随させた／索引や一覧を手で直した | 道案内（値は正典の1か所にだけ書き、他は節の名前で指す） |
   | 時間の偏り | `長く待った呼び出し`（段ごとの時間は週ごとの振り返りの観点「段の所要時間」で見る） | 1回の呼び出しが180秒以上で、その中身が検証・送り・錠の待ち | 道具の経済（その待ちを、変えたファイルに合わせて検証を絞る・錠を取らない・並べる、のどれかで縮められるか） |
   | `tw ship` の失敗（`VERIFY_FAILED` など） | ― | この時点ではまだ起きていない。止まったら `/loop` も止まって人に預かるので、ここでは扱わない | ― |

   表に無い観点（常に読み込まれる設定ファイル・空振り）は、このタスクで読んだ設定ファイルが
   その「使うとき」に当たったときだけ候補にする
3. **候補を物差しにかける**。候補ごとに、その箇所だけ材料を読み直し（`git diff -- <path>`、要れば
   `--signals` を外して `material.py` を打つ）、次に同じ状況が来たときに誰かの振る舞いが変わるかを問う。
   変わらないものは落とす（一度きりの事故、そのタスク固有の事情、「うまくいった」の確認は次に効かない）。
   残った候補には、色（節「色と1行の書式」）・観点・何を足す（直す・消す）か・根拠（上の「守ること」3の形）を付ける
4. **どの材料にも当たらなければ何も積まない**（「うまくいった」は書かない）。
   `## 結果` に `- 振り返り: 兆候なし` を足す
5. **残った候補を、起こされ方で分けて扱う**:
   - **利用者が `/next-task` を直接呼んだとき**: 候補を色の重い順（`赤` → `黄`）に、1件1行で
     色・観点・何を足すか・根拠を添えて示し、どれを採るかを利用者に聞く。採ると答えたものだけを
     下の「ドラフトに積む」へ。1件も採られなければ積まない
   - **`/loop` から回っているとき**: 人がいないので聞かず、残った候補をすべて下の「ドラフトに積む」へ
     （承認は、ユーザーがいるセッションで `/plan-tasks` が取る）

**ドラフトに積む**（手順5で積むと決まったものだけ）:

1件を1ファイルにして `draft` の行のディレクトリ（例 `.tw/draft/`）に足す（既存のファイルは書き換えない）。ファイル名は
`<YYYY-MM-DD>-<英小文字・数字・ハイフンの要約>.md`（`task-workflow` の `WORKFLOW.md`「指示メモ」）で、
中身はこの形:

```markdown
# <何を変えるか（1行）>（振り返り: T-XXX）

- 観点: <色> <節「改善の7観点」の観点の名前>
- 根拠: <材料のどこにどう出ていたか。数で言えるものは数で>
- 出し先: <どのファイルのどの節に足すか / タスクにするなら何をするタスクか>
```

`- 観点:` の行は1つ（色は節「色と1行の書式」の2つから、観点は節「改善の7観点」の7つから1つずつ）。

**機械的な違反なら、出し先は決定的な検査にする**（決まった構文の形・禁止の API・import の形・
ファイルの置き場所の規則。節「改善の7観点」の「コーディング規約」）。規約・手順の文書に足すのは、
どの検査にも置き換えられない判断ものだけ。

`direction` の行のファイル（例 `.tw/direction.md`）の `## ユーザーから` には書かない（あそこはユーザーの入口）。ここに積んだ
ものは、ユーザーの承認を得てから `/plan-tasks` がタスクにする（`task-workflow` の `WORKFLOW.md`「指示メモ」）。

`## 結果` には `- 振り返り: <当たった材料・観点>（ドラフト N件）` を足す（物差しで落とした・利用者が
1件も採らなかったら `0件`）。
行頭の `- 振り返り:` は機械が読む（`tw done` がこの行から `flow/` の `reflection` を決める。
`task-workflow` の `WORKFLOW.md`「結果の書き方と知見の置き場」）ので形を変えない。積んだドラフトの
ファイルは、`/next-task` の手順7で作業と同じ1コミットに入る。

## 週ごとに振り返る（`/next-task` の頭から）

1件ごとの振り返りは、複数のタスクにまたがる形（流れの数が悪くなる・規則が増える一方になる）を見ない。それを見るのがこの節で、
`tw status` が `retrospect_due` の行を出したとき（最後の記録から7日以上。記録が無いあいだは
台帳の `flow/` の最も古い出来事から7日以上）に、`/next-task` が選ぶ前に**メインが**この節だけを
読んで1回行う。`/loop` から回っているときも行う。上の「守ること」2・3はそのまま効く。

1. **材料を出す**（期間はスクリプトが最後の記録から決める。7〜28日）:

   ```bash
   python3 ${CLAUDE_SKILL_DIR}/../retrospect/scripts/weekly.py .
   ```

   読み直すのはこの出力だけ。ドラフト・`docs/history/` の履歴・トランスクリプト・`material.py` は
   開かない（選ぶ前の手番を長くしない）
2. **3つの観点で、ドラフトにするかを数で決める**（どの観点も、1つにつきドラフトは1件まで）:

   | 観点 | 材料の行 | 当たりの目安 | 出し先にするもの |
   | --- | --- | --- | --- |
   | 流れの数 | `WORSE`・`CHANGE` | `WORSE` がある（良くなった・変わらない数は書かない） | 悪くなった数と、同じ期間に入ったやり方の変更（`CHANGE`）を並べた原因の候補と、それを確かめる・戻す手 |
   | 段の所要時間 | `STAGE`（4列目が道 `direct`／`normal`） | 1つの段の中央値が、同じ `difficulty`・道の着手から送り出しまで（流れの数の `lead_median_seconds`）の半分以上。または同じ `difficulty` で `direct` の段の合計が `normal` より縮んでいない | その段を縮める手（検証を絞る、など）。`direct` と `normal` の比較からは、委譲しない近道の基準の表（task-workflow の正典「difficulty とモデルの切り替え」）を狭めるか広げる手 |
   | 規則の棚卸し | 規則の発火の集計の出力 | 期間（30日）に1度も拒んでいない hook がある／拒んだ回数が多い hook がある | 0回の hook は消す候補、多い hook は規則か道具の側を変える候補（拒まれる前に正しい形が手に入るようにする） |

   規則の棚卸しの材料は、`tw config` の `hook_tally` の行の
   値（例 `` `node scripts/hook-denial-tally.ts --days 30` ``。直近30日の hook ごとの
   拒否の回数を出すコマンド）。行が `なし` のプロジェクトでは、この観点を飛ばす。

   当たったものは物差し（次に同じ状況が来たときに振る舞いが変わるか）にかけ、残ったものだけを積む。何も残らなければドラフトは積まない
3. **ドラフトを積む**: 形は節「1件だけ振り返る」の「ドラフトに積む」と同じで、違いは2つ:
   - 見出しの括弧は「（横断の振り返り: <開始日>〜<終了日>）」（`PERIOD` の3・4列目）
   - `- 観点:` の行には色を付けず、上の3つの観点の名前を1つ書く

   ```markdown
   # <何を変えるか（1行）>（横断の振り返り: 2026-09-27〜2026-10-04）

   - 観点: <流れの数 | 段の所要時間 | 規則の棚卸し>
   - 根拠: <材料のどの行にどう出ていたか。数で>
   - 出し先: <どのファイルのどの節を変えるか / タスクにするなら何をするタスクか>
   ```
4. **記録を書く**（ドラフトが0件でも必ず）: `docs/history/retrospect.md`（無ければ見出し
   `# 横断の振り返りの記録` で作る）の最初の `## ` の前に、次の3行を足す。前の回の記述は書き換えない。
   `tw status` はこの見出しの日付を読むので、見出しの形を変えない:

   ```markdown
   ## <今日の日付 YYYY-MM-DD>（<開始日>〜<終了日>）

   - 材料: WORSE <件数>・段の所要時間 <あり | なし>・規則の発火の集計 <あり | なし>
   - ドラフト: <件数>件（<ファイル名, …> | なし）
   ```
5. **送る**: ドラフトのファイルと記録だけを個別に `git add` し、件名
   `横断の振り返り（<開始日>〜<終了日>）` の1コミットにして `tw ship` で送る（タスクIDは置かない）。
   送れなければ `/next-task` と同じく出力を添えて止まる（記録が主ブランチに入らないと、ほかの作業ツリーでは
   due のまま）

## 人に差し戻されたとき

人の訂正・やり直し・revert は一番強い材料だが、人の発言が差し戻しかどうかはトランスクリプトの
数からは分からない。だから**その場にいるメインが自分で書き留める**。`/loop` から回っているときは
人がいないので起きない。

- **観点は、差し戻しで自分が直した差分から当てる**（何を直したか → 節「改善の7観点」）。
  人の発言を観点の根拠にして写さない。色は `赤`
- **根拠に書くのはタスクID・コミット・パス・件数だけ**（上の「守ること」3）。
  「人に差し戻された」以上の中身（誰が何と言ったか）は書かない
- **`tw done` の前**（受け入れの途中）なら、「1件だけ振り返る」の材料「人の差し戻し」として扱う
- **`tw done` のあと**に戻させられた・直させられたなら、その場で候補を示して採るかを聞き
  （「1件だけ振り返る」の手順5の「利用者が直接呼んだとき」と同じ）、採られたら上の「ドラフトに積む」と
  同じ形で `draft` の行のディレクトリ（例 `.tw/draft/`）に1件積み、戻す・直すコミットと一緒に入れる

## 他のプロジェクトで使うとき

**前提は `task-workflow` の運用**（task・`draft` の行のディレクトリと `docs/history/`、
**コミットの件名にタスクIDを置く**）。この運用のプロジェクトなら、置き場も
IDの形も同じなので何も変えずに動く。

前提が揃わないプロジェクトでは、スクリプトは落ちずに `-` と欠席の理由を出す（材料が減るだけ）。
そのうえで次の4つが合わないなら、合わせるか、このスキルを使わない:

| 前提 | 使っているところ | 合わないときの影響 |
| --- | --- | --- |
| タスクIDが `T-` + 3桁以上 | `material.py` の照合 | `material.py` がコミットを1件も拾えず、材料が空になる |
| コミットの件名にタスクIDがある | 同上 | 同上 |
| タスクが Beads にある（Beads に無い古いタスクは `docs/history/tasks.md`・`docs/history/progress.md`） | `material.py` の材料2つ（タスクの本文と、登録から完了までの差分） | 材料がコミットと手数だけになる |
| ドラフトを `draft` の行のディレクトリに1件1ファイルで置く | 「1件だけ振り返る」の「ドラフトに積む」の出し先 | 積む先が無い。プロジェクトの「未対応の指示の置き場」に読み替える |

送り方は `tw ship` が CLAUDE.md の `- ブランチ:` に従って決める（このスキルは「ドラフトのファイルを
指定してコミットし、`tw ship` で送る」としか決めていない）。

## このスキルがしないこと

- **ドキュメントを直さない・タスクを登録しない。** 承認ゲートの手前で止まる（上の「守ること」2）。
  書くのはドラフトと、週ごとの記録 `docs/history/retrospect.md` に足す見出しだけ
- **タスクの是非を蒸し返さない。** 「あのタスクはやるべきでなかった」は振り返りの対象外で、
  見るのは*やり方*と、それを支えるエージェントの環境（節「改善の7観点」）だけ
