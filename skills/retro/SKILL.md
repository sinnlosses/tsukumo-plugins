ユーザーが**振り返り（retrospective）**を求めた。直す相手はコーディングエージェントの**環境**
（道案内・機械の検査・コーディング規約・常に読み込まれる設定ファイル・道具）で、次の回の作業を
良くするための改善案を出す。

`retrospect`（`/next-task` が1件ごと・7日おきに自動で行う振り返り）とは材料と起こし方が違う。
こちらは**ユーザーが手で呼び、1つのセッションを丸ごと**材料にする。改善の7観点・色・ドラフトの形は
`retrospect` の SKILL.md にある（下の手順4〜6）。

## 守ること

1. **根拠は数と場所で書く。** 改善案にもドラフトにも、根拠はツール名・ファイルパス・コマンドの
   先頭2語・件数・時刻で書き、利用者と Claude の発言・返答の文は写さない。プロジェクトに会話内容の
   扱いの規約があるなら、それが優先する
2. **承認ゲートを通す。** このスキルが出すのは改善案と、ユーザーが選んだものの指示メモのドラフトまで。
   CLAUDE.md・規約・検査・hook を変えるのは、ドラフトがタスクになってから

## 手順

1. **書き方の物差しを読む。** スキルの一覧に `writing-for-agents` があれば、Skill ツールで呼ぶ。手順4の観点と、改善案の
   中身（ポインタの言い回し・情報の階層・空振り・先導語）はこの物差しで測る。無ければ下の「参照」の
   「ファイルの使い分け」を物差しにする。
   _済んだ印_: `writing-for-agents` が文脈にあるか、一覧に無いと確かめた

2. **材料を決める。** ユーザーがセッションを指定しなければ、いまのセッション（自分の文脈にある
   やり取り）を材料にする。過去のセッションを指定されたら、残っている記録から数で拾う:
   そのセッションのコミット（`git log`）、タスクの `## 結果`（task-workflow の運用なら `tw show`）、
   プロジェクトに集計の道具があればそれ（`tw config` の `hook_tally` の行など）、
   サブエージェントの手数（タスクに紐付くセッションなら
   `python3 ${CLAUDE_SKILL_DIR}/../retrospect/scripts/material.py . <タスクID> --signals`）。
   セッションのログ（jsonl）の本文は材料にしない（守ること1）。
   _済んだ印_: 材料にするセッションと、そこから取った記録の一覧が決まっている

3. **プロジェクトの今の環境を読む。** 既にあるのに効いていないものが、見つけるべきものの筆頭:
   - 常に読み込まれる設定ファイル（`CLAUDE.md`・`AGENTS.md`。リポジトリとユーザー単位の両方）
   - 検査のコマンド（`tw config` の `verify` の行、`package.json` などの
     `lint`・`check` スクリプト、CI のワークフロー）と、pre-commit などの hook
     （`.claude/settings.json` の `hooks` を含む）
   - コーディング規約の正典（CLAUDE.md が指す文書）と、レビューの観点（`code-review` スキルがあれば、その
     Standards 軸が何を読むか）

   _済んだ印_: 上の3種のそれぞれについて、あるか・どこにあるかが言える

4. **改善の候補を7つの観点で探す。** 観点は `retrospect` の SKILL.md
   （`${CLAUDE_SKILL_DIR}/../retrospect/SKILL.md`）の節「改善の7観点」にある。読んで、各観点の
   「使うとき」に当たるものを見る。
   _済んだ印_: 「使うとき」に当たった観点のすべてに、候補か「候補なし」が付いている

5. **候補を重い順にユーザーへ示す。** 物差しにかけ、示し方は `retrospect` の SKILL.md の節
   「1件だけ振り返る」の手順3と、手順5の「利用者が直接呼んだとき」に従う（色は節「色と1行の書式」、
   根拠は守ること1の形）。
   _済んだ印_: ユーザーがどの候補を採るかを答えた

6. **選ばれたものをドラフトに積む。** ユーザーが採ると言った候補だけを、`retrospect` の節
   「1件だけ振り返る」の「ドラフトに積む」と同じ形で
   `draft` の行のディレクトリ（例 `.tw/draft/`）に1件1ファイルで足す。見出しの `（振り返り: ...）` には、セッションで扱った
   タスクID を並べる（無ければ `（振り返り: セッション <YYYY-MM-DD>）`）。
   ドラフトのコミットと送り方は `retrospect` の節「他のプロジェクトで使うとき」に従う。
   `draft` の行が無いプロジェクト（task-workflow の運用でない）では、手順5の一覧で終える。
   _済んだ印_: 採った候補の数と同じ数のドラフトが送られている

## 参照

### 実装とレビュー

作業はすべて実装とレビューの2段を通る。実装のエージェントが最も**文脈の圧迫**を受ける。
探索・コードを書くこと・失敗のデバッグを受け持つからだ。

レビューのエージェントの文脈の圧迫は最も小さい。差分を受け取るので探索が要らず、多くの場合
コードを書くこともデバッグすることもない。

だから、コーディング規約を課すのはレビューのエージェントの役目にする。

### ファイルの使い分け

- `CLAUDE.md`/`AGENTS.md`: このリポジトリで働くどのエージェントの文脈にも押し込まれる。ごく控えめに
  使い、たいていは別のファイルへの**文脈のポインタ**だけにする
- コーディング規約の文書: 実装中ではなくレビューのときに読まれる。1,000行を超えたら、docs の
  ディレクトリへの**文脈のポインタ**を足す
- docs: 他のファイルから指される参照用のファイルとして使う。新しく書く前に既存の docs を探す
- スキル: 説明（`description`）がエージェントの文脈に入るので、docs の代わりにも、ユーザーが呼ぶ
  コマンドにも使う。`writing-for-agents` があれば、書き方はそれに従う
