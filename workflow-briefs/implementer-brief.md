# 実装の依頼の決まり

ワークフロースクリプト `task-flow` の実装の agent が、最初に読んで従う決まり。タスクごとに変わること（タスクID・渡された段・別のリポジトリ・並列の段・描画）は依頼文（`implementer-request.md`）が足す。

## タスクの読み書き

- まず `tw show <ID>` で読む。書き足すときは節の中身だけを `tw edit <ID> --section '<節名>' --body-file -` に渡す。
- 前提が崩れていて作業が要らないと分かったら、作業せずに止まって、`dropped` にすべき理由を報告する（`## やること` は書かなくてよい）。
- `## 目的・背景` がファイルの存在・パス・行番号を主張していたら、作業の前に実物で確かめる（別のリポジトリのファイルなら、そのリポジトリの実物を見る）。違っていたら直さず「前提が誤り」と報告する。
- 本文が見本（画・ラフ）のパスを名指していたら、最初にそれを開いて読み、`## やること` と作るものを見本と食い違わないようにする。
- 本文に `## 結果` の節を書かない（`tw done` が書く）。
- 完了条件が後段のタスクの本文を直す・分けるよう求めていても、後段には手を付けず申し送りだけ書く（本文の編集と `tw new` での分割はメインが受け入れで行う）。

## コミットと `tw` コマンド

- コミットしない（別のリポジトリが作業先のときだけ、依頼文のとおりにコミットする）。`git push`・`git worktree remove`・`git branch -d`・書き込みの `bd` も打たない。打ってよい `tw` は `show`・`edit`・`verify`・`step`・`pause`・`relay`（依頼文が言うとき）だけ。
- ドラフトにしたい改善は、報告に `- ドラフト: <何を変えるか（1行）>`（子項目に `根拠`・`出し先`）で書く。メインが積む。
- 検証コマンド（check の全段）は `tw verify` 以外で打たない（対象を絞った単体・E2E のファイル単位は打ってよい）。一部の段が落ちたら、落ちた1本だけを絞ったコマンドで直し、`tw verify` は直ってから1回だけ打つ（全件には回数の上限がある）。通したあとにファイルを変えたら打ち直す。
- `tw verify` が背景に回ったら、止めず、`^VERIFIED` か失敗の行が出るまで待ってから返す。待つあいだ別の `tw verify` を打たない。
- `CONFLICT` が出たら、計画が別の手順を名指していればそれに従い、そうでなければ解かずに、衝突したファイルを添えて報告して止まる。

## 段の進め方と返却

- `## やること` の段（`### <n>.`）を、渡された段だけ進めて返す。次の段は `SendMessage` で届く。作業があるなら、返す前に `## やること` を `tw edit` で書いておく。
- 最後でない段は返す直前に `tw step <ID> <段の番号>` を打つ。`STEP_CHECK_FAILED` なら指摘を直して打ち直す。最後の段は `tw verify` を通してから返す。
- `tw step` に `MAIN_TOUCHED\t<ID>\t<ファイル>` が出たら、主ブランチがそのファイルを変えている。別のリポジトリで着手後に自分のコミットがあるなら、何もせず次の段へ進む（取り込みは送り出しが行う）。それ以外は次の段の前に、(1) 重なるファイルだけを作業ツリーの外へ退避し、(2) `git restore <ファイル>`、(3) `tw verify` で取り込み（`CONFLICT` なら止まる）、(4) 退避した内容に主ブランチの変更を写し直す。`rebase`・`reset`・マージは使わない。
- `tw verify` を打たずに返すとき（判断待ちで止める・`CONFLICT`・計画を作業の後に書いた・目視待ち・`tw verify` を打たないよう言われた直し）は、返す直前に `tw pause` を打つ。着手後のコミットも変更も無いタスク（計測と案づくりだけ）の最後の段も、`tw step` でなく `tw pause` を打って返す（`tw verify`・自己点検・`## 構造の変更` は要らない）。`tw step`・`tw pause` のあとに中身を変えたら打ち直す。
- 返却の本文の先頭に、した結果を1文で書く。止めたときは先頭を `止めた:`・`前提が誤り:`・`dropped にすべき:` で始めて理由を続ける。
- 段を済ませたら（止めたときも）、`SubagentHandback` の直前に `phase_result` を1回呼ぶ（`phase`＝渡された段の番号、`count`＝`## やること` の段の数、`outcome`＝`finished`／`stopped`（1〜2文の `reason`）／`skipped`）。計画だけの回と、ツールが無い環境では呼ばない。
- 最後の段の返却には `## 構造の変更` の節を書く（形は依頼文）。
- 段の区切りと長いコマンドの前に、`SendMessage({to:"main"})` で `状況 | 何をした・何が分かった` の1行を送る（段の番号は入れない）。

## 自己点検（最後の段の担当だけ）

- `tw verify` の前に、このファイルと同じディレクトリの `self_review.py` を打つ。差分を読むので、コミットする作業先ではスクリプト → 直す → コミット → `tw verify` の順。前の段のコミットも点検するなら `main..<枝>` を渡す。`SELF` の行ごとにコマンドを打って答え、当たったものを直す。`SKIPPED` の行はそのまま報告に書く。
- 続けて差分（`git diff HEAD` と未追跡のファイル。範囲を渡したならその範囲）を、同じディレクトリの `review-criteria.md` の4種類で点検し、当たるものを直す。
- 答えは `自己点検: <性質か「観点」>: 当たり、<直したこと>` か `…: 外れ` の1行ずつ。`自己点検: なし` はスクリプトが `NOTHING` で観点も外れのときだけ。

## 報告

- `## 完了条件` の各行について、満たしたか・何で確かめたかを1行ずつ書く。見た目や設定を変えたら、効いたことを実物で確かめる。画面に出るものを変えたら、変えた場面を撮って画像の絶対パスを書き（撮れなければ理由）、完了条件が挙げる状態・幅・モーダルの中まで撮り、崩れ・はみ出し・重なりが無いかを自分で見る。
- 書き始める前に、プロジェクトの規約の索引から触る層・種類の節を読み、`- 規約: <読んだ節の名前>`（読まなかったら `なし`）の1行を書く。
- friction log: 作業中に気づいた時点で、`tsukumo-workflow:retrospect` の `detail.md`「色と1行の書式」の1行（`- <色>: <何が起きたか>（<根拠の場所>）`）で書き留め、報告に載せる。打ち直したら通った検証も書く。何も無ければ `- friction log: なし`。
- 報告に書く数は、測ったコマンドの出力をそのまま写す。

## 作業の作法

- ファイルは `Edit`（多箇所は `replace_all` か1か所ずつ）・`Write` で書く。作業ツリーに置かない控えは `/tmp/<名前>/…` へ。一括に直したら `git diff --stat` で名指しの外が変わっていないかを見る。
- `git stash` は `list`・`show` 以外を使わない。前後を見比べるなら `git show HEAD:<path>`。
- グローバルへのリンク・ホームのファイル・グローバル設定を触らない。外部に捨てる資源を作る前に、`gh auth status` のスコープで消せることを確かめる。
- `/` やホーム全体を `find` で探さない。待つコマンドには上限を付け、背景のコマンドは報告の前に止める（背景に回った `tw verify` だけは完了まで待つ）。止めてよいのは自分で起こした pid だけで、ほかは pid と理由を報告に書く。
- 作業先が tsukumo-plugins で task-model を直すときは、段の途中は名前を渡したテストだけを流す（`selftest_t_*` は `python3 skills/task-model/scripts/tests/selftest_task.py`、`selftest_b_*` は `…/selftest_beads.py`）。全件は最後の `tw verify` でだけ流す。
- コメントは、消すと壊れる場面を言えるものだけ足す。コードの言い直し・経緯・採らなかった案・ほかの箇所との照らし合わせ・規約の要約は書かない。書き換えたコードのコメントが食い違っていないかも見る（細則はプロジェクトの規約）。
- 全体についての事実（「既定は〜」「〜のときだけ」）を書くときは、当てはまる箇所を全件数えてから書き、数えた手と件数を報告に書く。
- 関数を移す・形を変えるときは、呼ぶたびに評価される引数（時刻・カウンタ・乱数など）を1回にまとめていないかを `git show main:<ファイル>` と突き合わせる。
- 名前・振る舞い・条件を変えたら、変えた識別子と消した語で grep し、同じことを言うコメントと文書を揃える。言い換えた主張（「掛からない」「だけ」）も洗い、残した文は報告に書く。
- コマンドの手順を書く文書を変えたら、書いた順を一時の状態で実際に打つか、順を縛る実装の行を根拠として報告に添える。手順を言う箇所はコマンド名で全件 grep する。
- 検査を置き換える・足す段では、(1) 弱めた実装で自己テストが落ちること、(2) 実行時間の前後で既存の単体がタイムアウトしないことを確かめる。
- テストを足すときは、守りたい性質ごとに1行壊した版で既存のテストが落ちるかを見て、落ちない性質だけを足す。報告に `性質 | 壊した版で既存が落ちたか` の表を書く。
- 計画だけの回で、計画が頼る実行時の値（分岐・待ち・完了の判定の根拠）は、代表の場面で1回走らせて取れることを確かめ、打ったコマンドと結果を段の「前提の裏取り」に書く。出力は作業ツリーの外に置く。
- `Agent` ツールがあっても、サブエージェントの中では別のエージェントを立てない。
